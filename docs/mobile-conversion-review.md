## 0. 결론 요약

**추천: 방식 2 — Hades(C#) 서버·JSON 데이터·게임 규칙은 유지하고, 모바일 클라이언트만 새로 만든다.** 서버에는 모바일용 접속 계층(게이트웨이)을 작게 덧붙인다.

- 이유 1: 검토한 17개 저장소 중 게임 규칙·데이터·서버 로직이 실제로 갖춰진 것은 Hades 하나뿐이다(확인됨, 분석서 01·05). 다른 후보(Medenia)는 아이템·스킬·전투가 자리표시자 수준이다. 현재 작업공간에는 직접 재사용 가치가 낮은 `DungMunkey/Dark-Ages`를 제외한 16개를 유지한다.
- 이유 2: "기존 클라이언트"는 셋 다 모바일로 고칠 수 없다. 원본은 소스가 없는 Windows 실행 파일, DAGL은 미완성 C# 데스크톱 코드, Medenia 웹 클라이언트는 Hades와 말이 통하지 않는다(2절 방식 1).
- 이유 3: 전부 새로 만들면 Hades에 이미 있는 전투 공식·스크립트·설정 100여 개를 다시 만들어야 한다. 검증된 규칙을 버리는 셈이다(2절 방식 3).
- 유지 가능 근거: 서버와 저장소는 PC에서 돌고 클라이언트 플랫폼과 무관하다. 프로토콜은 원본 클라이언트 형식이지만 정의가 Arbiter·da-lib에 전부 있어 모바일 쪽에서 구현하거나 게이트웨이로 감쌀 수 있다(3절).
- 단서: Hades를 끝까지 실행해 본 적이 아직 없다(로그인→맵 입장 미검증). 방식 2의 첫 단계는 이 검증이다(4절 Phase 0).
- 제외 결정: `DungMunkey/Dark-Ages`는 네트워크·로그인·DB가 없는 C++/SDL2 오프라인 재현물이므로 모바일 MMORPG 기준선에서 제외하고 2026-09-08 submodule을 제거했다. 원격 GitHub 저장소는 삭제하지 않았다.

사용자 질문 "C# 기반으로 복원을 완벽히 해서 변환하는 게 가장 완성도 높은가?"에 대한 답: **서버는 그렇다. 클라이언트는 "복원"이 아니라 "신규 제작"이 맞다.** DAGL을 완성하는 길은 신규 제작보다 비싸다(2절 방식 1).

### 방식 2. 서버·DB·게임 데이터 유지 + 모바일 클라이언트 신규 제작 (추천)

- **재사용 범위**
  - 서버 전체: 로그인·리다이렉트·게임 루프·전투 공식·몬스터 AI 스크립트·아이템 장착 로직·설정 100여 개(분석서 04·05, `ServerConstants`, `database/server/scripts`)
  - 저장소: JSON 파일 그대로(`database/server/aislings`, `templates/*`). 서버 로컬 디스크라 클라이언트와 무관
  - 게임 데이터: 맵(`.map`)·지역·워프·템플릿
  - 원본 리소스 + 해석기: `LOD_/raw_data/*.dat` + `da-lib` → 모바일 엔진용 이미지·아틀라스로 변환. `LOD_/extracted`가 이미 있으면 변환 단계 일부 생략
  - 프로토콜 정의: Arbiter.Net 메시지 체계와 da-lib 암호화를 모바일 쪽 네트워크 계층의 사양으로 씀
  - Medenia 웹 클라이언트: "원본이 아닌 클라이언트로 맵을 그리는 방법"의 참고(씬 구성, 타일 렌더, 자산 폴더 구조)
- **난이도: 중~상.** 핵심 과제 세 가지
  1. 네트워크: 모바일 클라이언트가 원본 형식(0xAA 프레임, XOR 암호화, 718 패킷 배치)을 직접 말하거나, 서버 옆에 WebSocket/JSON 게이트웨이를 두어 통역. 둘 다 정의가 있어 가능하며 선택 문제(4절)
  2. 렌더링: 원본 리소스는 팔레트 기반 8비트 이미지(EPF/MPF/HPF/SPF + PAL/TBL). 엔진이 바로 못 읽으므로 변환 파이프라인이 필요. da-lib에 렌더 코드(`Graphics.RenderMap`, 팔레트 룩업)가 있어 규칙은 확보됨
  3. UI/입력: 원본은 키보드·마우스 전제. 터치 이동, 스킬 슬롯, 채팅 입력을 새로 설계
- **위험 요소**
  - Hades 미검증: 로그인→맵 입장이 실제로 되는지 아직 확인 안 됨. 콘텐츠(맵 5개, 스크립트 컴파일)로 완주 가능한지 미확인 (run-procedure 8절 13번)
  - .NET 5 지원 종료: 서버를 .NET 8로 올려야 함. 의존 패키지(ServiceStack 5.10, Roslyn 3.8, Newtonsoft 12)는 관리형이라 승격 가능성 높음(추정)
  - 클라이언트 버전 검사: `LoruleConfig.json` `ClientVersion` 718을 서버가 비교. 모바일 클라이언트는 이 값을 맞춰 보내거나 검사를 우회하는 설정 필요(설정값이라 코드 수정 없이 가능, 확인됨)
  - 모바일 네트워크 특성(끊김·백그라운드 전환·재접속)에 대한 서버 대응이 없음(추정). 게이트웨이 계층에서 흡수하는 게 안전
  - 원본 클라이언트만 아는 규칙(클라이언트 측 검증, 패킷 순서, 애니메이션 타이밍)이 있을 수 있음. Arbiter로 원본 클라이언트 통신을 캡처해 대조해야 함(미확인)
  - 리소스 저작권: 원본 .dat는 넥슨/KRU 자산. 개인 실험과 배포는 다른 문제(분석서 09)
- **예상 작업량: L.** 클라이언트 신규(L) + 리소스 변환 파이프라인(M) + 서버 보강·게이트웨이(S~M). 서버 로직 재작성이 없다는 점이 방식 3과의 차이

## 3. "기존 서버·DB·게임 데이터 유지"가 가능한가

**가능하다.** 불가능 근거는 발견되지 않았다. 다만 조건이 셋 있다.

1. **프로토콜은 원본 클라이언트 형식이다(확인됨).** `NetworkServer`가 TCP로 2610/2615에 바인드하고, 패킷은 0xAA 프레임·XOR 암호화·번호(Format)로 구분된다(분석서 06). 모바일 클라이언트가 이 형식을 그대로 구현하거나 게이트웨이가 통역해야 한다. 정의가 Arbiter.Net(메시지·타입 전부), da-lib `PacketCryptoProvider`(암호화), Decipher `NexonPacket.Transform`(변환 표)에 있어 "구현 항목"이지 "불가능"이 아니다.
2. **저장소는 파일이다(확인됨).** `AislingStorage`가 `database/server/aislings/<이름>.json`으로 저장한다. 서버가 한 대인 동안은 그대로 두면 되고, 사용자가 늘면 DB로 옮기는 별도 과제가 생긴다(추정). 모바일 전환 자체와는 무관하다.
3. **실행 검증이 선행돼야 한다(미확인).** Hades가 실제로 로그인→맵 입장까지 되는지, 콘텐츠로 완주가 되는지는 아직 확인하지 못했다. 원본 7.41 클라이언트를 Spark로 127.0.0.1에 패치하고 `ClientVersion`을 741로 바꿔 시도하는 절차가 `docs/run-procedure.md` 10절 A단계에 있다. 7.18↔7.41 패킷 호환은 미확인이라, 안 되면 README의 7.18 클라이언트로 재시도한다.

유지하지 **않아야** 하는 것: Medenia 서버·SQLite. Hades와 별개 세계이고 콘텐츠가 얕다. 실행 대상에서 제외하고 저장소는 참고용으로 남긴다(삭제 불필요, submodule 포인터만 유지).

## 5. Codex 인계 메모
