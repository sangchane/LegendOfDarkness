- 기준일: 2026-09-08
- 기준선: Hades/Lorule C# 서버 + 기존 JSON/MAP/스크립트 + 신규 모바일 클라이언트
- 선행 문서: [모바일 전환 기술 검토서](mobile-conversion-review.md), [현행 프로젝트 분석서](current-system-analysis/README.md)

표기:

## 0. 테스트 버전 정의

첫 테스트 버전은 아래 한 줄 흐름이 실제 모바일 기기에서 끝까지 이어지는지만 검증한다.

> 앱 실행 → 로그인 → 캐릭터 선택 → 맵 입장 → 이동 → NPC 대화 → 기본 전투 → 아이템 획득

대상 사용자는 일반 이용자가 아니라 개발 중인 빌드를 검증하는 내부 테스터다. 회원 모집, 장기 플레이, 운영 및 수익화 가능성을 검증하는 버전이 아니다.

## 1. 개발 목적

### 목표

1. Hades 서버의 인증·맵·이동·대화·전투·아이템 흐름을 신규 모바일 클라이언트에서 재사용할 수 있는지 검증한다.
2. 4방향 타일 MMORPG를 터치 조작만으로 플레이할 수 있는지 검증한다.
3. 완성형 개발 전에 프로토콜, 콘텐츠 데이터, 모바일 성능에서 막히는 지점을 찾아낸다.

### 성공 지표

- SC-001: 사전에 준비한 테스트 계정으로 위 전체 흐름을 10회 연속 완료하며 앱과 서버가 비정상 종료되지 않는다.
- SC-002: 각 실행에서 획득한 테스트 아이템이 화면의 최소 인벤토리 표시와 `database/server/aislings/<username>.json` 양쪽에 반영된다.
- SC-003: 신규 테스터 5명 중 4명 이상이 별도 설명 없이 이동, NPC 대화, 기본 공격, 아이템 줍기를 각각 1회 완료한다.
- SC-004: 네트워크를 제외한 모든 필수 조작 요소의 터치 영역이 최소 48×48dp다. 이는 [Android 접근성 권장 기준](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views)을 따른다.

## 2. 지원 플랫폼과 화면 방향

| 항목 | 첫 테스트 범위 | 상태 |
|---|---|---|
| 플랫폼 | Android 스마트폰 1종과 iPhone 1종 | 사용자 요구 반영 |
| 운영체제 최소 버전 | 엔진과 기준 시험 기기를 결정한 뒤 확정 | **결정 필요** |
| 화면 방향 | 가로 방향 고정 | **제품 가정** |
| 기준 화면 | 16:9를 기준으로 구성하되 20:9에서 잘림 없이 표시 | **제품 가정** |
| 입력 | 터치만 필수. 키보드·마우스·게임패드는 검증 대상 아님 | 확정 범위 |
| iOS | iPhone 실기기에서 전체 핵심 흐름 검증. 빌드에는 macOS와 Xcode 필요 | 확정 범위 |
| 태블릿 | 첫 테스트에서 제외 | 확정 범위 |

가로 방향은 왼손 이동 패드, 중앙 게임 화면, 오른손 행동 버튼을 동시에 배치하기 위한 최소안이다. 최종 제품의 화면 방향을 확정하는 결정은 아니다.

화면비 검증은 16:9(기준)와 20:9(최소 확장) 두 가지에서만 한다. 21:9 이상은 좌우 여백(레터박스)을 허용하고, 기기 안전 영역(노치·둥근 모서리)은 P0 UI 배치에서 제외한다. 두 비율 모두에서 P0 UI가 잘리지 않아야 한다(AC-014).

## 3. 포함 기능과 제외 기능

### 3.1 포함 기능(P0)

| ID | 기능 | 최소 동작 |
|---|---|---|
| FR-001 | 앱 실행 | 로컬에 포함된 필수 리소스를 읽고 로그인 화면을 표시한다. |
| FR-002 | 로그인 | 테스트용 사용자명과 비밀번호를 서버에 보내 성공·실패 결과를 표시한다. |
| FR-003 | 캐릭터 선택 | 인증된 계정과 같은 이름의 캐릭터 카드 1개를 표시하고, 선택하면 게임 서버 입장을 요청한다. |
| FR-004 | 맵 입장 | 캐릭터, 맵 타일, 주변 NPC·몬스터·지면 아이템을 표시한다. |
| FR-005 | 이동 | 화면 왼쪽 4방향 패드로 한 타일씩 이동한다. 서버가 거부하면 서버 위치로 화면을 보정한다. |
| FR-006 | NPC 대화 | 가까운 NPC를 탭해 대화창을 열고, 선택지 1개를 누른 뒤 대화창을 닫는다. |
| FR-007 | 기본 전투 | 가까운 테스트 몬스터를 대상으로 기본 공격해 HP를 감소시키고 사망 상태까지 처리한다. |
| FR-008 | 아이템 획득 | 몬스터가 떨어뜨린 테스트 아이템을 탭해 줍고, 획득 알림과 최소 인벤토리에서 확인한다. |
| FR-009 | 오류 표시 | 로그인 실패, 서버 연결 종료, 맵 입장 실패를 사용자 문구로 표시하고 로그인 화면으로 돌아갈 수 있게 한다. |
| FR-010 | 테스트 콘텐츠 | 시작 맵 또는 별도 테스트 맵에 NPC 1명, 몬스터 1종, 확정 드롭 아이템 1종을 배치한다. |

FR-010은 선택 기능이 아니다. 현재 번들 데이터에는 시작 맵과 연결되는 NPC·몬스터·유효한 드롭 조합이 없어 FR-006~008을 검증하려면 최소 시험 데이터가 필요하다.

확정 드롭 조건(**제품 가정**):

- 테스트 몬스터 템플릿의 드롭 목록에는 테스트 아이템 1종만 두고 확률을 100%로 지정한다. 다른 드롭 항목과 확률 드롭은 두지 않는다.
- 테스트 아이템 이름은 아이템 템플릿에 실제로 존재하는 이름이어야 한다(현재 spider 드롭 이름 불일치 사례 참고).
- 드롭된 아이템은 획득 검증이 끝날 때까지 지면에 남아야 한다. 서버의 지면 아이템 소멸 시간 설정값을 확인해 60초 이상으로 맞춘다(**결정 필요**: 설정 키와 기본값은 구현 전 확인).
- 인벤토리는 각 실행 시작 시 비어 있어야 한다(8절 반복 실행 초기화).

### 확인된 데이터 공백

- `database/server/templates/mundanes/`와 `database/server/interactive/Menus/`가 현재 번들에 없어 NPC 대화용 실제 콘텐츠가 확인되지 않는다.
- 현재 몬스터 템플릿은 `AreaID=3029`를 사용하지만 번들 area/map 목록에는 3029가 없다.
- spider의 드롭 이름은 현재 아이템 템플릿과 일치하지 않는다.
- 로컬 복사본 `sources/Dark-Ages-Private-Server-master`와 내부 중첩 복사본도 같은 데이터 공백을 가지며 YAML 메뉴 파일이 없다. 이 복사본은 부족한 콘텐츠를 보완하지 않는다(2026-09-09 확인).
- NPC 메뉴 경로가 서버 코드 안에서 두 곳으로 갈린다. 실제 NPC 클릭 흐름은 `interactive/Menus`를 읽고, 별도 `ObjectManager`는 `Scripts/Menus`를 읽는다. 이 PRD는 클릭 흐름 기준(`interactive/Menus`)을 따르되, 어느 경로가 런타임에서 유효한지는 **미확정**이며 9절 실행 확인 항목으로 남긴다.

따라서 서버 코드 재작성은 범위에 넣지 않지만, 테스트용 데이터 fixture는 반드시 준비해야 한다. 원본 submodule을 직접 수정하지 않고 프로젝트 Git 규칙에 따라 fork 또는 별도 시험 데이터 계층에서 관리한다.

## 5. 모바일 조작 방식

### 공통 배치

- 왼쪽 아래: 고정형 4방향 패드. 대각선 이동은 없다.
- 오른쪽 아래: `공격` 버튼 1개.
- 게임 화면: NPC, 몬스터, 지면 아이템을 직접 탭할 수 있다.
- 오른쪽 위: 최소 인벤토리 버튼과 연결 상태 표시.
- 중앙 하단: 획득·오류 같은 짧은 상태 메시지.

### 조작 규칙

| 행동 | 입력 | 시스템 반응 |
|---|---|---|
| 이동 | 방향을 1회 탭 | 해당 방향으로 한 타일 이동 요청, 400ms 이내 시각 피드백 |
| 연속 이동 | 방향을 누르고 유지 | 서버 이동 제한을 넘지 않는 간격으로 같은 방향 이동 요청 |
| NPC 대화 | 인접 NPC 탭 | NPC 강조 후 대화창 표시 |
| 대상 선택 | 몬스터 탭 | 선택 테두리 또는 표식 표시 |
| 기본 공격 | 공격 버튼 탭 | 캐릭터가 바라보는 인접 대상에게 `Assail` 요청 |
| 아이템 획득 | 지면 아이템 탭 | 획득 요청 후 성공 시 지면에서 제거하고 알림 표시 |
| 대화 진행 | 대화 선택지 탭 | 다음 문장 표시 또는 대화 종료 |

모든 필수 버튼은 48×48dp 이상의 터치 영역을 사용한다. 화면 가장자리와 기기 안전 영역에 버튼이 잘리지 않아야 한다. 스와이프나 멀티터치만으로 가능한 필수 행동은 두지 않는다.

## 6. 서버와 DB 재사용 범위

### 그대로 재사용

- Hades 로그인 서버와 게임 서버의 프로세스 구조
- `Aisling`, `Map`, `Mundane`, `Monster`, `Item`, `Skill` 도메인 모델
- 로그인→게임 서버 리다이렉트와 캐릭터 로드 흐름
- 서버 권위 이동 판정, 충돌, 공격 지연, 피해, 사망, 드롭, 아이템 획득 처리
- JSON 캐릭터 저장소, area JSON, `.map`, 템플릿 JSON, C# 스크립트 구조

### 최소 변경 후보

- 모바일 클라이언트와 Hades 사이의 프로토콜 어댑터 또는 게이트웨이
- 테스트 전용 계정·맵 배치·NPC·몬스터·아이템 fixture
- 클라이언트 버전 식별값과 테스트 서버 주소 설정
- 로그인·맵 입장·전투·획득 실패를 진단할 최소 서버 로그

### 재사용하지 않는 것

- Hades의 미완성 `src/Hades.Client`
- 원본 Windows UI·입력·렌더링
- Medenia 서버, SQLite, 인증 모델과 게임 콘텐츠
- 현행 평문 비밀번호 방식을 인터넷에 노출하는 운영 인증

첫 테스트가 로컬 PC 또는 격리된 사설망에서 실행되는 동안에는 테스트 전용 비밀번호만 사용한다. 인터넷을 통한 원격 테스트가 필요하면 TLS 게이트웨이와 안전한 비밀번호 저장이 P0 선행 조건이다.

## 7. 성능 및 네트워크 요구사항

아래 수치는 첫 테스트용 잠정 기준이다. 기준 Android 기기와 iPhone, 네트워크 방식을 정한 뒤 확정한다.

| ID | 요구사항 | 측정 방법 |
|---|---|---|
| NFR-001 | 필수 리소스가 설치된 상태에서 앱 실행 후 5초 이내 로그인 입력이 가능하다. | 기준 기기에서 완전 종료 후 10회 측정, 최댓값 확인 |
| NFR-002 | 로그인 제출 후 성공·실패 결과가 3초 이내 표시된다. | 서버와 같은 LAN, 왕복 지연 100ms 이하에서 10회 측정 |
| NFR-003 | 캐릭터 선택 후 5초 이내 맵과 조작 UI가 표시된다. | 테스트 맵으로 10회 입장 |
| NFR-004 | 이동·공격·NPC 선택·아이템 획득 입력은 100ms 이내 눌림 피드백을 표시하고, 정상 LAN에서 400ms 이내 서버 결과를 반영한다. | 입력 타임스탬프와 수신 패킷 로그 비교 |
| NFR-005 | 맵 입장 후 5분 플레이에서 평균 30fps 이상이며 500ms 이상 화면 정지가 없다. | 기준 실기기 프레임 측정. Android 게임은 일반적으로 30fps 또는 60fps를 목표로 한다는 [공식 안내](https://developer.android.com/games/optimize/power)를 최소 기준으로 사용 |
| NFR-006 | 전체 E2E 흐름 10회 동안 처리되지 않은 예외, 앱 크래시, 서버 크래시가 0건이다. | 앱·서버 로그와 실행 결과표 확인 |
| NFR-007 | 소켓이 명시적으로 종료되면 3초 이내 연결 종료를 표시하고 로그인 화면으로 돌아갈 수 있다. | 맵 입장 후 서버 프로세스를 정상 종료해 확인 |
| NFR-008 | 게임 중 사용자명, 비밀번호, 전체 패킷 원문을 일반 로그에 남기지 않는다. | 앱·서버 로그 문자열 검사 |

네트워크 전제:

- 첫 테스트는 온라인 전용이며 오프라인 플레이를 지원하지 않는다.
- 최초 자산 다운로드 시스템은 만들지 않고 필수 자산을 테스트 앱에 포함한다.
- 무선 환경 품질 기준은 왕복 지연 100ms 이하, 패킷 손실 1% 이하로 둔다.
- 자동 재접속과 세션 복원은 제외한다. 연결이 끊기면 상태를 알리고 로그인부터 다시 시작한다.

| AC-012 연결 종료 | 캐릭터가 맵에 입장한 상태 | 서버 연결이 명시적으로 종료 | 3초 이내 연결 종료를 표시하고 로그인 화면으로 이동 가능 |
| AC-013 맵 입장 실패 | 테스트 맵 파일이 없거나 캐릭터의 AreaID가 번들 area 목록에 없음 | 게임 입장을 요청 | 5초 이내 맵 입장 실패 문구를 표시하고 로그인 화면으로 돌아갈 수 있으며 앱·서버가 종료되지 않음 |
| AC-014 화면비 | 16:9 기기와 20:9 기기(또는 에뮬레이터) | 로그인·맵·대화·인벤토리 화면을 각각 표시 | 모든 P0 버튼과 문구가 잘리지 않고 48×48dp 규칙을 유지하며, 21:9 이상은 레터박스로 표시됨 |

반복 실행 초기화 규칙(SC-001·SC-002의 10회 연속 실행에 적용):

- 각 실행 전에 테스트 계정의 JSON을 fixture 원본으로 되돌린다(위치는 시작 지점, 인벤토리 비움, HP 최대).
- 테스트 몬스터가 리스폰되어 있고 지면에 남은 아이템이 없는지 확인한 뒤 시작한다.
- 초기화가 실패했거나 확인하지 못한 실행은 횟수에 넣지 않고 무효로 기록한다.
- 초기화는 서버를 멈춘 상태에서 파일을 교체하는 방식으로 하며, 서버의 자동 저장이 교체한 파일을 덮어쓰지 않도록 저장 주기를 지나 확인한다.

### 코드 실행으로 확인할 사항

- **완료(Windows/Android)**: Godot 4.6 .NET 빈 프로젝트가 Windows에서 빌드·실행되고 Android APK로 export·서명된 뒤 Android 15 x86_64 에뮬레이터에서 C# 실행과 화면 렌더링까지 통과했다. 증거 프로젝트는 `experiments/godot-csharp-mobile-smoke/`다.
- **Mac 후속 gate**: 같은 커밋의 macOS 빌드·실행과 iOS Xcode export·서명·arm64 iPhone 실기기 설치를 확인한다. Windows 전용 의존성이 없는 것과 iOS preset 포함은 확인했지만, Windows에서는 Apple 도구 체인을 실행할 수 없다. 공식 문서상 C# Android·iOS 지원은 experimental이다: [C# 플랫폼 지원](https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/index.html), [Android 내보내기](https://docs.godotengine.org/en/4.6/tutorials/export/exporting_for_android.html), [iOS 내보내기](https://docs.godotengine.org/en/4.6/tutorials/export/exporting_for_ios.html).
- Hades 서버가 현재 환경에서 빌드되고 로그인→맵 입장까지 실제 완주되는가.
- SHA-256 `1E34B83A81E5F844AA62DE496A689706590334E3F3D01D8E1330B1907CBADAF7`인 로컬 7.18 실행 파일이 Hades 서버에 접속 가능한가.
- `ClientVersion=718` 기준 패킷 정의가 신규 클라이언트 구현에 충분한가.
- 테스트 NPC 메뉴 파일과 monster/item fixture가 런타임 스크립트 컴파일 및 로딩에 성공하는가.
- 몬스터 사망 후 확정 드롭과 `Format07Handler` 획득 결과가 캐릭터 JSON에 저장되는가.
- NPC 메뉴가 런타임에서 `interactive/Menus`와 `Scripts/Menus` 중 어느 경로에서 실제로 읽히는가(4절 미확정).
- 서버 자동 저장 주기와 지면 아이템 소멸 시간의 설정 키·기본값이 무엇인가(AC-011, 확정 드롭 조건).
- 모바일 앱의 백그라운드 전환 시 Hades 세션이 어떤 상태로 남는가.

## 10. 후속 제안 — 첫 테스트 범위 밖

아래 항목은 첫 테스트가 AC-001~012를 모두 통과한 뒤에만 별도 PRD로 검토한다.

- 안전한 계정 시스템과 복수 캐릭터
- 자동 재접속과 세션 복원
- 스킬·마법·장비·상점·퀘스트
- 채팅·파티·길드 등 소셜 기능
- 태블릿·게임패드 지원
- 자산 패치와 CDN, 운영 DB, 모니터링
- 원격 배포를 위한 TLS, 비밀번호 해시, rate limiting
