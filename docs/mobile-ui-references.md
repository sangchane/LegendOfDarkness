# 모바일 UI 레퍼런스 조사

- 문서 버전: 0.1
- 기준일: 2026-09-10
- 목적: greybox 다음 단계에서 "어떤 스타일로 보일지"를 정하기 위한 근거 수집. 배치 규칙은 `mobile-test-v1-wireframes.md`가 이미 정했고, 이 문서는 **표현**을 다룬다.

## 1. dia2.hardt.in — 실제로 무엇으로 만들어졌나

사용자가 제시한 참고 링크. 확인 결과 어둠의 전설과 무관한 **"Diablo II · Sanctuary Survivors"**(디아블로2 풍 서바이벌 로그라이크)이며, 중요한 것은 구현 방식이다.

| 항목 | 확인 결과 | 확인 방법 |
|---|---|---|
| 게임 엔진 | **없음.** Phaser·PixiJS·Three.js·WebGL 어느 것도 번들에 없다 | 2.8MB 번들 문자열 검색 |
| 2D 캔버스 | **쓰지 않는다.** `getContext("2d")` 0회 | 같은 검색 |
| 실제 구성 | **React + Vite.** `<div id="root">`, 콘텐츠 해시가 붙은 ES 모듈 번들 | HTML 소스 |
| 화면 표현 | **전부 DOM + CSS.** 99KB CSS에 `linear-gradient` 52, `box-shadow` 42, `text-shadow` 18, `grid-template` 61 | CSS 소스 |
| 디자인 토큰 | `--gold:#b99c69`, `--muted:#85857a`, `--line:#b7a48033`, `--serif:"Cinzel", Georgia, serif` | CSS 변수 |
| 서체 | Cinzel(디스플레이 세리프) + Noto Sans KR | Google Fonts 링크 |
| 반응형 | `--raster-size`를 480/430/360px 구간마다 축소하고, **360px 이하에서는 액션바의 인벤토리 슬롯을 감춘다** | CSS 미디어쿼리 |

**결론:** 그 퀄리티는 엔진이 만든 것이 아니라 **토큰 몇 개와 CSS가 만든 것**이다. 그리고 그 게임은 월드를 그리지 않는다 — 액션바·인벤토리·스킬트리 같은 **패널 UI가 게임의 본체**인 로그라이크다.

**우리에게 적용되는 것과 아닌 것**

- 적용된다: 고급스러움의 출처가 색 3~4개와 서체 2개라는 점. 좁은 화면에서 요소를 **줄이지 않고 감추는** 전략. 디스플레이 서체가 분위기의 절반을 차지한다는 점.
- 적용되지 않는다: 우리는 타일 맵과 스프라이트가 실제로 움직이는 월드가 있다. 그래서 웹 DOM만으로는 안 되고 엔진(Godot)이 필요하다. dia2를 "이렇게 만들면 된다"의 예로 삼으면 안 되고, **"UI 표현은 이 정도까지 갈 수 있다"의 예**로 삼아야 한다.

## 2. 같은 문제를 먼저 푼 게임들

### 2.1 바람의나라: 연 (넥슨, 2020)

우리와 가장 가까운 사례다. 1996년 한국 2D 타일 MMORPG를 모바일로 옮겼다.

- 맵·몬스터·NPC 텍스트를 **원작과 동일하게** 가져왔다. 즉 **월드는 보존하고 UI만 새로 만들었다.**
- PC 원작의 조작감을 모바일에서 살리기 위해 **조작 버튼 시인성**을 우선했다.
- "옛 버전과 신 버전의 장점만 수용"이라는 평가 — 원작 그대로도, 요즘 게임 그대로도 아니다.

### 2.2 Old School RuneScape 모바일 (Jagex, 2018~)

데스크톱 MMO를 모바일로 옮긴 사례. **구체적인 UI 결정이 문서로 남아 있어 가장 실용적이다.**

| 결정 | 이유 | 우리에게 |
|---|---|---|
| **채팅창을 위로 옮김** | 모바일 키보드가 **아래에서** 올라오기 때문 | 우리도 로그인 폼에서 같은 문제를 겪었다. 입력이 있는 화면은 전부 위쪽 배치가 기본이어야 한다 |
| 사이드 패널을 **둘로 쪼개 좌우로** 배치 | 폰을 잡는 방식과 엄지 위치 | 우리 와이어프레임의 좌우 엄지 구역과 같은 결론 |
| 패널을 **감출 수 있게** | 보이는 월드를 최대화 | **우리 미해결 문제(이동 패드가 화면 42% 점유)의 유력한 답** |
| 보이는 것보다 **넓은 히트 영역** | 터치는 부정확하다 | 48dp는 최소치일 뿐, 히트 영역은 그보다 커도 된다 |
| **가까운 슬롯으로 흡착(snap)** | 같은 이유 | 인벤토리·아이템 조작에 적용 |

## 3. 두 갈래 전략

| | 원작 보존형 | 재구성형 |
|---|---|---|
| 예 | OSRS 모바일 | 바람의나라: 연 |
| 방식 | 원작 UI를 최대한 유지하고 터치만 보정 | 월드는 보존, UI는 처음부터 모바일용으로 |
| 장점 | 원작 이용자가 바로 적응 | 신규 이용자 진입이 쉽고 화면이 넓다 |
| 단점 | 좁은 화면에서 조작이 빡빡함 | 원작 감성이 옅어짐 |

우리 와이어프레임은 이미 **재구성형**을 택했다(고정 4방향 패드, 좌우 엄지 구역, 읽기 전용 인벤토리). 남은 것은 **표현을 어느 쪽에서 가져올지**이며, 그것이 다음 결정 사항이다.

## 4. 시안

`docs/ui/hud-mockup.html` — 브라우저로 열면 된다. **원작 클라이언트가 실제로 그린 화면 위에 HUD만 얹었고, 새로 그린 그림은 없다.**

- 재질·색은 원작 화면에서: 푸른기 도는 석재(`#0c0e14`~`#1e2331`), 깎인 돌 모서리(`#4a5468`), 금빛 강조(`#c9a227`), 체력 적색(`#b3323c`).
- 배치·조작은 현행 관례: 월드 full-bleed, 좌하 방향 패드, 우하 주 행동(원형, 재사용 대기 표시), 상단 좌우 분리, 대상 정보는 선택 시에만 상단 중앙, HUD 흐리게.
- 상태를 주소로 열 수 있다: `?zones=1`, `?target=1`, `?dim=1`.

### 4.1 시안이 드러낸 것

| 발견 | 내용 | 대응 |
|---|---|---|
| **원작 캐릭터는 폭 28px** | 그대로는 48dp 터치 최소 크기에 한참 못 미친다 | 보이는 그림보다 넓은 반응 영역을 따로 둔다(OSRS와 같은 해법). 시안의 「터치 영역 보기」가 그 차이를 보여준다 |
| **인접 캐릭터의 반응 영역이 겹친다** | 두 캐릭터가 한 칸 옆에 서면 영역이 포개져 어느 쪽을 눌렀는지 모호하다 | 겹칠 때는 탭 지점에서 가장 가까운 대상으로 흡착(snap)한다. 미해결 |
| **이동 패드가 방을 가린다** | 실제 맵 위에 얹으니 좌하단이 상당히 덮인다 | 「HUD 흐리게」로 확인 가능. 반투명·자동 흐림·접기 중 택일을 실기기에서 결정 |

### 4.2 자산 실태 (조사 중 확인)

- `LOD_/extracted_images/maps` — **쓸 수 있다.** 복원된 전체 맵 10장(2727×1510 등).
- `LOD_/picture/page_inGame.png` — **쓸 수 있다.** 원작 클라이언트 캡처. 시안의 기본 배경.
- `LOD_/extracted_images/standing_chars`, `characters/*` — **캐릭터가 아니다.** 실제로 열어 보면 탁자·항아리·벽걸이·문·책장 같은 맵 오브젝트다. 폴더 이름과 내용이 다르다. 캐릭터 스프라이트는 아직 확보되지 않았으며 `.dat`에서 다시 추출해야 한다.
