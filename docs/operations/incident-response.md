# 장애 대응

## 현재 구현 상태

정식 당번 체계, 자동 호출, 공용 상태 페이지, 장애 훈련 기록은 **미구현**이다. 이 문서는 공개 테스트 전에 사람과 도구를 연결하기 위한 기준이다.

## 심각도

| 등급 | 판단 예시 | 최초 행동 |
|---|---|---|
| SEV-1 | 전체 로그인/월드 진입 불가, 광범위 데이터 손상·계정 침해 | 즉시 Incident Commander 지정, 변경 동결, 서비스 보호 우선 |
| SEV-2 | 핵심 기능의 다수 사용자 장애, 우회가 어려운 성능 저하 | 담당 호출, 영향 범위 확인, 완화책 실행 |
| SEV-3 | 제한된 사용자·기능 장애, 안전한 우회 가능 | 업무 시간 내 담당 배정과 추적 |
| SEV-4 | 사용자 영향 없는 경고·문서·운영 개선 | 백로그로 관리 |

등급은 원인이 아니라 **사용자 영향, 데이터·보안 위험, 지속 시간**으로 정한다. 불확실하면 한 단계 높게 시작하고 근거가 생기면 낮춘다.

## 역할

- **Incident Commander(IC):** 우선순위, 역할, 중지·복구 결정을 총괄한다.
- **Operations Lead:** 진단과 완화 작업을 수행하고 모든 변경을 시간순으로 알린다.
- **Communications Lead:** 사용자·팀 상태 공지를 일관되게 관리한다.
- **Scribe:** 증상, 가설, 명령/변경, 결과, 결정을 타임라인에 기록한다.

1인 운영에서는 한 사람이 여러 역할을 맡을 수 있지만, `지금 IC로 판단`, `지금 작업자로 변경`처럼 역할 전환을 기록해 성급한 조작을 줄인다.

## 대응 흐름

1. **탐지:** 경보나 신고를 접수하고 시간·증상·영향 사용자 여정을 기록한다.
2. **분류:** 심각도와 IC를 정하고 장애 채널·타임라인을 연다.
3. **안전 확보:** 비밀 유출, 데이터 손상, 비용 폭증 가능성이 있으면 접근·배포·트래픽을 제한한다.
4. **진단:** 최근 변경, 로그인, 월드 진입, 저장, 네트워크, 의존성 순으로 범위를 좁힌다.
5. **완화:** 가장 빠르고 되돌릴 수 있는 방법으로 사용자 영향을 줄인다. 원인 규명은 병행하되 완화를 지연시키지 않는다.
6. **복구:** 서비스와 데이터가 기대 상태인지 핵심 여정과 무결성 검사로 확인한다.
7. **종료:** 관찰 기간과 재발 경보를 정한 뒤 IC가 종료를 선언한다.
8. **사후 검토:** 개인 비난 없이 시스템 조건, 감지 지연, 대응 판단, 재발 방지 작업을 남긴다.

### 보안 사고 분기

계정 탈취, 비밀 노출, 권한 우회, 의심스러운 데이터 반출 가능성이 있으면 일반 장애 완화와 함께 다음을 수행한다.

1. 영향받은 계정과 세션·토큰 폐기 범위를 정하고 재인증을 강제한다.
2. 노출 비밀 회전 순서를 정해 공격자의 접근을 먼저 차단한다.
3. 원본 로그와 시스템 시각을 보호하고 증거 보존 담당자·접근자를 기록한다.
4. 개인정보·결제·스토어 정책에 따른 침해 통지 판단을 책임자와 법률 자문에 에스컬레이션한다.
5. 정상 버전으로 롤백해도 탈취 자격 증명과 지속 접근이 남지 않았는지 별도로 확인한다.

증거 확보를 위해 공격자의 접근을 방치하지 않는다. 서비스 보호가 먼저이며, 보존 방식은 접근을 차단한 뒤 검증 가능한 사본과 시간 기록으로 남긴다. 자격 증명 관리 원칙은 [보안 유지보수](security-maintenance.md)를 따른다.

## 첫 15분 체크리스트

- 사용자 관점에서 무엇이 언제부터 실패했는가?
- 보안 사고나 데이터 손상 가능성이 있는가?
- 영향받는 버전, 서버, 계정 범위는 어디까지인가?
- 직전 배포·설정·데이터 변경과 상관관계가 있는가?
- 안전한 롤백 또는 기능 차단이 가능한가?
- 다음 상태 공유 시각과 책임자는 누구인가?

로그를 붙일 때 비밀번호, 토큰, 쿠키, 개인 식별자와 기타 비밀은 제거한다. 원본 증거는 접근 제한 저장소에 보존하고 일반 채팅이나 공개 이슈에 복사하지 않는다.

## 상태 공지 템플릿

```text
[시각] [SEV 등급] 어떤 사용자 여정이 영향을 받는지
현재 영향:
현재 조치:
다음 업데이트 예정:
사용자가 할 일: (없으면 없음)
```

원인이나 복구 시각을 추측하지 않는다. 확인된 사실과 다음 업데이트 약속만 쓴다.

## 사후 검토 완료 조건

- 탐지→완화→복구 타임라인과 영향 범위가 있다.
- 직접 원인과 잠재 조건을 구분했다.
- 잘 작동한 방어와 실패한 방어를 모두 기록했다.
- 재발 방지 작업마다 책임 역할, 우선순위, 완료 조건이 있다.
- 같은 유형을 더 빨리 탐지하는 테스트 또는 경보가 추가된다.

운영 조작은 [실행 절차](../run-procedure.md), 배포 복구 판단은 [릴리스·롤백](release-rollback.md)을 함께 따른다.
