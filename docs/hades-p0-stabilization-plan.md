# Hades P0 안정화 계획 및 회귀 테스트 경계

- 문서 버전: 1.1
- 상태: 확정 (1.1 — S0 착수에서 확인한 객체 서버 포트 제약과 S0 harness 위치를 반영)
- 기준일: 2026-09-09
- 적용 대상: Hades/Lorule 7.18 C# 서버
- 목적: 모바일 첫 테스트 버전을 실제 Hades 서버에 연결하기 전에 필요한 최소 안정화 범위와 통과 기준을 고정한다.

## 1. 결론

Hades는 현행 게임 규칙과 콘텐츠 동작을 확인하는 기준선으로 유지한다. 전면 리팩터링, DB 교체, 일괄 성능 최적화는 먼저 하지 않는다. 대신 서버 전체 중단, 인증 우회, 경로 이탈, 패킷 유실, 캐릭터 저장 손상, 기본 전투 오류로 이어질 수 있는 경계만 P0로 안정화한다.

진행 순서는 다음과 같이 확정한다.

1. **S0 — 현행 동작 고정:** 원본 7.18 동작을 변경하지 않고 특성화 테스트와 golden fixture를 만든다.
2. **S1 — 모바일 연동 안전선:** 네트워크, 입장 인증, 연결 정리, 저장, 기본 전투의 치명적 오류를 테스트 우선으로 수정한다.
3. **S2 — 5~10인 비공개 테스트 안전선:** 비밀번호 저장, 로그인 남용 방지, 정상 종료 저장, 지원 런타임, 10인 부하·복구를 검증한다.

Godot 화면은 fixture를 사용하는 격리 작업이라면 S0 이후 진행할 수 있다. 실제 Hades 연동은 S1 통과 후, 지인 5~10명이 접속하는 비공개 테스트는 S2 통과 후에만 진행한다.

### 2.2 판단 또는 아직 확인이 필요한 내용

- 위 결함이 실제 운영 중 모두 재현됐다는 뜻은 아니다. 코드상 실패 가능성이 확인되어 P0 방어 대상으로 분류했다.
- 다만 예외 격리 결함은 2026-09-09 S0 harness 실행에서 실제로 재현됐다. 2620이 선점된 상태에서 서버는 예외를 삼키고 로그인 서버 없이 계속 떠 있었다.
- 원본 클라이언트가 기대하는 정상 패킷 바이트와 서버 상태 변화는 S0의 실제 캡처로 확정해야 한다.
- Hades 서버의 현재 처리량 병목은 아직 측정하지 않았다. 따라서 CPU 최적화와 게임 루프 재설계는 P0에 포함하지 않는다.
- 5~10명 규모에서는 JSON 저장을 유지할 수 있다고 판단한다. 단, 원자적 저장과 복구 시험을 통과해야 한다.

### 2.3 하드코딩된 상수 목록 (S1 정리 대상)

배포 환경에 따라 달라지는 값이 코드나 데이터에 박혀 있으면 격리 실행과 병렬 테스트가 막히고, 나중에 서버를 옮길 때도 그대로 걸린다. S1 fork 작업에서 아래를 설정 키로 빼고 환경변수로 덮어쓸 수 있게 한다. 검토 중 새로 찾은 값은 이 표에 추가한다.

| 값 | 위치 | 지금 영향 | S1 목표 |
|---|---|---|---|
| `http://localhost:2620/` | `Hades.Server.Base/Network/Game/GameServer.cs`의 `Start` | 설정 키가 없어 이 PC에서 서버가 한 대만 뜬다. 격리 harness의 병렬 실행이 불가능하고, 선점 시 로그인 서버 없이 조용히 뜬다 | `ServerConfig`에 객체 서버 포트 키를 두고 환경변수 override 허용 |
| `MServerTable.xml`의 `Port` = 2610 | 빌드 산출물 데이터 | 로비 리다이렉트가 격리 밖 포트로 클라이언트를 보낸다. 현재는 harness가 실행마다 이 파일을 다시 써서 우회 중 | 실행 시 `LOGIN_PORT`에서 파생하거나 설정으로 주입 |

**규칙:** 주소·포트·경로처럼 환경마다 달라지는 값은 설정 파일 키를 정본으로 두고, 환경변수로 덮어쓸 수 있게 한다. 코드 안의 리터럴은 기본값 자리로만 남긴다.

## 3. 범위

### 3.1 P0에 포함

- 패킷 프레임, 길이, 명령, 문자열 경계 검증
- 오류 처리기가 다시 예외를 만들지 않는 서버 수준 예외 격리
- 캐릭터명 정규화와 `aislings` 저장 경로 이탈 방지
- 만료되는 일회용 게임 입장 티켓과 검증 후 입장 순서
- 연결 컬렉션 동기화, 인증 전·후 연결 정리, handshake 시간 제한과 연결 수 상한
- 사용자별 순서 보장·용량 제한 송신 큐와 완전 전송 처리
- 캐릭터별 직렬화, 임시 파일 쓰기, 원자적 교체, 백업 및 복구
- 기본 공격 간격 계산과 잘못된 cast 항목의 무한 반복 수정
- 하드코딩된 주소·포트 상수의 설정 키 분리와 환경변수 override (2.3의 목록)
- 실패 원인을 비밀정보 없이 식별할 최소 구조화 로그와 계수기
- 지원 중인 .NET LTS로의 단계적 이전과 의존성·빌드 검증(S2)

### 3.2 P0에서 제외

- 전체 구조 재작성, 큰 파일의 일괄 분할, 전역 상태의 전면 제거
- JSON을 SQL DB로 교체하거나 다중 서버 구조를 도입하는 작업
- 측정 결과가 없는 게임 루프, 암호화, 가시성 계산 최적화
- Godot 화면의 색상·아트·최종 UX와 WebView 전환
- 신규 NPC·맵·퀘스트·직업·스킬 콘텐츠와 게임 밸런스
- App Store 또는 공개 인터넷 서비스를 위한 TLS 게이트웨이와 배포 자동화

## 4. 단계별 실행 계획

### S0 — 특성화 기준선

목표는 취약한 동작을 보존하는 것이 아니라, 정상 7.18 흐름과 저장 결과를 변경 전에 기록하는 것이다.

| ID | 작업 | 산출물 | 완료 조건 |
|---|---|---|---|
| P0-00 | 원본 서버를 수정하지 않는 격리 harness 구성 | 테스트 전용 프로세스·포트·임시 데이터 경로 | 실행 중인 수동 서버 및 실제 데이터와 분리됨 |
| P0-01 | 7.18 로그인→redirect→게임 입장 정상 흐름 캡처 | 비밀정보가 제거된 golden packet/state fixture | 합성 계정으로 같은 입력이 같은 명령 순서와 핵심 상태를 재현함 |
| P0-02 | 저장 전후 정상 상태 고정 | 최소 캐릭터 JSON fixture와 의미 비교기 | 시간·임의값을 제외한 필드 변화가 설명되고 반복 가능함 |

**진행 상황 (2026-09-09):** P0-00 완료 — `tests/hades-characterization/`(net8.0, xunit)의 `IsolatedHadesServer`가 빌드 산출물과 `database/server`를 임시 경로로 복사하고, 비어 있는 `aislings`와 사용 중이 아닌 포트를 배정한 뒤 서버를 띄우고 종료 시 지운다. 격리를 일부러 깨면 원본 무변경 테스트가 실제로 실패하는 것까지 확인했다. 하드코딩된 2620 때문에 harness는 한 번에 한 대만 띄울 수 있어, 다른 Hades가 떠 있으면 `Start`가 즉시 실패하고 스위트도 직렬로 실행한다(전체 11개, 약 1분).

P0-01 완료 — 합성 계정으로 로그인부터 월드 입장까지 완주하고, 16단계 명령 순서를 `Fixtures/hades-718-login-flow.json`에 고정했다. 성공 판정은 서버 로그의 `<이름> : Welcome to Lorule`이다. seed·salt·해시·serial처럼 실행마다 달라지는 값은 고정하지 않았고 실제 계정·비밀번호는 쓰지 않는다. 암호화는 재작성 대신 서버의 `SecurityProvider`를 참조해 정본으로 쓴다. 기록 과정에서 예상과 달랐던 동작 하나를 확인했다 — 리다이렉트 후 새 연결마다 handshake 배너(0x7E)가 다시 온다.

P0-02 완료 — 갓 생성된 캐릭터의 최소 상태를 `Fixtures/hades-718-character.json`에 고정하고, 두 번의 독립 실행을 비교하는 의미 비교기를 붙였다. 실행 간 달라지는 필드는 `Created`, `LastLogged`, `SkillBook` 셋뿐이며 각각 이유를 fixture에 적었다(`SkillBook`은 `GiveAssailOnCreate`로 부여되는 스킬의 `ID`가 난수 시리얼이고 나머지 필드는 동일하다). 비교기가 실제로 드리프트를 잡는지도 값을 일부러 바꿔 확인했다.

**S0 gate: 통과 (2026-09-09).** 테스트 14개가 원본 기준선에서 재현되며, fixture·로그·테스트 결과에 실제 계정과 비밀번호가 없다(합성 계정 `lodharness`만 사용). 전제: 서버가 미리 빌드돼 있어야 하고(`Staging/net5.0`), 2620 제약 때문에 스위트는 직렬로 약 30초 걸린다.

**S0 gate 원문:** 격리 테스트가 원본 기준선에서 재현되며 fixture, 로그, 테스트 결과에 실제 계정이나 비밀번호가 없다.

P0-14 완료 — **송신이 서로 다른 세 갈래였고 각자 다르게 패킷을 잃었다.** `FlushAndSend`는 다른 송신이 진행 중이면 **아무 말 없이 보내지 않고 돌아왔다**. 비동기 송신을 시작하고 끝내지 않아 실제로 나간 바이트 수를 본 적이 없고, 완료 핸들에 잠금 안에서 대기해 사실상 동기 송신이었다. 나머지 두 갈래는 `Socket.Send`의 반환값을 버렸다 — 소켓은 자리가 있는 만큼만 받으므로 바쁜 연결에서는 **패킷이 반만 나가고**, 받는 쪽은 길이를 읽고 그만큼 기다리므로 스트림이 영영 어긋난다. 게다가 그 둘은 전역 잠금 아래에서, `FlushAndSend`는 바깥에서 써서 두 패킷이 섞일 수 있었다. 이제 연결마다 쓰는 스레드가 하나뿐이고, 받아주지 않은 나머지를 다 나갈 때까지 다시 내민다. 대기 한도(`SendQueueDepth`, 기본 512)를 넘기면 그 연결을 포기한다.

P0-15 완료 — **저장이 파일을 비우고 채웠다.** 그 사이에 멈추면 캐릭터가 있던 자리에 빈 파일이 남고 돌아갈 곳이 없었다. 같은 캐릭터를 동시에 저장하면 서로 덮어썼다. 이제 옆에 다 쓰고 디스크까지 내린 뒤 바꿔 넣는다 — 읽는 쪽은 옛 것 전부나 새 것 전부만 보고, 옛 것은 백업으로 남는다. 한 파일은 한 번에 하나만 저장한다. 불러올 때 현재 파일을 캐릭터로 읽을 수 없으면 백업으로 넘어간다.

P0-16 완료 — **공격 간격 검사가 반대로 쓰여 한 번도 동작하지 않았다.** 마지막 공격은 과거라 `마지막 - 지금`은 음수이고, 음수가 양수 지연보다 클 수 없다. 설정값의 500배로 때릴 수 있었다. 경계를 메서드로 빼서 지연 전후를 표로 못박았고, 시간이 미래로 찍힌 경우는 통과시키지 않고 기다린다. 함께 — **시전 처리 루프가 끝나지 않을 수 있었다**: 빈 슬롯을 가리키는 시전이 오면 스택에서 아무것도 빼지 않고 루프 처음으로 돌아가, 잘못된 시전 하나가 월드 갱신 스레드를 붙잡았다. 이제 그 시전을 버리고 지나간다. 스택은 넣을 때 쓰던 잠금을 읽을 때도 쓴다.

P0-17 완료 — **객체 서버 주소가 코드에 박혀 있어 한 PC에 서버가 한 대만 떴다.** 두 번째는 포트를 못 잡고 로그인 리스너 없이 조용히 올라왔다(예외 종류가 주변 catch에 안 걸렸다). 설정 키가 됐고 환경변수가 파일을 덮어쓴다(`ServerConfig__ObjectServerPort`). harness가 실행마다 빈 포트를 잡아 주므로 **격리 시험이 병렬로 돈다 — 약 3분에서 약 1분으로 줄었다.**

### 관측된 한계 — 한 연결이 다른 연결을 굶길 수 있다 (2026-09-12 해결)

읽지 않는 클라이언트 하나가 갱신 요청 4,000건을 몰아 보내면, **다른 클라이언트가 30초가 넘도록 답을 받지 못하는 경우가 세 번에 한 번꼴로 재현된다**(2026-09-10 측정, 3회 중 1회 실패). P0-14의 송신 큐를 넣은 뒤에도 남아 있다 — 큐는 "쓰기가 남을 막지 않는다"를 보장하지만, 요청 **처리**는 여전히 상당 부분이 `ServerContext.SyncLock` 하나 뒤에서 직렬화된다.

이것을 재는 종단 시험은 서버가 얼마나 일할지에 달려 있어(`Format38Handler`는 `IsRefreshing`이면 그냥 무시한다) 결과가 흔들렸다. **흔들리는 시험은 없는 것보다 나쁘므로 지우고 여기 적어 둔다.** 송신 큐의 상한 정책 자체는 `SendQueueTests`가 결정적으로 확인한다.

**2026-09-12 해결.** 나가는 패킷 **모두**가 `ServerContext.SyncLock` 하나를 잡고 직렬화·암호화하고 있었다 —
그래서 갱신 요청을 몰아 보내는 연결 하나가 서버의 모든 응답을 자기 뒤에 줄 세웠다. 그 잠금이 지키던 것은
전부 연결별 자원이었고(`Writer`·`Encryption` 은 생성자에서 연결마다 만든다), 같은 파일의
`Send(NetworkFormat)` 은 이미 `lock (Writer)` 를 쓰고 있었다. 두 송신 경로를 같은 연결별 잠금으로 바꿨다.
경쟁 상태도 함께 닫혔다 — `Send(byte[])` 는 `Writer` 에 쓰면서 전역 잠금을 잡아 `Send(NetworkFormat)` 과
서로 배제하지 못했다. fork `fix/run-on-macos`.

**P0-13 은 macOS 에서 다시 재어 보고서야 끝났다.** 이 절의 원래 측정은 Windows 기준이었고 거기서는 0개였다.
같은 시험을 macOS 에서 돌리니 인증 전에 떠난 연결 50개가 **전부** `CLOSE_WAIT` 으로 남았다 —
`Socket.Disconnect` 는 핸들을 놓지 않는데다 `Socket.Connected` 로 가려져 있어, 상대가 먼저 떠나는
바로 그 경우에 아무도 소켓을 닫지 않았다. 무조건 닫도록 고쳤고 격리 시험 52개가 전부 통과한다.

P0-10 완료 — `fix/hades-network-boundary`. 악성 프레임 5종(잘못된 magic, 길이 0, 잘린 본문, 과대 길이, 미등록 명령)이 **서버 프로세스를 통째로 죽이던** 결함을 고쳤다. 원인은 `ServerContext.Error`가 한 번도 할당되지 않는데 모든 소켓 콜백의 catch 블록이 그것만 호출해, 수신 경로의 예외가 IO 완료 스레드에서 `NullReferenceException`으로 번져 unhandled로 끝나는 것이었다. 오류 sink에 스스로 던지지 않는 기본 구현을 줬다. 이어서 프레임 검증도 넣었다 — 수신 경로가 아무 3바이트나 헤더로 받아들여, magic이 틀리거나 길이가 0이거나 수신 버퍼(65534)를 넘는 프레임이 **오지 않을 본문을 기다리며 연결을 영원히 붙잡고** 있었다(과대 길이는 버퍼보다 1바이트 더 읽으려는 문제도 있었다). 모든 읽기가 지나가는 한 곳에서 검증하고 socket error를 보고하게 했으며, 두 수신 콜백이 이미 그 조건에서 연결을 끊으므로 해당 연결만 사라진다.

형태만으로 판정할 수 없는 것은 손대지 않았다 — **잘린 본문은 느린 송신자와 구분되지 않아** handshake 시간 제한이 필요하고(P0-13), 미등록 명령은 구조적으로 멀쩡한 프레임이다.

P0-11 완료 — **캐릭터 이름으로 임의 파일 쓰기가 가능했다.** 이름이 네트워크에서 그대로 저장 경로에 붙어, `../escaped`는 `database/server/escaped.json`을, `../../escaped`는 `database/escaped.json`을 만들었다. 서버 프로세스가 쓸 수 있는 어느 위치든 이름 선택만으로 닿는다. load·save가 함께 지나가는 한 곳에서 경로를 해석하고, 캐릭터 폴더 **바로 아래**로 떨어지지 않는 이름은 거부한다. 이어서 **이름 정책**도 넣어 P0-11을 마쳤다. 서버는 클라이언트가 보낸 어떤 이름이든 그대로 파일로 만들었고, `a`·`two words`·`wren!`은 물론 Windows 장치명 `con`·`nul`·`com1`까지 캐릭터 파일이 됐다. 허용은 **영문·숫자·한글 완성형**이며 길이는 설정값(`CharacterNameMinLength`/`MaxLength`, 기본 2~12)으로 뺐다.

**한글은 명시적으로 지원 범위다.** 리더 `GetEncoding(0x3B5)`와 라이터 `GetEncoding(949)`는 같은 CP949이므로 프로토콜과 서버는 이미 한글 이름을 나른다. 못 치는 것은 영문 7.18 클라이언트의 입력 필드뿐이고, 모바일 클라이언트는 보낸다. 정책이 한글을 막지 못하도록 **정책보다 먼저** 한글 저장 테스트를 두었다.

P0-12 완료 — **입장 티켓 검증이 입장 뒤에 있었다.** `Format10Handler`가 `EnterGame`을 먼저 실행하고 그 다음에 검사해서, 검증되지 않은 연결이 캐릭터를 로드하고 월드에 들어간 뒤에야 끊겼다. 검사 대상도 요청이 아니라 방금 로드된 캐릭터였다. 요청의 이름으로 티켓을 먼저 소비하도록 바꿨다 — `Remove`가 "이번 호출이 가져갔는지"를 알려주고 기존 lock이 그것을 원자적으로 만든다. 계획서 5.2의 정량 기준(동일 티켓 2개 연결 중 정확히 1개 성공)을 테스트로 확인했다: 고치기 전에는 **2개 모두 입장**했다.

P0-13 완료. **소켓 정리는 이미 올바르다는 것이 측정으로 확인됐다** — 인증 전에 떠나는 연결 50회 뒤 서버가 붙잡고 있는 소켓(CLOSE_WAIT)은 0개다. 이 결과를 테스트로 고정했고, 소켓 열거가 실제로 이 서버의 연결을 본다는 대조군도 함께 넣었다.

접속자 컬렉션 동기화는 고쳤으나 **테스트로 재현하지 못했다.** `Clients`는 접근할 때마다 새 리스트를 만드는 프로퍼티라 `lock (Clients)`가 아무것도 잠그지 않았고, `AddClient`/`RemoveClient`는 소켓 콜백에서 잠금 없이 `Dictionary`를 변경했다. 150개 동시 연결이 트래픽까지 보내도 이 PC에서는 터지지 않아, **코드 검토 근거로** 수정했다. 관련 테스트는 증명이 아니라 회귀 방지다. 실제로 드러날 곳은 P0-24의 10인 soak다.

**시간 제한도 넣어 P0-13을 마쳤다.** 게임 서버에는 자체 유휴 검사가 있었지만 로그인 서버에는 없어서, 헤더 3바이트만 보내고 조용해지면 소켓을 영원히 붙잡을 수 있었다. 무조건적인 연결 수명 제한 대신 **"프레임이 진행 중인 채로 멈춘 연결"**만 1초 주기로 걷어낸다 — 프레임 사이에서 쉬는 연결은 진행 중이 아니므로 사람이 입력하는 동안 끊기지 않는다(유휴 연결이 같은 시간을 버티는지 대조군으로 확인한다). 제한 시간은 `IncompleteFrameTimeoutSeconds`(기본 15초) 설정값이며, harness가 이를 3초로 낮춰 쓰는 것으로 **설정 키가 실제 반영된다는 것도 함께 검증**된다.

**S1 gate:** 아래 5장의 필수 suite가 모두 통과하고, 변경 코드의 line/branch/method coverage가 각각 80% 이상이며 인증·경로·저장 손상 경계의 branch coverage는 100%이고 skip된 필수 테스트가 없다. 원본 7.18 클라이언트의 로그인→redirect→맵 입장이 10회 연속 성공해야 한다. 이 gate 뒤에만 Godot 클라이언트를 실제 Hades에 연결한다.

P0-20 완료 — **비밀번호가 캐릭터 파일에 친 그대로 들어가 있었다.** 그 폴더를 읽을 수 있으면 모든 비밀번호를
읽을 수 있었고, 사람들은 비밀번호를 다른 곳에도 쓰므로 피해가 이 게임에서 끝나지 않는다. 이제 PBKDF2-SHA256
에 무작위 소금, 210,000회로 저장하며, 한 문자열이 방식·횟수·소금·해시를 모두 지닌다 — 횟수가 값마다 함께
저장되므로 나중에 올려도 기존 값이 무효가 되지 않는다.

**옛 계정을 잠그지 않는 것이 이 작업의 핵심이었다.** 그 계정들은 아직 평문을 들고 있고, 그 사람들을 못 들어오게
만드는 것은 고치려던 결함보다 나쁜 실패다. 검사기가 평문도 받아들이되 "옮겨야 한다"고 알려 주고, 로그인
경로가 **평문이 손에 들어온 그 한 순간**에 해시로 바꿔 저장한다. 계정은 주인이 처음 들어올 때 옮겨지고 그 뒤로는
다시 일어나지 않는다. 평문 비교도 해시 비교도 고정 시간으로 한다.

실제로 평문으로 저장돼 있던 계정으로 확인했다 — 로그인되고, 파일이 `pbkdf2-sha256$210000$…` 로 바뀌고,
평문은 사라지고, 두 번째 로그인은 해시로 통과하며, 틀린 비밀번호는 거부된다. 격리 시험 59개 통과.

그 과정에서 `CharacterStateCharacterizationTests` 가 빨간불이 됐다 — 소금이 매번 달라 `Password` 가 실행마다
달라지기 때문이다. 그것이 바로 이 시험이 있는 이유이므로, 이유를 적어 fixture 의 변동 필드에 등록했다.

P0-22 완료 — **`Ctrl+C` 와 `kill` 이 그냥 프로세스를 없앴다.** 캐릭터는 `SaveRate`(기본 10초)마다 저장되므로
서버를 세울 때마다 접속 중이던 사람이 최대 그만큼 되돌아갔다 — 개발 중에는 자주 일어나는 일이다. 두 신호가
이제 컨텍스트에 이미 있던 `Shutdown()` 을 부르고, 그 `Shutdown()` 이 저장을 한다.

**저장은 `Abort()` 앞에 둬야 한다.** `Abort()` 는 리스너를 닫고 나서 **모두를 끊는데**, 끊으면 클라이언트
목록에서 빠지므로 뒤에 놓인 저장은 아무도 못 찾는다 — 첫 시도가 접속자가 분명히 있는데도
`saved 0 character(s)` 를 찍었다. 끊을 때도 저장하긴 하지만 마지막 저장에서 2초가 지났을 때뿐이다.
종료 저장은 조건 없이 하고 몇 명을 썼는지 남긴다.

접속자를 둔 채 확인했다 — `Shutting down — saved 1 character(s).` 가 찍히고 프로세스가 신호로 죽는 대신
0으로 끝난다. 격리 시험 59개 통과.

**갑작스러운 종료는 이미 덮여 있다**(재어 본 결과): `SaveRate` 10초 주기 저장 + `SaveComponent` 45초 일괄
저장 + 접속 종료 시 저장이 겹쳐 있고, 저장 자체는 P0-15 로 원자적이다. 전원이 뽑혀도 최대 10초 분량만
잃는다. P0-22 는 그 10초를 0으로 만드는 것이다.

P0-24 부분 — **10인 4분 soak 를 돌렸더니 셋 중 둘이 실패했다.** 로그인은 빨랐는데(중앙값 41ms) 그 다음
**자기 위치가 오지 않아 화면이 빈 채로 남았다.** 30분 기준에는 못 미치는 4분 예비 실행이지만, 그것만으로
충분했다 — 30분을 돌릴 이유가 없었다.

원인 둘은 같은 모양이었다. 월드의 **모든 아이슬링을 훑는 조건식**이, 다른 연결이 한창인 사이에 없을 수도
있는 것을 건드렸다. `GameClient.Insert` 는 `aisling.Username` 을 비교하다 터졌고 그 예외가 **월드 입장
한가운데서** 나와 캐릭터가 놓이지 않았다 — 던진 횟수 320회가 실패 320회와 정확히 같았다.
`GameClient.ObjectCheckPoint` 는 갱신 루프에서 캐릭터를 쥐지 않은 채 `Aisling.Username` 을 읽어,
로그인과 캐릭터 로드 사이의 연결이 **아이슬링 하나마다 한 번씩** 던졌다 — 4분에 167,000회이고,
그 홍수가 로그의 다른 줄을 전부 덮고 있었다.

둘 다 캐릭터를 한 번 잡아 두고, 없으면 일찍 돌아가고, null 원소를 건너뛰게 했다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 성공한 판 | 168 | **1,435** |
| 실패 | 320 (66%) | **4 (0.28%)** |
| 서버 로그 | 1,839,936줄 | **2,964줄** |
| 남은 소켓 | — | 1개 (연결 약 1,439회 중) |

**남은 것**: 그 로그의 `IndexOutOfRange` 2회와 `OutOfMemoryException` 1회, 그리고 30분 기준 실행.

**S2 gate:** 보안 음성 테스트와 10인 soak를 포함한 전체 suite가 통과한 빌드만 지인에게 배포한다.

### 5.2 정량 합격 기준

- malformed, fragmented, 최대 크기 경계 입력 1,000건 후 서버가 살아 있고 정상 클라이언트의 핵심 흐름이 완료된다.
- 동일 입장 티켓을 동시에 소비하는 2개 연결 중 정확히 1개만 성공한다.
- 연결·로그인·종료 100회 후 접속자 컬렉션과 socket에 잔여 항목이 0개다.
- 동일 계정 저장·재시작 100회 후 현재 JSON 또는 백업으로 100% 복구된다.
- 잘못된 cast 입력 처리는 50ms 안에 반환되고 다음 게임 갱신이 계속된다.
- 10인 30분 soak에서 tick 지연은 p95 16ms 미만, p99 33ms 미만이다.
- 디스크 저장 시간을 제외한 패킷 handler 지연은 p95 10ms 미만이다.
- 사용자별 송신 queue 깊이는 p99 50 미만이며 시간에 따라 계속 증가하지 않는다.
- warm-up 이후 30분간 관리 메모리 증가는 20% 이하다.
- 변경·추가한 안정화 코드의 line, branch, method coverage가 각각 80% 이상이다.
- 인증 선검증, 저장 경로 containment, 입장 티켓 단일 소비, 원자적 저장 실패·복구 경로의 branch coverage는 100%다.

성능 수치는 첫 기준값이다. 기능 정확성 시험은 수치 조정으로 우회할 수 없다. 환경 차이로 성능 기준 조정이 필요하면 측정 장비, 빌드, 원자료를 기록한 별도 결정으로 변경한다.

### 5.3 테스트가 소유하지 않는 영역

P0 서버 suite는 Godot 표시 품질, 모바일 조작성, safe area, NPC 대사의 내용 품질, 전체 전투 밸런스를 판정하지 않는다. 이 항목은 모바일 PRD와 와이어프레임의 별도 acceptance criteria가 담당한다. 반대로 모바일 E2E 통과만으로 서버의 동시성, 저장 복구, 인증 안전성을 통과 처리하지 않는다. 현재 `mobile/tests`의 synthetic login fixture도 클라이언트 codec 계약만 담당하며 Hades 서버 P0 통과 증거로 사용하지 않는다.

## 6. 구현 및 Git 경계

### 6.1 원본과 fork

- `sources/`의 원본 submodule은 읽기 전용 기준선으로 유지한다.
- S0 특성화 harness는 원본을 수정하지 않으므로 root 저장소 `tests/hades-characterization/`에 두고, fork는 서버 코드를 실제로 고치는 S1 시점에 만든다.
- 서버 변경은 `kimsangchan/Dark-Ages-Private-Server` fork를 만들거나 확인한 뒤 그 저장소에서 수행한다.
- 원본 저장소는 `upstream`, 개인 fork는 `origin`으로 구분한다.
- root 저장소에는 검증된 Hades fork의 submodule commit 포인터만 반영한다.

### 6.2 Graphite stack

서버 fork의 권장 스택은 다음과 같다.

1. `test/hades-characterization` (S0 산출물은 root 저장소에 있으므로, 이 브랜치는 S1에서 fork로 옮겨 갈 때만 만든다)
2. `fix/hades-network-boundary`
3. `fix/hades-auth-boundary`
4. `fix/hades-persistence`
5. `fix/hades-gameplay-correctness`
6. `chore/hades-runtime-lts`

각 브랜치는 한 실패 경계와 그 테스트만 소유한다. 기존 패킷 계약과 무관한 이름 변경, 포맷팅, 대규모 파일 이동은 섞지 않는다. root 저장소에서는 이 계획 문서, 모바일 프로토콜 코어, 검증된 submodule 포인터를 서로 다른 Graphite 변경으로 관리한다.

## 7. 중단 및 되돌림 기준

- S0 기준선을 재현하지 못하면 서버 코드를 수정하지 않고 fixture 또는 실행 환경 차이를 먼저 해결한다.
- 정상 7.18 흐름이 깨지는 변경은 해당 stack에서 중단하고 마지막 green parent로 되돌린 뒤 원인을 분리한다.
- 테스트가 실제 계정, 평문 비밀번호, 전체 패킷 평문을 출력하면 결과물을 배포·커밋하지 않고 fixture를 폐기해 다시 만든다.
- 원자적 저장 시험에서 현재 파일과 백업이 모두 손상되면 실제 사용자 데이터로 시험하지 않는다.
- 성능 기준을 통과하지 못하면 측정 자료로 병목을 특정한 뒤 별도 `perf` 변경을 만든다. P0 기능 변경에 추측성 최적화를 섞지 않는다.
