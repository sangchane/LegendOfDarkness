# 08. 모바일 전환 재사용성

아래는 **추정**이며, 확인된 코드 결합도를 근거로 한 전환 판단이다.

| 영역 | 재사용 판단 | 근거 |
|---|---|---|
| Hades 게임 규칙·도메인 모델 | 인터페이스 교체 후 재사용 | `Aisling`, `Map`, `Monster`, `Item`, `Skill`, `Spell`, 스크립트가 UI와 비교적 분리됨 |
| Hades 콘텐츠 JSON/MAP/스크립트 | 높은 재사용 후보 | 서버 권위 데이터로 구성되어 있으나 포맷 정규화와 라이선스 검증 필요 |
| Hades 인증·저장소 | 재작성 가능성 높음 | 평문 비밀번호, 파일 단위 JSON, 단일 프로세스 메모리 캐시 |
| 레거시 패킷 지식 | 높은 참고 가치 | Arbiter, Hades, Medenia, DAGL에 교차 구현이 있음 |
| Medenia TypeScript 서버 공용 패키지 | 높은 재사용 후보 | network/encryption/serialization/fsm이 독립 workspace 패키지 |
| Medenia Phaser 렌더러 | PWA/WebView면 부분 재사용 | 웹 기술이라 모바일 브라우저에서 동작 가능하나 성능·자산 크기 검증 필요 |
| Medenia Svelte UI/입력 | 큰 폭 재설계 | 현재 PC 화면·포인터 중심; 터치, 작은 화면, 가상 조이스틱, 접근성 필요 |
| da-lib의 파일 파서 | 높은 재사용 후보 | .NET/SkiaSharp 기반의 명확한 리소스 변환 계층 |
| DungMunkey SDL 코드 | 알고리즘/자산 참고 | 렌더 루프와 전투가 단일 플레이·하드코딩 중심이라 MMORPG 기반으로 직접 사용하기 어려움 |
| Windows 런처·봇·후킹 | 재작성/제외 | Win32 프로세스, DLL 주입, 메모리 주소, 키보드·마우스 메시지에 종속 |
| 맵·아이콘·데이터 도구 | 데스크톱 운영도구로 유지 | 모바일 앱 안에 넣기보다 콘텐츠 제작 백오피스로 가치가 큼 |

## 모바일에서 새로 만들 가능성이 높은 부분

1. 터치 입력, 가상 조이스틱, 스킬 단축바, 화면 회전·안전 영역 대응 UI
2. 모바일 렌더링 및 자산 스트리밍/압축/캐시
3. TLS 로그인, 토큰 기반 세션, 안전한 비밀번호 저장과 계정 복구
4. 연결 끊김·백그라운드 전환·재접속·상태 동기화
5. 서버 권위형 전투 검증, 치트 방지, 속도 제한
6. 운영자 웹 콘솔, 로그·지표·백업·배포 자동화
7. 앱스토어용 패치/업데이트 체계와 자산 라이선스 정리

## 권장 기준선

**추정:** 서버는 Hades의 풍부한 콘텐츠 모델을 참고하되 인증·DB·네트워크 경계를 새로 설계하고, 클라이언트는 목표가 빠른 검증이면 Medenia의 Phaser/Svelte를 PWA로 평가하는 것이 가장 짧다. 장기 네이티브 게임을 원하면 Unity/Godot 등으로 렌더링·UI·입력을 새로 만들고 프로토콜·콘텐츠 변환기만 재사용하는 편이 안전하다.
