# Quality Decomposition — 질적 표현의 측정 가능 기준 변환

기획 산출물에서 검증 기준 없는 질적 표현을 제거하고, 셀 수 있는 기준으로 변환하는 규칙.

## 형용사 금지 규칙

다음 유형의 표현은 산출물(05~07)에 그대로 남길 수 없다.
- 검증 불가 형용사: 직관적인, 간편한, 빠른, 세련된, 사용자 친화적인, 강력한, 유연한
- 참조 제품 비유: "토스처럼", "노션처럼", "애플 감성"

발견하면 반드시 아래 변환 카드를 거쳐 measure_method가 붙은 기준으로 바꾼다.
변환 전 원문은 카드의 qualitative_input에 보존한다 (사용자 의도 추적용).

## 참조 제품 분해 (Reference Decomposition)

사용자가 참조 제품을 대면 이 순서로 분해한다.

1. **원칙 조사** — 해당 제품의 공개 디자인 원칙·디자인 시스템·기술 블로그를 웹 검색으로 찾는다 (예: 토스는 디자인 컨퍼런스와 블로그로 원칙을 공개). 출처 URL과 확인일 필수.
2. **사용자 의도 확인** — 참조에서 사용자가 원하는 게 무엇인지 좁힌다. 대부분 전체가 아니라 특정 성질(단계 축소, 무설명 사용, 시각 밀도 등)이다. 불명확하면 5대 질문 중 하나로 올린다.
3. **기준 변환** — 좁혀진 성질을 아래 카드로 변환한다.

## 변환 카드 형식

```yaml
qualitative_input: "토스처럼 사용자 친화적인 UI"
reference_source: "토스 디자인 원칙 (URL, 확인일)"   # 참조 제품 없으면 null
decomposed_criteria:
  - id: UX-01
    criterion: "핵심 태스크의 사용자 입력 단계 수"
    target: "경쟁 제품 동일 태스크 대비 50% 이하, 절대값 3단계 이하"
    measure_method: "화면 플로우 다이어그램에서 사용자 결정 지점 카운트"
  - id: UX-02
    criterion: "설명 없는 첫 사용 완료율"
    target: "온보딩 안내 없이 신규 사용자 태스크 완료 80% 이상"
    measure_method: "프로토타입 사용성 테스트 5인"
```

작성 규칙:
- target은 숫자 또는 비교 기준을 포함해야 한다. "높게", "충분히"는 금지.
- measure_method는 실제 수행 가능한 방법이어야 한다. 측정 불가능하면 기준이 아니라 희망사항이다.
- 요구사항 문장은 가능하면 EARS 패턴("~할 때, 시스템은 ~해야 한다")으로 쓴다.

## 흘러가는 곳

변환된 기준은 버려지지 않고 다음에 반영된다.
- `05-product-blueprint.md` 비기능 요구 섹션 (기준 ID 그대로 인용)
- `07-roadmap.md` 해당 기능의 완료 기준 ("UX-01 통과"처럼 ID로 참조)

이렇게 하면 "토스 같은가?"라는 논쟁 대신 "UX-01 통과했는가?"를 확인하게 된다.

## 자주 쓰는 UX 기준 변환 예시

| 질적 표현 | 변환 후보 |
|---|---|
| 간편한 가입 | 가입 완료까지 입력 필드 수 N개 이하, 소요 시간 N초 이하 |
| 직관적인 화면 | 화면당 사용자 결정 1개 (One Thing per Page), 무설명 태스크 완료율 |
| 빠른 앱 | 첫 화면 표시 N초 이하, 주요 액션 응답 N ms 이하 (측정 도구 명시) |
| 접근성 좋은 | WCAG 2.1 AA 준수 항목 체크리스트 통과 |
