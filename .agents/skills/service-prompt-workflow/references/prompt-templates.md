# 단계별 프롬프트 템플릿 (복붙용)

각 블록을 복사해 `{{빈칸}}`을 채워 에이전트에게 준다. XML 태그로 지시·맥락·데이터·예시를
분리하는 이유: 에이전트가 "지시"와 "데이터"를 섞지 않게 하기 위함(Anthropic 구조화 원칙).

> 공통 규칙
> - **역할 한 줄**로 시작한다(페르소나). 톤·전문성이 고정된다.
> - **원하는 것**을 쓴다("하지 마" 대신 "이렇게 해").
> - 애매하면 예시 3~5개를 `<example>`로 붙인다(관련·다양·구조화).
> - 방향을 바꿔야 하면 에이전트가 **한 번에 하나** 묻게 한다.

---

## 0) BASE — 저장소 상시 지침 (CLAUDE.md / AGENTS.md)

한 번만 만들어 두면 매 세션 자동 로드된다. "제거하면 에이전트가 실수하게 되는 줄"만 남긴다.

```
<task>이 저장소의 에이전트 지침 파일(CLAUDE.md)을 만들/갱신해라.</task>
<include_only>
- 추측 불가능한 것만: 빌드/테스트/실행 명령, 기본과 다른 스타일 규칙, 테스트 러너,
  디렉터리 구조, 프로젝트 고유 아키텍처, 환경 함정(gotcha), 커밋/PR 관례.
</include_only>
<exclude>자명한 것, 일반 언어 상식, 장황한 배경 설명.</exclude>
<test_each_line>"이 줄을 지우면 에이전트가 실수하는가?" 아니오면 삭제.</test_each_line>
<format>짧고 사람이 읽기 좋게. 꼭 지켜야 할 항목은 이유를 붙인 평서문으로. git에 커밋.</format>
```

## 1) FRAME — 무엇을·왜 (착수 진단)

도메인을 알면 이 블록, 모르면 **service-autopilot을 먼저**.

```
<role>제품을 함께 정의하는 냉정한 시니어 PM. 근거 있는 판단만 말한다.</role>
<idea>{{한두 문장 아이디어}}</idea>
<interview>
아래를 한 번에 하나씩 물어 확정해라. 답을 못 채우면 업계 기본값으로 가정하고 "가정"이라 표시.
1. 사용자: 이걸 가장 절실히 필요로 하는 실제 사람은 누구인가(직함까지)?
2. 문제: 지금 그들은 이걸 어떻게(대충이라도) 해결하고 있고, 그 비용은?
3. 가장 좁은 쐐기: 이번 주에 돈 낼 만한 "가장 작은 버전"은?
4. 성공 기준: 무엇이 측정되면 성공인가(정성 표현은 측정 가능 지표로 변환)?
5. 범위 경계: 이번에 만들 것 / 명시적으로 안 만들 것.
</interview>
<hard_gate>산출은 frame 메모(위 5항목)뿐이다. 코드는 쓰지 않는다.</hard_gate>
<output>frame 메모를 파일로 저장. 완료상태: DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT.</output>
```

## 2) EXPLORE — 코드·패턴 먼저 읽기 (plan mode)

```
<role>이 저장소를 처음 여는 신중한 엔지니어.</role>
<task>{{목표}}를 구현하기 전에, 관련 코드와 기존 패턴을 먼저 조사만 해라.</task>
<rules>
- plan mode: 어떤 파일도 수정하지 마라.
- 관련 파일을 실제로 읽고 `파일:줄` 로 인용해라.
- 이 목표와 닮은 기존 구현을 최소 1곳 찾아 "이 패턴을 따르면 된다"를 지목해라.
- 재사용할 유틸/컴포넌트/서비스, 건드리면 안 되는 영역, 함정을 목록화해라.
</rules>
<output>탐색 노트: (1) 관련 파일 file:line 표, (2) 따라야 할 기존 패턴, (3) 재사용 대상, (4) 위험/함정.</output>
```

## 3) SPEC — 자기완결 명세 (진실원)

설계 패키지(service-autopilot 03~07)가 있으면 `<inputs>`에 붙인다.

```
<role>낯선 구현자도 그대로 실행할 수 있는 명세를 쓰는 스태프 엔지니어.</role>
<inputs>{{frame 메모 / service-autopilot 설계 패키지 / 탐색 노트}}</inputs>
<write_spec_md>
아래 목차로 SPEC.md를 작성. 설계 결정을 하나도 남기지 마라(구현자가 고민할 게 없어야 함).
## 배경(Context) — 왜 지금 필요한가
## 현재 상태(Current State) — 관련 코드 file:line 감사표
## 제안 변경(Proposed Change) — 무엇을 바꾸나
### 구현 세부(Implementation Details) — 파일·인터페이스·데이터 흐름을 이름까지 명시
## 수용 기준(Acceptance Criteria) — pass/fail로 판정 가능하게(정성 표현은 측정 기준으로 변환, "테스트 통과" 포함)
## 테스트 계획(Testing Plan) — 단위/통합/E2E 표 (+N건)
## 검증 방법(Verification) — 끝나면 무엇을 실행해 어떻게 "됐다"를 확인하나
## 롤백 계획(Rollback)
## 범위 밖(Out of Scope)
## 참조 파일(Files Reference) — 표
</write_spec_md>
<quality_gate>
작성 후 스스로 채점: "낯선 구현자가 이 명세만으로 실행 가능한가?" SCORE: N/10.
7점 미만이면 모호한 부분을 고쳐 다시 쓴다(최대 3회). 정성 표현·미결정 사항이 있으면 감점.
</quality_gate>
<output>SPEC.md 저장 + 최종 점수.</output>
```

## 4) PLAN — 순서 있는 작업 분해

```
<role>스펙을 실행 가능한 작업으로 쪼개는 엔지니어.</role>
<spec>{{SPEC.md 경로}}</spec>
<make_tasks_md>
tasks.md 작성:
- 각 작업은 작고(반나절 이내) 개별 검증 가능해야 한다.
- 순서(의존성)를 명시하고, 서로 독립인 작업은 [P](병렬 가능)로 표기.
- 각 작업에 "검증 가능한 완료 기준"을 붙인다.
- 테스트 우선: 각 기능 작업 앞에 "실패하는 테스트 작성" 작업을 둔다.
- 각 작업에 `model: opus|sonnet|haiku` 태그를 붙인다 (분류: references/model-routing.md —
  불변식·동시성·인증·마이그레이션=opus / CRUD·화면·RED 테스트·설정=sonnet / 리네임·문구·포맷=haiku).
  service-autopilot 08의 <model_hints>가 있으면 그 값을 초기값으로 쓴다.
</make_tasks_md>
<output>tasks.md 저장.</output>
```

## 5) BUILD — 구현 (새 세션 권장)

깨끗한 새 컨텍스트에서 SPEC.md/tasks.md를 보고 시작한다.

```
<role>{{예: 시니어 백엔드}} 엔지니어. 기존 코드처럼 읽히는 코드를 쓴다.</role>
<spec>{{SPEC.md}}</spec>
<tasks>{{tasks.md, 이번에 할 작업 번호, 그 작업의 model 태그}}</tasks>
<ladder>
코드를 쓰기 전에, 문제와 그 코드가 닿는 파일을 다 읽은 뒤, 첫 번째로 성립하는 단에서 멈춘다 (ponytail):
1 필요한가(YAGNI) → 2 이 코드베이스에 이미 있나 → 3 표준 라이브러리 → 4 플랫폼 네이티브 →
5 이미 설치된 의존성 → 6 한 줄로 되나 → 7 그제야 최소 코드.
줄이지 않는 것: 신뢰 경계 입력 검증, 데이터 손실 방지 에러 처리, 보안, 접근성, 명시 요청.
의도적 단순화는 `# ponytail: <상한>, <업그레이드 경로>` 주석으로 남긴다.
</ladder>
<how>
- 테스트 우선: 실패 테스트 → 최소 구현 → 리팩터. 한 작업씩, 작은 증분으로.
- 기존 패턴을 따른다(참조: {{탐색 노트에서 지목한 file:line}}).
- 요청 밖의 기존 버그·개선점은 이 변경에서 고치지 않고 요약에 후속으로 적는다. 테스트는 요청된 동작당 하나,
  이 저장소가 그런 변경에 테스트를 두는 곳에만 커밋한다. 검증용 스크래치 스크립트는 커밋하지 않는다.
- 라이브러리 import 전 package.json/의존성에 실제 존재하는지 확인한다.
- 오류는 억누르지 말고 근본 원인을 고쳐라.
- 이 작업을 서브에이전트에 위임하면 tasks.md의 `model:` 태그를 Agent `model`에 그대로 준다.
  VERIFY에서 2회 실패하면 한 등급 올려 재시도, 그래도 실패면 모델이 아니라 명세 문제 — SPEC으로 되돌아간다.
</how>
<examples>{{입출력/엣지케이스 예시 3~5개 — 있으면}}</examples>
<stop_condition>같은 문제로 3번 고쳐도 안 되면 멈추고 무엇이 막혔는지 보고해라.</stop_condition>
<output>변경 파일 목록 + 각 작업의 완료 기준 충족 여부 + 사다리에서 건너뛴 것과 추가 시점 (`skipped: X, add when Y`).</output>
```

## 6) VERIFY — 실행 검증 (증거 요구)

```
<task>{{방금 만든 것}}이 실제로 동작하는지 끝까지 실행해 확인해라.</task>
<close_the_loop>
- 통과/실패를 돌려주는 것을 실제로 실행해라: 테스트 스위트 / 빌드 종료코드 / 린트 /
  (UI면) 스크린샷을 기대 화면과 비교.
- 실행 결과(로그·종료코드·스크린샷)를 증거로 붙인다.
- 실패하면 근본 원인을 고치고 다시 실행한다.
</close_the_loop>
<output>검증 로그 + 통과/실패 판정 + 남은 리스크.</output>
```

## 7) REVIEW — 적대적 검토 (새 컨텍스트)

서브에이전트/새 세션에게 **diff와 기준만** 준다(구현 맥락 오염 없이).
정확성 리뷰어는 `model=opus`(생성 모델과 같거나 높은 등급), ponytail-review는 `sonnet` — `references/model-routing.md`.
리뷰어는 `fresh-reviewer` 에이전트 타입으로 띄운다 (읽기 전용, ponytail 페르소나 미주입).

```
<role>적대적 코드 리뷰어. 이 변경을 만든 사람이 아니다. 통과시키는 게 목표가 아니라 결함을 찾는 게 목표.</role>
<diff>{{변경 diff}}</diff>
<criteria>{{SPEC.md의 수용 기준}}</criteria>
<check>
- 정확성: 수용 기준을 실제로 충족하나? 반례가 있나?
- 요구사항 누락 / 범위 이탈은 없나?
- 회귀: 기존 동작을 깨뜨리지 않나?
- (프론트면) references/anti-patterns.md의 slop 체크리스트 적용.
- 정확성 판정 뒤 과잉설계만 따로 한 번: `ponytail:ponytail-review` 형식
  (`L<line>: delete|stdlib|native|yagni|shrink: 무엇을. 대체.`, 끝에 `net: -N lines`). 미설치면 같은 형식으로 직접.
문제만 file:line으로 적는다. 칭찬은 쓰지 않는다.
</check>
<output>확인된 결함 목록(심각도순) + 각 결함의 재현/실패 시나리오. 없으면 "결함 없음"과 그 근거.</output>
```

## 8) SHIP — 배포 (커밋·PR)

```
<task>검증·리뷰를 통과한 변경을 커밋하고 PR을 열어라.</task>
<rules>
- 논리 단위로 증분 커밋. 커밋 메시지·PR 제목/본문은 한글, 본문에 변경 항목을 정리.
- 확정 기록/불변 규칙(있다면)을 위반하지 않았는지 확인.
- 커밋/푸시는 사용자가 요청했을 때만. 기본 브랜치면 먼저 브랜치를 판다.
</rules>
<output>커밋 해시 + PR 링크(또는 준비된 메시지 초안).</output>
```

## 9) REFLECT — 회고·학습

```
<task>이번 작업에서 배운 것을 다음 세션이 재사용하도록 남겨라.</task>
<capture>
- 이번에 통했던/실패한 프롬프트·접근을 한 줄씩.
- 반복될 규칙은 CLAUDE.md에 append(추측 불가·재발 방지 가치 있는 것만).
- 방향 결정은 decision-log에: 무엇을·왜 선택, 어떤 대안을 왜 버렸는지.
</capture>
<output>학습 기록 + CLAUDE.md/decision-log 갱신 diff.</output>
```

## 부록: 컨텍스트 위생 (전 단계 상시 적용)

- 무관한 작업 사이 `/clear`. 긴 작업엔 `/compact <초점>`.
- 같은 지시를 **2번 고쳐도 안 되면** 세션을 비우고 프롬프트를 처음부터 다시 쓴다.
- 조사·리뷰 같은 대용량 읽기는 **서브에이전트**에 위임하고 1~2천 토큰 요약만 받는다.
- 긴 문서는 프롬프트 위쪽에 `<document>`로 넣고, "관련 구절을 먼저 인용하라"고 지시.
