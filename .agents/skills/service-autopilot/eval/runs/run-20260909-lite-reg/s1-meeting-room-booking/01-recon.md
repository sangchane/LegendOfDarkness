조사일: 2026-09-09 · 웹 호출 5회 (WebSearch 1 + WebFetch 4; 세션 WebSearch 예산이 첫 검색 뒤 소진되어 나머지는 1차 소스 직접 조회로 대체)
근거 표기: **[출처]** = 웹에서 확인한 사실 · **[사용자]** = 시드 원문 · **[추론]** = 그로부터 도출 · **[미확인]** = 확인 못 함

## 도메인 업무 흐름 — 사내 회의실 예약이 실제로 어떻게 돌아가는가
- 현재: 화이트보드에 회의실×시간 칸을 그려 수기로 이름을 적는다 **[사용자]**. 화이트보드 방식의 고유 문제 **[추론]**: (1) 사무실 밖(재택·외근·다른 층)에서 빈 시간을 못 본다 (2) 지운 자국·겹쳐 쓴 글씨로 누가 언제 잡았는지 불분명 (3) 취소가 전파되지 않아 빈 방이 "예약됨"으로 남는다 (4) 분쟁 시 기록이 없다.
- 디지털 대체품의 공통 루프 **[출처]**: 회의실(자원) 등록 → 캘린더/타임라인 뷰에서 빈 슬롯 선택 → 예약 생성 → 본인/관리자 취소. MRBS README가 스스로를 "physical booking systems를 대체하는 중앙 디지털 솔루션"으로 정의 — https://github.com/meeting-room-booking-system/mrbs-code (확인 2026-09-09)
- 핵심 불변식 **[출처]**: 같은 회의실에 시간이 겹치는 예약 2건이 공존하면 안 된다. PostgreSQL은 이를 DB 제약으로 표현한다: `EXCLUDE USING GIST (room WITH =, during WITH &&)` (btree_gist 확장) — https://www.postgresql.org/docs/current/rangetypes.html §Constraints on Ranges (확인 2026-09-09)

## 이해관계자 — 누가 쓰고, 누가 돈을 내는가
- 임직원(예약자): 빈 방 찾기·예약·취소. **[사용자]** 사내용
- 관리자 1인(총무/IT 담당 추정 **[추론]**): 회의실 등록·이름 변경·타인 예약 정리. LibreBooking·MRBS 모두 "admin이 room/area 설정" 역할을 분리 **[출처]** (위 두 저장소)
- 비용 부담: 회사(사내 도구, 판매 없음) **[사용자]**. 상용 대안 가격은 아래 유사 솔루션 표.

## 규제·표준
- 개인정보: 처리 항목이 임직원 이름·사내 이메일·예약 시각뿐이라 민감정보·결제정보 없음 **[추론]**. 국내 사업장이므로 개인정보보호법(최소 수집·보존기간·파기) 적용 대상 — 법령 원문 URL https://www.law.go.kr/법령/개인정보보호법 은 **[미확인]**(이번 런에서 조회 못 함). 설계는 최소 수집 + 보존기간 명시 + 기한 후 파기로 잡고(P2 기본값), 03 상수 표에서 보존기간을 `설계 결정`으로 둔다 — SC 목표에는 쓰지 않는다.
- 접근성·표준: 사내 도구라 법정 의무 없음 **[추론]**. WCAG 2.1 AA 항목 중 키보드 조작·대비만 자체 기준으로 채택(ux-principles-kr.md).
- 시간 표준: 저장은 UTC ISO 8601, 표시는 Asia/Seoul **[추론 — A5 데이터 규칙]**.

## 스택 후보 2개 (lite 상한 2)
fit 판단 기준(evidence-map fit_score): 요구 충족 · 팀 적합성(미상 → Assumed) · 운영 환경(사내 서버 1대·1인) · 생태계 · 총비용.

| 후보 | 구성 | 근거·트레이드오프 | fit |
|---|---|---|---|
| **A (채택)** TypeScript 풀스택 | Next.js(App Router, Route Handlers) + PostgreSQL 16(btree_gist EXCLUDE) + Drizzle ORM + Docker Compose(app·db 2컨테이너) | 이중예약 방지를 앱 로직이 아니라 DB 제약으로 보장 [출처 PostgreSQL 문서]. 프론트·백을 한 저장소·한 언어로 → 1인 운영 부담 최소. 트레이드오프: 관리자 화면을 직접 만들어야 함(회의실 CRUD 1화면이라 작음). 팀이 TS를 모르면 B | 높음 — 운영 환경·총비용·요구 충족. 팀 적합성은 Assumed |
| B Python | Django 5 + PostgreSQL + Django admin | 관리자 화면(회의실 CRUD)을 admin으로 공짜. 트레이드오프: 타임라인 UI는 어차피 JS가 필요해 언어 2개, 반응형 인터랙션에 템플릿+HTMX 학습. PG EXCLUDE는 마이그레이션에서 RawSQL로 동일하게 적용 가능 | 중간 — 관리자 화면 이득보다 언어 2개 비용이 큼(1인 운영) |

SQLite 단일 파일은 검토 후 제외 **[추론]**: range 타입·EXCLUDE 제약이 없어 이중예약 방지를 앱 트랜잭션에 의존해야 하고, 그 코드가 곧 최상위 리스크(INV-1)가 된다. PG 컨테이너 1개 추가 비용이 더 싸다.
