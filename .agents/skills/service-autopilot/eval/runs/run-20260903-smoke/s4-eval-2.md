# 심사 판정 — s4 (시드: 라즈베리파이로 IP 카메라를 제어하고 실시간 모니터링하는 서비스)

심사 대상: doc1(PiCam Watch 패키지) vs doc2(PiCam Hub v0.1)
판정 기준: 구현 착수에 필요한 정보의 밀도. 길이는 품질이 아니다.

---

## [1. 완전성]

**doc1 근거 인용**

- 엣지케이스가 독립 절로 존재하고 Given/When/Then 16건 전수:
  "E-8 | 이벤트 | 클립 진행 중(t=0 시작) | t=15s, t=25s에 모션 | 이벤트 1건, 클립 종료 = t=45s(마지막 모션 + 20s), 사각지대 없음"
  "E-11 | 보존 | 부팅 직후 NTP 미동기(RTC 배터리 방전) | 이벤트 발생 | 클립 저장하되 `time_unsynced=true` + 단조시계 오프셋 기록"
- 위협모델이 경계별 STRIDE 6범주 전수 → 처리표 → 상위 리스크 재검토의 3단 구성:
  "| **TB3 Pi→카메라** | 가짜 카메라(ARP 스푸핑)로 위장 | RTSP 평문 스트림 변조 | 해당없음 — 카메라는 행위자 아님 | 카메라 자격증명·영상 LAN 스니핑 | ... |"
  "| TB3-E 카메라발 페이로드 | Mitigate | zeep/lxml `resolve_entities=False`·`no_network=True`(XXE), ffmpeg·go2rtc 별도 UID·read_only·다이제스트 고정 |"
- 운영/장애가 RTO/RPO까지 내려간 9행 시나리오 표 + 런북 골격 + 준비도 체크리스트:
  "| NVMe 고장 | 부팅 실패·I/O 에러 | 클립·DB·설정 전부 | ... | 4h / **24h(외부 USB 정상 시), USB 미장착·고장 시 복구 불능** |"
- 영역 간 누락을 스스로 전수 대조:
  "P0·P1 매핑 0건: **없음** — P0 17건, P1 9건, P2 3건 전부 매핑."
  "누락 확인(ID 전수 대조): SC-001 ... = 15/15 · P0 FR 17건 17/17 · ... · E-1~E-16 16/16. **누락 0.**"

**doc2 근거 인용**

- 사용자 정의는 doc2가 더 두껍다: 페르소나 3종에 기술 수준까지 —
  "| P1 소상공인 사장(카페/매장) | 카메라 2~4대, 매장 밖에서 폰으로 확인 | 쉬운 설치, 원격 확인, 사건 시 클립 저장 | 낮음 |"
  역할 3종(owner/operator/viewer)과 US-1~11 + 수용 기준.
- doc1에 아예 없는 영역을 보유: 로드맵("**M0 PoC** | 2주 | ... | **M3 Ops** | 3주"), 부록 B 카메라 호환성 매트릭스(브랜드별 RTSP 템플릿·이벤트 토픽), 부록 A 용어, 부록 C CSI 확장안, UI 화면 9종 표.
- 그러나 엣지케이스 전용 절이 없고, 위협모델은 경계별이 아닌 평면 16행 목록이며, 장애 대응은 RTO/RPO 없는 6행 요약:
  "| 카메라 offline | `/system/health`, ping, `ffprobe rtsp://` | 자격증명/IP 변경 확인, 카메라 재부팅, ONVIF 포트(80/8080/2020) 확인 |"
- 감사 액션 목록, 엔드포인트별 에러코드, FR↔엔드포인트↔테스트 대조표가 없다.

**판정: doc1** — 차원이 지정한 6개 영역 중 엣지케이스·보안위협·API/데이터·테스트·운영 5개에서 doc1이 전수 대조 수준으로 앞서고, doc2가 앞서는 것은 사용자 정의와 로드맵·호환성 부록에 한정된다.

## [2. 비모호성]

**doc1 근거 인용**

- 요구사항이 EARS 문장으로 주어·조건·수치를 모두 고정:
  "FR-007 | Owner가 PTZ 패드를 누르고 있는 동안, 클라이언트는 750ms 주기로 이동 요청을 갱신하고 시스템은 ContinuousMove(Timeout=1s)를 보내며, 키를 떼면 100ms 내 Stop을 보내야 한다"
  "FR-013 | ... 진행 중이면 그 클립의 종료 시각을 '마지막 모션 + 20초'로 연장(상한 시작 + 120초)해야 한다"
- 모호어를 수치로 치환한 기록이 남아 있다:
  "#34 E-11 보정 규칙 수치화: 단조시계 오프셋으로 created_at·expires_at 재계산, 미동기 90일 지속 시 파기 — '보수적(늦게)' 모호성 제거"
- "## 미결정 — 0건 (v1.2에서 리뷰어가 미결정으로 지목한 4건 — 알림 채널·외부 프로브·녹화 소스·90일 근거 — 는 각각 FR-028·non-goal·FR-014·INV-4 Assumed로 결정했다.)"
- 다만 자기 모순 7건을 스스로 적발해 남겼다:
  "D3 | HIGH | E-11의 단조시계 오프셋은 재부팅 시 리셋되어 보정식 무효; 미동기 중 '건너뜀'이 retention 7일 클립을 90일 보관 → INV-4 자기모순"
  "D1 | HIGH | 03은 Tailscale/FR-020을 P2로 두는데 04·07은 MagicDNS origin·Tailscale 설치를 MVP 필수 절차로 둠 — MVP 시청 origin 모순"
  단, 각 건에 확정된 수정안이 붙어 있다("**FR-020을 P1로 승격**", "EVENT에 `boot_id` 추가 ... RTC(배터리) 값 폴백").

**doc2 근거 인용**

- 표기 규칙 자체는 우수하다: "**[확정]** 근거 있는 사실/결정 · **[가정]** 이 문서가 스스로 정한 전제 · **[미확정]** 검증·의사결정이 남은 항목", 가정표에 "가정이 틀리면 영향" 열까지 있다.
- 그러나 미결정이 기초 층에 남았다:
  "1. 사용자군이 B2C 셀프호스팅인지 B2B 관제인지 — 답에 따라 멀티사이트·RBAC 깊이 변경."
  "5. MediaMTX 버전 핀과 삭제 경로 설계(§6.5, §10.3) — M0/M2에서 확정."
- MVP 경로 위에 미결정이 걸려 있다:
  "보존 정책 삭제는 hub-api가 recordings를 읽기 전용으로 마운트하므로 **삭제는 MediaMTX `recordDeleteAfter` + hub-api가 Control API/전용 삭제 사이드카(쓰기 권한 최소)로 수행** `[미확정: 삭제 경로 최종 결정은 M2]`" — 그런데 FR-11 보존 정책은 Must다.
- 검증 불가·느슨한 표현:
  "| MediaMTX CPU (패스스루, 채널당) | Pi 5 ≈ 2~4 %, Pi 4 ≈ 4~7 % | Go 패스스루 벤치 경험치 |"
  "보존 하한(예: 3일)은 경고", "우선순위(owner 우선)"(기전 미정의).
- 표기되지 않은 모순: 백업은 "`sqlite3 .backup` + `/etc/picamhub`(키 제외)"인데 복구는 "카메라·사용자·프리셋 복원"이다. master.key가 백업에서 빠지면 AES-256-GCM으로 암호화된 카메라 자격증명은 복호할 수 없다.

**판정: doc1** — doc1은 남은 모호성마저 번호를 붙여 수정안과 함께 드러낸 반면, doc2는 대상 사용자군·보존 삭제 경로 같은 상위 결정이 미정으로 남고 키 제외 백업 같은 모순은 표기조차 되지 않았다.

## [3. 검증가능성]

**doc1 근거 인용**

- 성공 기준 15개가 전부 pass/fail이며 측정 방법과 게이트 열을 갖는다:
  "SC-005 | PTZ 100회 → 감사로그 100건, 누락 0, 해시 체인 검증 통과 | DB 카운트 + `picam audit verify` | MVP"
  "SC-011 | 전원 강제 차단 10회 → 부팅 10/10, SQLite `integrity_check` OK, 차단 직전 커밋된 감사 행 보존 10/10, 고아 `recording` 이벤트 0 | 리허설(차단 직전 PTZ 1회 후 즉시 차단, HW rig) | MVP"
  "SC-013 | 모든 스트림 정의·링버퍼 세그먼트·클립에 오디오 트랙 0개, 오디오 관련 설정 키·API 0개 | ffprobe + 설정·OpenAPI 검사 | MVP"
- 수용 기준이 시나리오로 1:1 변환되고 레이어·목킹까지 지정된다:
  "| FR-014 (전 10초) | Given 이벤트 시각 T / When 클립 생성 / Then 첫 프레임 PTS ≤ T−8s, 진행 중 세그먼트 포함, DTS 불연속 0(ffprobe) | integration | GOP 2s testsrc |"
- SLI/SLO도 판정 가능하게 정의: "| 보존 준수 | 만료 후 1h 내 purged 비율 | 100% (법정 — 예외적으로 100%, 위반 = 즉시 알람) |"

**doc2 근거 인용**

- KPI 표는 목표치와 측정 방법을 갖는다:
  "| 온보딩 시간(전원 켜고 첫 라이브까지) | ≤ 5분 (P50), ≤ 10분 (P90) | 사용성 테스트 5명 |"
  "| 녹화 누락률 | ≤ 0.1 % (분 단위 갭 기준) | 세그먼트 인덱스 갭 분석 |"
- 일부 수용 기준은 명확하다: "US-3 ... Chrome/Safari/Firefox 최신 2개 버전에서 WebRTC 재생, 실패 시 5초 내 HLS 폴백", "§9.4 [ ] 72 h 소크 KPI 충족 / [ ] 보안 자동화 스캔 High 0건".
- 그러나 판정 경계가 없는 항목이 섞여 있다:
  "US-2 ... 프로필 목록 중 '라이브용(H.264, ≤1080p)'과 '녹화용(메인)'을 자동 추천, 사용자 변경 가능" — 무엇이 실패인지 정의되지 않음.
  "NFR-01 | 성능 | Pi 5: 8대 패스스루 녹화 + 동시 시청 세션 6개에서 CPU ≤ 60%" — 측정 창·부하 절차 미정(doc1은 "5분 평균 ≤ 60%, 프레임 드롭 ≤ 1%"로 고정).
- FR-01~20은 Must/Should/Could 우선순위만 있고 FR별 수용 기준이 없으며, KPI↔테스트 대조표도 없다. 게다가 KPI "카메라 호환성 | 상위 6개 브랜드에서 온보딩 성공"의 판정 근거인 부록 B는 스스로 "[초안, 검증 대상]"이다.

**판정: doc1** — doc1은 SC 15건 전부가 측정 방법·게이트와 함께 시나리오로 전수 변환되어 누락 0을 대조까지 하는 반면, doc2는 KPI 수준의 목표치는 있으나 FR별 수용 기준과 기준↔테스트 연결이 비어 있다.

## [4. 실행가능성]

**doc1 근거 인용**

- 착수 직후 결정해야 할 값이 복붙 수준으로 확정되어 있다:
  "카메라별 ffmpeg `-c:v copy -an -f segment -segment_format mpegts -segment_time 10 -segment_wrap 4`를 **tmpfs 링버퍼**(`/run/picam/ring`)에 상시 기록 ... 사이징: 4대 × 4Mbps × 40s ≈ 80MB → tmpfs 128MB"
  "api↔recorder IPC | **SQLite 테이블 폴링(outbox)**: recorder는 `event.status='recording'`(1s)·`camera`(10s)를 폴링. 별도 소켓·큐 없음"
  "`CREATE TRIGGER audit_log_immutable BEFORE UPDATE ON audit_log BEGIN SELECT RAISE(ABORT,'append-only'); END;`"
  compose에 UID·`read_only`·`mem_limit`·`pids_limit`까지, nftables는 "443/tcp(→ `redirect to :8443`)·8555/udp·8555/tcp"까지 명시.
- 약점: 마일스톤·착수 순서가 없고, 스스로 착수 차단을 선언한다 —
  "그중 4건(Tailscale P1/P2 모순, E-11 재부팅 보정 무효, 프리셋 recall로 INV-9 우회, 자격증명 재입력 경로 부재)은 **결정 수정 없이는 MVP 착수 불가**다."
  다만 D1~D7 각각에 "처리 계획"이 확정 문장으로 붙어 있어 실질은 적용만 하면 되는 패치 목록이다.

**doc2 근거 인용**

- 첫날 순서가 검증 조건과 함께 제시된다:
  "1. 리포 골격(monorepo: apps/hub-api, apps/hub-web, deploy/ansible, deploy/compose, tools/sim) → 검증: CI lint/test 통과 ... 4. 스트림 JWT + JWKS + MediaMTX jwt 인증 → 검증: aiortc WHEP 클라이언트 프레임 수신"
- 하드웨어 없이 개발을 시작할 수단을 설계했다:
  "| ONVIF 장치 | 자체 제작 최소 SOAP 목(FastAPI): GetSystemDateAndTime, ... CreatePullPointSubscription, PullMessages. 호출 기록·지연/오류 주입 API 제공 |"
  브랜드별 RTSP 템플릿("Hikvision `/Streaming/Channels/101`, Dahua `/cam/realmonitor?channel=1&subtype=0` ...")과 quirks 테이블도 즉시 쓸 수 있다.
- 약점: 착수 직후 필요한 두 값이 비어 있다 — "image: bluenviron/mediamtx:1.x.y # 핀 고정 [미확정: M0에서 확정]", 그리고 보존 삭제 주체 "[미확정: 삭제 경로 최종 결정은 M2]". §4.6 성능 예산 전체가 "[가정 — HIL 테스트로 검증 필요]"라 채널·뷰어 상한 강제 로직의 근거값이 미확정이다.

**판정: doc1** — 착수 순서 제시는 doc2가 낫지만, 컴포넌트 경계·IPC·스키마·설정값처럼 착수 직후 반드시 확정돼야 할 항목의 결정도는 doc1이 크게 앞서고 doc1의 잔여 7건은 수정안이 이미 문장으로 적혀 있어 적용만 하면 되는 반면 doc2의 미확정은 답 자체가 없다.

## [5. 근거성]

**doc1 근거 인용**

- 출처를 유형별로 분리하고 URL과 확인일을 강제한다:
  "표기: **[사실]** 출처 직접 확인 · **[2차]** 블로그·요약 등 2차 출처(교차 확인 필요) · **[추론]** 사실에서 도출"
  "Pi 5는 H.265 HW 디코드만, **H.264 HW 인코더 없음·H.264 디코드도 SW** [사실: [Pi 포럼](...t=357999), [HN](...)] → 트랜스코딩 회피가 설계 원칙"
  "BCM2835 HW 워치독 기본·최대 타임아웃 15초 ([Pi 포럼 watchdog](...t=353094))"
- 2차 출처의 한계를 스스로 표시한다: "보관기간 기본값 | 별도 정함 없으면 **30일** ... [2차: 검색 요약, 가이드라인 원문 재확인 권고]"
- 가정이 가정임을 값 옆에 붙인다: "**INV-4** ... 보존기간 상한 90일(**Assumed** — 가이드라인 '필요 최소기간' 요구에 따라 무기한 보존을 막는 운영 상한, 법정 수치 아님)"
- 기술 선택마다 버린 대안과 이유가 남는다: "#2 스트림 게이트웨이 go2rtc 채택 ... / MediaMTX 기각 — ONVIF 디스커버리 부재", 스택 표에 "근거 | 트레이드오프 | fit" 열.

**doc2 근거 인용**

- 가정표가 "가정이 틀리면 영향" 열을 갖는 점은 doc1에 없는 강점이다:
  "| A11 | 카메라는 최소 **H.264 스트림 1개** ... | 브라우저 WebRTC H.264 범용성 | §4.5 결정 트리 참조 |"
- ADR에 결과/트레이드오프가 붙는다: "| ADR-003 | 스트림 인증은 JWT+JWKS | ... | 토큰 유출 시 5분 창. 쿼리스트링 토큰은 로그 마스킹 필요 |"
- 스택 표도 기각 이유를 남긴다: "go2rtc(녹화·플레이백 없음, 별도 ffmpeg 세그먼터 필요) / ffmpeg 직접(시그널링·재생 서버를 직접 작성해야 함)"
- 그러나 출처가 추적 불가능하다: 부록 D는 "Raspberry Pi 포럼 'RPi5 Codec confusion' 및 'Lack of Hardware H.264 Decoding' 스레드, Jeff Geerling ... Frigate Discussion #18431"처럼 URL·확인일이 없는 산문이고, §3.3은 [확정]으로 표기되었는데 Pi 4의 "HW 1080p30 (V4L2 m2m)" 같은 수치에도 링크가 없다.
- 핵심 설계 예산이 무근거다: "| WebRTC 뷰어 세션당 추가 CPU | ≈ 1~3 % (SRTP 암호화) | |"(근거 열 비어 있음), 표 전체가 "[가정 — HIL 테스트로 검증 필요]".

**판정: doc1** — doc2의 "가정이 틀리면 영향" 열은 우수하나, doc1은 사실/2차/추론 구분과 URL·확인일까지 강제하고 Assumed 수치마다 "법정 수치 아님" 같은 한계를 붙여 근거의 추적 가능성이 한 단계 높다.

## [6. 범위 절제]

**doc1 근거 인용**

- 절제한 지점은 분명하다:
  "**오디오 스트리밍·녹음(자택 전용 모드 포함)** — 녹음 금지 조항 대응으로 기능 자체 부재"
  "영구 상시 녹화(24/7 저장), NAS 연동 — 40초 휘발 링버퍼(RAM)는 저장이 아니며 재부팅 시 소실"
  "객체 인식·사람/차량 분류(Frigate + Hailo로 확장 가능, 본 범위 아님)"
- 그러나 시드가 요구하지 않은 하드닝이 두껍다: 감사 해시 체인 + "체인 앵커 HMAC(master.key 파생)", "감사로그 1년 아카이브 ... 트리거 2개 DROP → `DELETE WHERE at < now-1y` → 트리거 재생성 ③ `audit.archive` 행 ... 앵커로 추가", 1회용 설정 토큰과 복구 키 1회 표시, age 암호화 USB 백업, 부팅 시 클립 해시 재검증, "API 프로세스는 비루트로 **8443**에 바인딩하고 호스트 nftables가 443→8443으로 리다이렉트".
- 산출물 자체에 프로세스 의례가 실려 있다: "## 검토 이력 | 1차 | B (fresh-context) | 03 v1.1, 04~07 v1.0 | FAIL (15건) |", 지적 처리표 25행, "## 참고자료 사용 기록" 16줄, decision log 42건 — 구현자에게 필요한 정보라기보다 작성 과정의 기록이다.

**doc2 근거 인용**

- 제외 목록과 단계 분리는 명확하고, M1은 시드에 거의 정확히 비례한다:
  "**MVP 제외 (Later)**: 클라우드 릴레이/계정, 네이티브 앱, 푸시 알림 인프라 / AI 객체 검출 ... / 오디오 양방향(talkback) ... / 다중 사이트 통합 관제, 멀티테넌트"
  "**M1 MVP-Live** | 4주 | 온보딩 마법사, 그리드, PTZ/프리셋, 인증/RBAC, 상태 대시보드, 설치 스크립트"
- 그러나 MVP 자체가 시드를 넘어 넓다: 연속 녹화 + 타임라인 재생 + 구간 내보내기 + 3역할 RBAC + PWA + Ansible + 옵션 Prometheus/Grafana/Loki. 스스로 부담을 드러낸다 —
  "| NFR-09 | 저장 효율 | 4 Mbps × 8대 = 약 345 GB/일. 1 TB SSD 기준 약 3일 → 기본은 메인스트림 2 Mbps 권장 및 보존 정책 안내 |"
- 요청 밖 확장 자산이 문서에 남아 있다: "FR-18 | Home Assistant 연동용 REST/WS API 토큰(스코프) | Could", 부록 C CSI 카메라 지원 방안, "**(Later) 클라우드 릴레이** | 시그널링·TURN·계정 서비스 ... | 미확정".
- 범위 내 자기 모순도 있다: §3.5는 "오디오 녹음 기본 OFF"인데 §6.3 응답 예시는 `"capabilities": { ... "audio": true }`, §8.2는 "자동재생 정책: 음소거 기본, 사용자 클릭 후 오디오 활성"이다.

**판정: tie** — doc1은 법 대응 하드닝과 검토 이력·참고자료 기록 같은 프로세스 장식으로, doc2는 MVP 기능 폭(연속녹화·타임라인·내보내기·관측 스택·확장 부록)으로 각각 시드를 넘어서므로 어느 쪽이 더 비례한다고 단정할 수 없다.

## 종합 판정: doc1

doc1은 완전성·비모호성·검증가능성·실행가능성·근거성 5개 차원에서 앞서고 범위 절제 1개 차원만 무승부인데, 우위의 근거는 분량이 아니라 요구사항·엔드포인트·엣지케이스·성공기준·테스트를 ID로 상호 대조해 "누락 0"을 스스로 증명하고 값마다 수치·출처·Assumed 표시를 붙였다는 점이다. doc2는 페르소나·로드맵·호환성 매트릭스·카메라 시뮬레이터처럼 doc1에 없는 실무 자산과 "가정이 틀리면 영향" 열을 갖췄으나, 대상 사용자군·보존 삭제 경로·MediaMTX 버전 핀이 미정으로 남고 성능 예산 전체가 무근거 경험치이며 백업 키 제외/오디오 기본값 같은 미표기 모순이 있다. doc1도 스스로 HIGH 7건을 남겼지만 각각에 확정된 수정 문장이 붙어 있어 적용 가능한 패치 목록인 반면, doc2의 미확정은 답 자체가 비어 있다는 점에서 착수 리스크가 더 크다.
