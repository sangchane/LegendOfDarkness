# 심사 결과 — s8 (doc1 vs doc2)

심사 대상: 요양시설 낙상 감지·알림 서비스 기획·설계 문서 2종
판정 기준: 구현 착수에 필요한 정보의 밀도 (길이는 품질이 아님)

## [1. 완전성]

**doc1 근거 인용**
- 엣지케이스가 흐름별 Given/When/Then으로 전수 나열: "**Given** 302호 구역 센서 2대, **When** 20초 간격으로 두 센서가 낙상 신호, **Then** FallEvent 1건(DETECTED), 알림 1회" / "**Given** 알림톡 대행사 5xx … **Then** 3회 재시도(10초 간격) 후 SMS 폴백, 둘 다 실패면 관리자에게 '수동 연락 필요' 알림" (흐름 A·B·C 12건)
- 보안: DFD + "STRIDE 표 (전 경계 6범주)" 7개 경계 × 6범주 격자 + 대응 표 22행 + "④ 충분한가 — 상위 리스크 3 재검토 + 잔여" (Accept 사유 명시)
- API/데이터: E-01~E-70 + 게이트웨이 로컬 API(L-11~L-90) + MQTT 토픽 계약 + OpenAPI 스케치 + 컬럼 수준 ERD, 그리고 "커버리지 매핑 (FR ↔ 엔드포인트/이벤트) … P0·P1 21건 중 미매핑 **0건**"
- 운영: 장애 시나리오 표에 RTO/RPO 수치("게이트웨이 하드웨어 사망 … RTO 4h / RPO 0"), 알람 9개 각각 런북 1:1, "R-1 게이트웨이 교체" 런북 본문(메타·트리거·진단·해결·에스컬레이션·검증·롤백), 준비도 체크리스트 12항
- 테스트: "누락 검사: SC-001~010 → 10/10, P0/P1 FR-001~016·020·021 → 18/18, INV-01~07 → 7/7, PRD 엣지케이스 … 12/12. **누락 0.**"

**doc2 근거 인용**
- 사용자 측면이 강함: 페르소나 4종("요양보호사 김OO — 야간 1인이 20명 담당 … 장갑 자주 착용"), Happy path 8단계 시각 타임라인("03:12 … 03:12:20 … 03:25")
- 보안: STRIDE 표 12행 + "7.3 개인정보 설계 원칙" 6항 + 인가 매트릭스(역할 5 × 리소스 6)
- API: 엔드포인트 표 + FallEvent JSON 표현 + 종결 요청 JSON + WSS 메시지 목록 + MQTT `SensorEvent` 스키마
- 운영: "10.5 런북(요약 목록) 시설 오프라인 대응 / 센서 오프라인 대량 발생 / 알림 채널 장애 폴백 확인 …" — **제목만 나열, 본문 없음**. 장애 대응은 "6.4 오프라인·장애 대응 설계" 표 6행이나 RTO/RPO 목표치 없음
- API 문서에 엔드포인트별 오류 카탈로그·권한 스코프·요구사항↔엔드포인트 매핑이 없음(F-01~F-19가 어느 API로 실현되는지 추적 불가)

**판정: doc1** — 지정된 6개 영역(사용자·엣지케이스·보안위협·API/데이터·테스트·운영/장애) 중 doc2가 앞서는 것은 페르소나 정도이고, 엣지케이스 전수·요구↔API 커버리지 매핑·RTO/RPO·런북 본문에서 doc1만 채워져 있다.

## [2. 비모호성]

**doc1 근거 인용**
- 설정값에 기본값과 허용 범위를 동시에 못박음: "`escalation_policy{zone_timeout_s:60 [30~120], all_timeout_s:120 [60~300], repeat_every_s:30 [15~60], repeat_max:3 [1~5] …}` — 범위 밖·비활성화(0) 불가"
- 수치 드리프트를 단일 출처로 봉합: "NFR-005 보존(단일 상수 표 — 04/05/07은 이 값을 참조) … 감사 로그 **3년** · 멱등성 키 72h … stale 판정: 게이트웨이 무응답 180초, 클라우드 단절 15분"
- 권위 시각 같은 애매점을 명시적으로 해소: "**법적·측정용 `ack_at`은 게이트웨이 수신 시각(RTC)** 이고 단말 탭 시각은 `device_at` 보조 필드로만 보존"
- "## 미결정 — **0건.**"
- 흠: 본문 곳곳에 "(참고자료)", "단계 RECON", "[01-recon §1]((문서))" 같은 치환 흔적이 남아 어떤 단계·자료를 가리키는지 불분명한 문장이 있음

**doc2 근거 인용**
- 조건부·미확정 표현이 상시 남아 있음: "인터넷 단절 시 로컬 패널·사이렌·시설 내 Wi-Fi 푸시(**가능 시**) 유지", "LoRaWAN 우선 … **필요 시** Wi-Fi/PoE", "레이더는 영상정보처리기기가 아니라고 보는 것이 **합리적이나 법적 판단 필요**"
- 검증 방법이 비어 있는 NFR: "운영 | 센서 교체·재바인딩 10분 내, 게이트웨이 OTA 무중단 | **런북**"
- 미결정 잔량: "11.3 오픈 이슈 [미확정] 1. 채택 센서 모델·벤더 2종 … 2. 가격·과금 단위 … 7. 화장실 레이더 설치 시 습기·설치 위치 기준" (7건) + 부록 A 가정 15건
- 문서 구조 결함: "## 7. 위협 모델·개인정보 설계"와 "## 7. 데이터 모델 (ERD)"이 같은 번호, 부록 A의 #열이 "단계"로 깨져 A1~A7 식별 불가

**판정: doc1** — 양쪽 다 치환·번호 결함이 있으나, doc1은 타이머·보존·권위 시각을 범위까지 확정하고 미결정 0을 선언한 반면 doc2는 핵심 선택(센서 벤더·가격·법적 성격)을 미확정으로 남겼다.

## [3. 검증가능성]

**doc1 근거 인용**
- 성공 기준 전부가 측정식과 함께: "SC-001 감지→직원 단말 표시 p95 ≤ 10초 | 파일럿 30일 전 이벤트의 `detected_at`→앱 `displayed_at` 차이", "SC-004 파일럿 4주차 주간 오탐률 ≤ 30% | FALSE_POSITIVE / (CONFIRMED+FALSE_POSITIVE)"
- 합격선과 운영 목표를 분리해 판정 혼선 제거: "*SC는 파일럿 합격선(소표본 전수), 07의 SLO 99.0%는 운영 월간 목표 — 둘은 다른 지표다*"
- 수용 기준 → 시나리오 변환표가 레이어·목킹까지 지정: "INV-01 부정 | **Given** CONFIRMED 통보 발송 전(큐 대기) 정정 **Then** 낙상·정정 둘 다 0건 | unit | 상태별 파라미터화"
- 판정 불가 항목도 판정 가능 형태로: "SC-010 파일럿 전 식약처 '해당 여부 질의' 접수번호 확보 … | 문서 존재"

**doc2 근거 인용**
- 감지 품질 기준이 명확: "**채택 기준**: 민감도 ≥ 95%, 느린 낙상 ≥ 85%, ADL 오탐 ≤ 3%", "라이브 전환 기준: 오탐 ≤ 1건/침상/주, 섀도 기간 시설 보고 낙상 중 미감지 0"
- 장애 주입 표에 합격 조건: "인터넷 단절 | 게이트웨이 WAN 차단 후 합성 낙상 | 10초 내 패널·사이렌 … 복구 후 5분 내 이벤트 동기화, 유실 0"
- 사용성도 수치화: "합격: 2탭 내 출동, 종결 60초 내, SUS ≥ 70"
- 다만 최종 인수 기준에 주관 항목: "§9.7 … 시설장 서면 확인: '도입 전 대비 발견 시간 단축 **체감**', 보호자 설문 만족 ≥ 4/5"

**판정: doc1** — doc2도 대부분 수치 기준을 갖췄으나, doc1은 SC·FR·INV 전건이 시나리오·측정 원천·레이어까지 1:1로 연결되고 누락 카운트를 스스로 검증한다.

## [4. 실행가능성]

**doc1 근거 인용**
- 엔드포인트가 필드·오류·스코프까지: "E-13 `POST /fall-events/{id}/resolve` | `outcome`(`CONFIRMED`|`FALSE_POSITIVE`), `injury?`, `note?`(≤500자), `resident_id`(**CONFIRMED면 필수** …) | 200 FallEvent | `resident-required`(422 …) | `events:fall-events:resolve`"
- 스키마가 제약까지: "fall_events { … uuid resident_id FK \"CONFIRMED면 NOT NULL (CHECK)\" … }", "`event_transitions`·`audit_log`·`notifications`: INSERT만 허용(`REVOKE UPDATE, DELETE`)"
- 컴포넌트가 메서드 시그니처 수준: "EventEngine { +mergeWindow 30s +ack(eventId, staffId, deviceAt) at=RTC now +amend(eventId, outcome) 5min window … }"
- 착수 순서까지 지정: "구현 순서: EventEngine 상태기계(unit 100%) → LocalStore/AuditLog 해시체인 → LAN WS + 기기 자격증명 → SyncAgent/outbox → 클라우드 ingest/mirror → NotificationService(INV-01 final-state) → …"

**doc2 근거 인용**
- 프로젝트 착수 계획은 더 구체: "M0 검증 4주 … 채택 센서 결정, 동의서 초안, '이 가격에 도입하겠다' 시설 2곳 LOI / M1 MVP 10주 / M2 파일럿 8주(섀도 4주 → 라이브 4주)"
- 인프라 뼈대 제시: "`network`, `iot-core`, `ingest`(IoT Rule → SQS DLQ 포함), `db`(RDS Multi-AZ, 자동 백업 35일, PITR), `services`(ECS Fargate: api, event-engine, notifier, ws-gateway) …"
- 그러나 API 대부분이 한 줄 요약에 그침: "`POST /events/{id}/arrive` | 직원 | →ON_SITE", "`POST /events/{id}/reopen` | 관리자 | 종결 정정(사유 필수)" — 요청/응답 스키마·오류 코드·권한이 없어 구현자가 다시 설계해야 함
- 런북·오류 카탈로그가 목록뿐이라 온콜 실행 불가

**판정: doc1** — doc2가 마일스톤·인프라 모듈로 "프로젝트 착수"에 유리한 반면, 문서 하나만 들고 첫 코드를 쓰기에는 계약·스키마·불변식·구현 순서가 확정된 doc1이 앞선다.

## [5. 근거성]

**doc1 근거 인용**
- 주장 단위 출처·확인일 규칙: "표기 규칙: **[사실]** = 출처 있는 사실 / **[추론]** = 사실에서 도출 / **[추천]** = 이 파이프라인의 선택. 전 항목 URL·확인일(2026-09-03) 병기" — 실제로 long lie, CCTV 시행규칙, 경쟁 5종, 정확도 문헌 각 행에 링크가 붙어 있음
- 기술 선택마다 버린 대안과 이유: "#D-003 MQTT 브로커 = Eclipse Mosquitto — 시설당 단일 노드로 충분 / EMQX 5.9+는 BSL 1.1 '타사 임베디드 제공 제한'이 시설 임베드 배포 모델과 충돌 가능"
- 가정을 가정으로 표기: "Assumed 44건", "→ 답: **무응답 → A Assumed(무응답)**", "**Assumed — 벤더 실검증 미완**"(Twilio)
- 자기 한계도 기록: "판정: **CONCERNS** … 패치의 정합성은 다음 단계에서 낯선 구현자가 재확인해야 한다"

**doc2 근거 인용**
- 표기 체계가 명확하고 확인 시점까지 지정: "[확정]/[가정]/[미확정]", 부록 A "가정 | 확인 시점" 열("낙상 이벤트는 민감정보로 취급 | 법무", "에스컬레이션 기본 타이머 45/90/180/300초 | 파일럿")
- 자문자답에 대안·이유·영향 3단: "Q3 … 대안: 자체 센서 개발(TI IWR6843 기반), 단일 벤더 종속 / 선택 이유: 하드웨어 개발은 12개월+ / 영향: 센서별 이벤트 포맷 정규화가 엣지의 핵심 책임"
- 다만 출처가 문장 옆이 아니라 부록으로 분리: "요양시설 낙상 사고는 최근 5년간 약 3배 증가했다 [확정]"에 인라인 링크 없음(부록 C 16건에서 역추적해야 함)
- ADR이 근거 없이 상태만: "ADR-001 | 감지는 센서 내장, 우리는 운영 계층 | 채택 [가정]"

**판정: doc1** — 두 문서 모두 가정 표기 규율은 훌륭하나, doc1은 주장 단위 URL·확인일과 결정별 폐기 대안(32건)까지 붙어 근거 추적 비용이 더 낮다.

## [6. 범위 절제]

**doc1 근거 인용**
- 만들 것을 넷으로 축소: "**우리가 만드는 것은** ①알림 상태기계·에스컬레이션 정책, ②직원 확인 앱, ③보호자 통보·이력·평가 리포트, ④시설별 온프레미스 게이트웨이 형상 — 이 넷뿐이다"
- 과설계를 명시적으로 기각: "#D-019 클라우드 = NestJS 모듈러 모놀리스 1개 … 3인·1시설에 서비스 3개는 과설계", "Kafka/NATS … 시설당 <1만 이벤트/일에 과잉 | YAGNI", "핫 스탠바이 이중화는 파일럿 규모에 과잉"
- 반면 프로세스 메타가 상당한 비중: 55항목 블라인드스팟 전수 마킹표(대부분 Assumed), 준비도 리포트, 결정 로그 32건, 단계별 참고자료 사용 기록 — 구현자가 읽어야 할 분량이 doc2의 2배 가까이

**doc2 근거 인용**
- 만들 것을 운영 계층으로 한정: "D3 센서 내장 감지 + 우리가 만드는 것은 알림·에스컬레이션·운영 워크플로우 … 제품이 죽는 이유는 오탐 피로와 알림 미응답이지 감지율이 아님"
- 위험 통제를 기능이 아닌 운영 모드로: "F-13 섀도 모드(알림 없이 기록만) | P0 | 파일럿 첫 4주 튜닝용", "ADR-008 게이트웨이 이중화 | 보류 → P2"
- 반대로 파일럿 단계에 과한 목표·구성: "확장성 | 시설 **300곳 × 100센서 = 30,000 센서 heartbeat/분** 처리"(M2는 시설 1~2곳·20~40침상), "`services`(ECS Fargate: api, event-engine, notifier, ws-gateway)" + Cognito + ElastiCache + IoT Core + ChirpStack + 벤더 2종 어댑터 + 스테이션 패널 + 보호자 웹을 MVP 10주에 배치

**판정: tie** — doc1은 빌드 표면·런타임을 최소화했지만 문서 자체에 프로세스 장식이 붙었고, doc2는 본문이 간결하고 섀도 모드로 위험을 줄였지만 파일럿에 불필요한 300시설 규모 목표와 4개 서비스·관리형 컴포넌트를 얹어 서로 다른 방향으로 과잉이 있다.

## 종합 판정: doc1

doc1은 요구사항·불변식·API 계약·스키마·시나리오가 서로 ID로 연결되고 누락 0을 자체 검증하므로, 다음 담당자가 재설계 없이 첫 커밋을 시작할 수 있다. doc2는 도메인 통찰(오탐 피로·다인실 식별 불가·섀도 모드)과 M0 검증·사업모델·페르소나에서 더 나은 기획 문서지만, 엔드포인트 계약·오류·런북 본문·RTO/RPO가 비어 있어 구현 착수 시점에 결정이 다시 필요하다. 여섯 차원 중 다섯에서 doc1이 앞서고 범위 절제만 무승부다.
