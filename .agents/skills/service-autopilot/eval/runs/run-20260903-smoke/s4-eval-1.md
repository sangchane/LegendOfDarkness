# 심사 결과 — doc1(PiCam Hub) vs doc2(PiCam Watch)

seed: 「라즈베리파이로 IP 카메라를 제어하고 실시간 모니터링하는 서비스를 만들고 싶다」

---

## [1. 완전성]

**doc1 근거**
- 사용자·스토리: 「P1 소상공인 사장(카페/매장) … P2 홈랩/스마트홈 사용자 … P3 소규모 사무실 관리자」 + US-1~11(각 수용 기준 1줄).
- 보안: 「5.3 STRIDE 분석」이 위협 16건을 시나리오·심각도·대응으로 나열, 「5.4 보안 기본값 체크리스트」 8항목.
- API/데이터: §6.2 엔드포인트 표 30여 행 + §6.4 WebSocket 이벤트 5종 + §6.5 MediaMTX 연동 규약 + §7 ERD 12엔티티·인덱스·`audit_log`는 트리거로 UPDATE/DELETE 금지.
- 테스트/운영: §9.2 카메라 시뮬레이터 스택(`ffmpeg -re -stream_loop -1 … -c copy -f rtsp`), 카오스·HIL 72h 소크, §10.4 Ansible 롤 8종, §10.7 운영 런북 6행.
- 다만 **엣지케이스 전용 절이 없다** — 「US-8 … 사용률 85% 도달 시 가장 오래된 세그먼트부터 삭제, 80% 미만까지」처럼 스토리·요구사항 안에 흩어져 있고, SLI/SLO·RTO/RPO·복원 리허설·하드웨어 BOM 항목은 부재.

**doc2 근거**
- 엣지케이스를 독립 절로 전수화: 「E-8 | 이벤트 | 클립 진행 중(t=0 시작) | t=15s, t=25s에 모션 | 이벤트 1건, 클립 종료 = t=45s(마지막 모션 + 20s), 사각지대 없음」 등 E-1~E-16.
- 위협모델을 **경계 × STRIDE 6범주 행렬**로 전수 마킹하고 빈칸에도 근거를 남김: 「해당없음 — DTLS 인증서 지문·ICE ufrag/pwd가 인증된 시그널링으로만 전달됨」, 처리도 Mitigate/Accept/Transfer로 분류.
- 운영: SLI/SLO 5개(「보존 준수 | 만료 후 1h 내 purged 비율 | 100%(법정 — 예외적으로 100%)」), 장애 표에 RTO/RPO(「4h / **24h(외부 USB 정상 시), USB 미장착·고장 시 복구 불능**」), RB-1~7 런북, 분기 1회 복원 리허설, 준비도 체크리스트 9항목.
- 반면 화면 목록은 4개뿐이고, 브랜드별 RTSP 템플릿·용어집·컴포넌트별 성능 예산은 없다.

**판정: doc2** — 루브릭이 지목한 6영역 중 엣지케이스·보안위협·테스트 계획·운영/장애 대응 네 곳에서 doc2가 전수 커버를 명시적으로 수행하고, doc1이 비운 SLO·RTO/RPO·엣지케이스 카탈로그를 채운다.

## [2. 비모호성]

**doc1 근거**
- 표기 규칙 자체는 우수(「**[확정]** … **[가정]** … **[미확정]**」)하나, **가정 표의 ID 열이 깨져 있다** — 「| 단계 | 대상 사용자는 …」이 A1~A7 자리에 반복되어, 「가정이 바뀌면 "영향" 열의 섹션을 재검토한다」는 참조 규약이 실제로는 따라갈 수 없다.
- 미확정이 문서 전반에 남음: 「MediaMTX 버전별 키 이름 변경 가능 → 설치 시 버전 핀 고정 `[미확정: 핀 버전은 M0에서 결정]`」, 「삭제는 … `[미확정: 삭제 경로 최종 결정은 M2]`」, §12.2 오픈 이슈 6건.
- 검증 불가 표현: 「액티브 쿨러·SSD 권장을 설치 마법사에서 **강제 수준으로 안내**」, 「원격 접근 UX가 VPN 설치에 의존 → **가이드 품질이 중요**」.

**doc2 근거**
- 요구사항이 EARS + 수치로 고정: 「FR-007 | Owner가 PTZ 패드를 누르고 있는 동안, 클라이언트는 750ms 주기로 이동 요청을 갱신하고 시스템은 ContinuousMove(Timeout=1s)를 보내며, 키를 떼면 100ms 내 Stop을 보내야 한다」, 「FR-024 | Stop 전송 후 1.5초 내 응답이 없으면 … Stop을 3회 재전송하고 실패 시 카메라를 ptz_fault로 표시」.
- 「## 미결정 — 0건」을 선언하고 그 근거까지 기재: 「리뷰어가 미결정으로 지목한 4건 … 은 각각 FR-028·non-goal·FR-014·INV-4 Assumed로 결정했다」.
- 반대로 문서 간 모순을 자백한다: 「D1 | HIGH | 03은 Tailscale/FR-020을 P2로 두는데 04·07은 MagicDNS origin·Tailscale 설치를 MVP 필수 절차로 둠 — MVP 시청 origin 모순」 외 HIGH 7건.

**판정: doc2** — 문장 단위 정밀도(수치·주어·EARS)와 미결정 0 선언이 doc1의 [미확정] 6건·깨진 가정 ID·"강제 수준으로 안내" 류 표현을 앞서며, doc2의 모순은 D1~D7로 위치·수정안까지 특정되어 있어 해석 여지가 남지 않는다.

## [3. 검증가능성]

**doc1 근거**
- KPI 표는 목표+측정법을 갖춤: 「라이브 지연(LAN, WebRTC) | ≤ 1.0 s (glass-to-glass) | 타임스탬프 화면 촬영 비교」, 「녹화 누락률 | ≤ 0.1 % (분 단위 갭 기준) | 세그먼트 인덱스 갭 분석」.
- 릴리스 게이트도 pass/fail: 「- [ ] 신규 Pi에서 설치 스크립트 → 첫 라이브까지 5분 이내(스톱워치)」 외 4항목.
- 그러나 **FR-01~20·NFR-01~12에 대응하는 수용 테스트가 없다**. §9.3은 레벨별 "주요 케이스"를 서술할 뿐 요구사항 ID와 연결되지 않아, 어느 요구사항이 어느 테스트로 닫히는지 문서만으로는 알 수 없다.

**doc2 근거**
- SC-001~014 전부가 「기준 | 측정 방법 | 게이트」 3열: 「SC-005 | PTZ 100회 → 감사로그 100건, 누락 0, 해시 체인 검증 통과 | DB 카운트 + `picam audit verify` | MVP」, 「SC-014 … MVP(mock) / P1 게이트(실카메라)」로 게이트까지 분리.
- 06이 SC/FR/E를 전부 Gherkin·레이어·목킹으로 변환하고 계수를 자기 검산: 「누락 확인(ID 전수 대조): SC-001…014 = 15/15 · P0 FR 17건 17/17 · P1 FR 9건 9/9 · E-1~E-16 16/16. **누락 0.**」
- 「각 시나리오는 처음엔 **반드시 실패(RED)** 해야 한다 — 컴파일/실행되어 의도한 이유로 실패한 것만 RED로 인정」.
- 약점도 스스로 표기: 「D5 | SC-014 "초과 ≤ 5°"가 메커니즘 … 에서 도출되지 않음」.

**판정: doc2** — doc1의 KPI는 제품 지표 7개에 그치는 반면 doc2는 요구사항·엣지케이스·성공기준 전부를 pass/fail 시나리오로 사상하고 ID 전수 대조까지 붙였다.

## [4. 실행가능성]

**doc1 근거**
- 착수 순서가 검증과 함께 명시된 유일한 문서: 「부록 E … 1. 리포 골격(monorepo: apps/hub-api, apps/hub-web, deploy/ansible, …) → 검증: CI lint/test 통과 … 4. 스트림 JWT + JWKS + MediaMTX jwt 인증 → 검증: aiortc WHEP 클라이언트 프레임 수신」.
- 외부 컴포넌트 연동 규약이 키 단위로 구체: 「`authMethod: jwt`, `authJWTJWKS: http://127.0.0.1:8000/api/v1/internal/jwks`, 클레임 `mediamtx_permissions: [{"action":"read","path":"cam_front"}]`」, 「`recordPath: /data/recordings/%path/%Y-%m-%d_%H-%M-%S-%f`」.
- 다만 요구사항→엔드포인트→테스트 사상이 없고, 「MediaMTX 버전 핀」·「삭제 경로」가 M0/M2로 미뤄져 구현자가 되짚어야 한다.

**doc2 근거**
- 요구사항이 담당 엔드포인트까지 전수 매핑: 「FR-027 | P1 | CAM-5 `ptz_limits`·`home_preset_token`, PTZ-1 409 `ptz-out-of-range` + `ptz.denied-range` 감사, PTZ-4 범위 검사, CAM-7 `position_status`」, 「P0·P1 매핑 0건: **없음**」.
- 계약이 스키마 수준까지: OpenAPI 스케치(`pan/tilt/zoom minimum: -1, maximum: 1`), 「`CREATE TRIGGER audit_log_immutable BEFORE UPDATE ON audit_log BEGIN SELECT RAISE(ABORT,'append-only'); END;`」, PRAGMA(「감사 커넥션 `synchronous=FULL`」), compose 다이제스트 고정·UID 3종·nftables 「443/tcp(→ `redirect to :8443`)」.
- 반대로 착수를 스스로 막는 문장이 있다: 「그중 4건 … 은 **결정 수정 없이는 MVP 착수 불가**다」 — 다만 「D7 자격증명 재입력 엔드포인트 + FR-030」처럼 수정안이 이미 처방되어 있다.

**판정: doc2** — doc1의 첫 작업 순서가 더 친절하지만, 기능 하나를 실제로 코딩할 때 필요한 스코프·에러코드·스키마·수용 시나리오가 doc2에는 전부 붙어 있고 D1~D7도 수정안까지 확정돼 있어 남는 판단이 더 적다.

## [5. 근거성]

**doc1 근거**
- 가정을 표로 고정하고 **파급까지 적은 점이 강점**: 「가정이 틀리면 영향 | B2B 관제라면 §4.8 멀티사이트·§5 RBAC 강화 필요」, 「8대 초과면 다중 Pi 또는 x86 미니PC 검토」.
- 기술 선택마다 기각 사유: 「미디어 코어 | **MediaMTX** | … | go2rtc(녹화·플레이백 없음, 별도 ffmpeg 세그먼터 필요) / ffmpeg 직접(시그널링·재생 서버를 직접 작성해야 함)」, ADR-001~007.
- 다만 출처가 **URL·확인일 없는 서술형**: 「부록 D … Raspberry Pi 포럼 "RPi5 Codec confusion" … Jeff Geerling "Can the Raspberry Pi 5 handle 4K?", Frigate Discussion #18431」. 성능 예산 근거는 「Go 패스스루 벤치 **경험치**」.

**doc2 근거**
- 근거 유형을 3단으로 분리하고 URL+확인일을 붙임: 「표기: **[사실]** 출처 직접 확인 · **[2차]** … · **[추론]**」, 「**[사실] 개인정보보호법 제25조 … ** ([법령정보센터 제25조](…) · [찾기쉬운 생활법령](…), 확인 2026-09-03)」, 「Pi 5는 H.265 HW 디코드만, **H.264 HW 인코더 없음** [사실: [Pi 포럼](…), [HN](…)]」.
- 법정 수치와 자체 가정을 분리: 「보존기간 상한 90일(**Assumed** — 가이드라인 "필요 최소기간" 요구에 따라 무기한 보존을 막는 운영 상한, **법정 수치 아님**)」.
- 결정 42건이 「결정 — 이유 / 버린 대안 — 이유」 형식으로 로그화: 「#2 … go2rtc 채택 … / MediaMTX 기각 — ONVIF 디스커버리 부재」, 리뷰 지적의 거짓 양성도 사유와 함께 분류(「C5(일부) … 거짓 양성 | 제25조⑦은 반출 금지가 아님」).

**판정: doc2** — 두 문서 모두 대안 기각 사유를 달았으나, 출처 URL·확인일·근거 등급과 "법정 vs 가정"의 분리까지 갖춘 쪽은 doc2뿐이다.

## [6. 범위 절제]

**doc1 근거**
- 단일 문서로 끝내고 제외 목록을 명시: 「**MVP 제외 (Later)** - 클라우드 릴레이/계정, 네이티브 앱, 푸시 알림 인프라 - AI 객체 검출 … - 다중 사이트 통합 관제, 멀티테넌트」.
- 그러나 MVP 자체가 seed("제어 + 실시간 모니터링")를 넘어 완전한 NVR로 확장된다: 「연속 녹화(fMP4 세그먼트), 타임라인 재생, 클립 내보내기(MP4)」, 9분할 그리드, 8채널, 「관측 스택(옵션 프로파일) | node_exporter, Prometheus, Grafana, (Loki+promtail)」, Ansible 롤 8종, 브랜드 호환성 매트릭스 6종.

**doc2 근거**
- 배제를 수치로 정당화: 「B | 24/7 상시 녹화 | 4대 × 2Mbps ≈ 86GB/일 → 30일 2.6TB. NAS 필수」 → non-goal, 「메트릭 | `/health/details` + SQLite 롤업 | Prometheus `/metrics` | 외부 수집기는 non-goal」, 「"80%+ 일률 커버리지"는 리스크 기반 목표로 대체」.
- 기능을 옵션으로 남기지 않고 제거: 「오디오 | 기능 부재(Eliminate) | 경고 후 Owner 활성 옵션 | … 옵션은 코드 경로를 남김」.
- 반대로 설계가 아닌 **프로세스 기록의 비중이 크다**: 02 레지스터 36항목의 무응답 질문지 5문항, 08 「검토 이력」·「1차 검토(리뷰어 B·C) 지적 처리표」·거짓 양성 필터, decision-log 42건 + 「참고자료 사용 기록」. 1~4대 규모 대비 「감사로그 1년 아카이브 … 트리거 2개 DROP → DELETE … → 트리거 재생성」, 「체인 앵커 HMAC(master.key 파생)」 등은 과중한 면이 있다.

**판정: tie** — doc1은 단일 산출물로 군더더기가 적은 대신 제품 표면(24/7 녹화·타임라인·Grafana 프로파일)을 seed 밖으로 넓혔고, doc2는 시스템 범위를 수치 근거로 좁힌 대신 설계가 아닌 프로세스·리뷰 기록을 다량 실어 두 과잉이 상쇄된다.

## 종합 판정: doc2

doc2는 요구사항(FR 29)·엣지케이스(E 16)·성공기준(SC 15)을 서로 사상하고 ID 단위로 전수 대조까지 마쳐, "무엇을 만들고 무엇으로 통과를 판정하는가"가 문서 안에서 닫혀 있다. doc1도 단일 문서로 아키텍처·API·ERD·IaC·착수 순서를 잘 갖췄지만 요구사항→테스트 연결이 없고 [미확정] 6건과 깨진 가정 ID가 남아 구현자가 되짚을 지점이 더 많다. 다만 범위 절제는 서로 다른 방향(doc1은 제품 표면 확장, doc2는 프로세스 기록 비대)으로 어긋나 무승부이며, doc2를 채택하더라도 스스로 밝힌 D1~D7을 먼저 반영해야 한다.
