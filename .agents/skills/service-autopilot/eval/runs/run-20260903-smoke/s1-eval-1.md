# 심사 결과 — s1 (doc1 vs doc2)

- 심사 대상: `s1-judge-1.md` 내 `<doc1>` (단일 기획·설계 문서, §0~§19 + 부록) vs `<doc2>` (Seed→Recon→블라인드스팟→PRD→아키텍처→API/ERD→테스트→운영→준비도→Decision Log 패키지)
- seed: "사내 회의실 예약을 웹에서 하고 싶다. 지금은 화이트보드에 수기로 적는다."
- 판정일: 2026-09-03

## 1. 완전성

**doc1 근거**
- 보안: §14 STRIDE 표 18행, 각 행에 대응 + **잔여 위험** 열. `"I | 민감 회의 제목 노출 | 인사 정보 유출 | 비공개 옵션(R11), 목록·상세·리포트·알림 모두 마스킹 | 예약자가 비공개를 안 켜는 경우"`
- 엣지·테스트: §15.2 `T1~T48` 매트릭스(겹침 기하 T2~T10, 경계 접촉 T7·T8, 취소분 제외 T9·T24, 자기 자신 갱신 T28, KST 날짜 경계 T43)
- 운영: §16.2 compose·Caddyfile·`.env.example` 전문, §16.4 관측성, 알림 규칙 5종, §16.5 런북 5행, §17.4 `"30분 이상 서비스 불능이면 ... 임시로 화이트보드/구두 조율"`
- doc2에 **없는** 영역: §8 화면 S1~S8 + 모바일 레이아웃 + §8.7 접근성(`role="gridcell"`, 화살표 키 이동, 명도 대비 4.5:1), §17 이관·출시(초기 데이터 입력·D-3/D+0/D+14 커뮤니케이션), §18 W1~W6 로드맵, §9.2 **전 테이블** DDL

**doc2 근거**
- 보안: 위협모델 4단계 — ① DFD + trust boundary 4개 ② `자산/경계 6행 × STRIDE 6범주 = 36셀`(해당없음 셀에도 전부 사유 기재: `"해당없음(불투명 ID, 서버 조회)"`) ③ 대응표에 Mitigate/Transfer/Accept/**Eliminate** 분류 ④ `"충분한가 — 상위 리스크 3 재검토"`
- 운영: SLI/SLO 5개, 4 골든 시그널 계측 위치, `"알람:런북 = 1:1, 증상 기반"` + 평가 주체 명시(`alert-check.sh` 1분 cron), 장애 시나리오 5건 RTO/RPO, 백업(age 암호화·오프사이트·**월 1회 복원 리허설**), `RB-02` 런북 전문(메타→트리거→진단→해결→에스컬레이션→검증→롤백), 준비도 체크리스트
- 추적성: 05 `"커버리지 매핑 (P0·P1 요구사항 → 엔드포인트/잡) — 매핑 0건 = 결함 ... P0·P1 매핑 누락: 0건"`, 06 `"누락 확인: SC 8/8 · P0/P1 FR 15/15 · EC 22/22 → 누락 0"`
- doc1에 **없는** 영역: 01-recon의 Adopt/Extend/Build 판정, 개인정보 보존·파기·익명화 정책(FR-015 + RetentionJob)

**판정: doc2** — 열거된 여섯 영역을 양쪽 모두 채우지만, 보안위협(36셀 전수 + 사유 기재)과 운영/장애(런북·복원 리허설·알람 주체)에서 doc2가 한 단계 깊고 유일하게 요구사항→엔드포인트→테스트 전수 매핑으로 누락 0을 스스로 증명한다. 다만 doc1의 화면·접근성·이관 계획이 doc2엔 통째로 없어 격차는 좁다.

## 2. 비모호성

**doc1 근거**
- §7 R1~R14: 규칙마다 기본값 + 에러 코드(`TIME_NOT_ALIGNED`, `DURATION_OUT_OF_RANGE`, `OVERLAP`(409), `USER_QUOTA_EXCEEDED`)
- 검사 순서까지 확정: `"규칙 우선순위: 인증 → 권한 → 형식(R1) → 값 범위(R2~R5, R7) → 회의실 상태 → 겹침(R6, DB). 앞 단계에서 실패하면 뒤를 검사하지 않는다."` → T12에서 코드 충돌을 `"정렬 먼저 검사 → 전자"`로 해소
- §1 A1~A14 각 가정에 `근거` + `틀렸을 때 영향` 열
- 잔여 모호: §11.1 스택 비교의 `"상 / 중 / 상"` 정성 등급(등급 정의 없음), §19.2 발주자 확인 9건(단, 전부 `현재 가정` 병기)

**doc2 근거**
- FR-001~015 전부 EARS 형식 — `"예약 요청을 받으면, 시스템은 (a) 시작·종료가 15분 경계 (b) 시작 < 종료 (c) 길이 ≤ 240분 ... 을 모두 검증하고 위반 시 422와 위반 항목을 반환해야 한다"` (주어·트리거·결과 모두 명시)
- `"## 미결정 — **0건.**"`, 08 정합성 표 `"측정 불가 표현(03 FR/SC) | 0건"`
- 잔여 모호: 본문 전반에 미해소 토큰 — `"Capability ((참고자료) 재진술)"`, `"((참고자료) Mode 1 — "왜"의 검증)"`, `"/(문서) 로 다음을 실행"`. 어떤 표준·문서를 인용하는지 독자가 알 수 없다
- 자체 고지된 잠재 드리프트: `"패치는 1회 적용됐으나 재검토를 돌리지 않았다 ... 새 드리프트를 만들지 않았는지는 자체 확인뿐이다"`

**판정: tie** — 요구사항 표면의 수치·에러코드는 양쪽 다 확정적이다. doc2는 EARS·미결정 0건으로 앞서지만 미해소 인용 토큰과 자체 신고한 드리프트 위험이 이를 상쇄하고, doc1은 자기완결적이나 정성 등급이 남는다.

## 3. 검증가능성

**doc1 근거**
- §3 G1~G6 전부 `지표 / 목표치 / 측정 방법` 3열 — `"G2 더블부킹 0 | 동일 회의실·시간 겹침 건수 | 0건 | DB 제약 위반 시 409 카운트 + 월간 감사 쿼리"`
- T1~T48 각 케이스에 입력·기대 상태코드·에러코드. 특히 `"T26 동시 경쟁 | 같은 슬롯 50개 병렬 POST | 정확히 1건 201, 49건 409, DB confirmed 1행"`
- 출시 게이트 명문화: §12.5 `"이 테스트가 통과하지 않으면 출시하지 않는다."`, §15.4 k6 `"조회 p95 < 300ms, 생성 p95 < 500ms, 5xx 0건, 409는 허용"`

**doc2 근거**
- SC-001~008 전부 `측정 방법 / 목표` — `"SC-001 | 겹치는 confirmed 예약 0건 | 같은 방·겹치는 구간 100 동시 요청 부하 테스트 후 DB 조회 | confirmed ≤ 1 (pass)"`
- TS-001~059 Gherkin + **레이어 지정**(U/I/C/E) + 데이터/목킹 열
- 주관적 기준을 자동 판정으로 환원: SC-008(막다른 에러 0) → `"TS-007 ... 모든 에러 컴포넌트에 data-testid="recovery-action" 버튼이 존재"`
- CI 게이트 정의: `"전체 라인 커버리지는 보고만 하고 게이트로 쓰지 않는다. 게이트 = 위 표의 시나리오 100% + RED→GREEN 이력."`

**판정: doc2 (근소)** — 케이스 단위 pass/fail 판정력은 대등하나(오히려 겹침 기하는 doc1이 더 조밀), 기준→시나리오 전수 매핑과 명시적 CI 게이트를 갖춘 쪽은 doc2뿐이다. 실제로 doc1은 F12(사용률 리포트)의 산식 검증 케이스가 T1~T48에 없다.

- 스키마가 그대로 실행 가능: §9.2에 `users / rooms / reservations / reservation_events / notifications / settings` **전 테이블** DDL + 인덱스 + `INSERT INTO settings` 시드 10행

**doc2 근거**
- 계약 정밀도: EP-01~19 표에 엔드포인트별 에러 slug 전부(`409 booking-overlap` / `422 policy-violation` / `409 booking-not-editable` ...), OpenAPI 3.1 스케치, 컴포넌트 분해(`AuthService·PolicyValidator·BookingService·AdminService·AuditWriter·OutboxWriter·NotificationWorker·RetentionJob`)

  - 일정·주차 계획 없음
  - 문서 자신의 판정이 `"## 판정: **CONCERNS**"`이고, 핸드오프가 `"착수 전 확인 2가지: (a) 회사가 M365/Google Workspace 캘린더를 쓰는가 → 쓰면 중단·설정 경로, (b) 03↔05↔06 교차 대조 ... 드리프트 0 확인"` 을 **첫 작업**으로 요구한다

**판정: doc1** — 다음 담당자가 추가 설계 없이 월요일에 W1을 시작할 수 있는 쪽은 doc1이다. doc2는 착수 전에 전제 검증과 문서 간 정합성 대조를 먼저 하라고 스스로 지시한다.

## 5. 근거성

**doc1 근거**
- 가정 라벨링은 우수: §1 표에 `가정값 / 근거 / 틀렸을 때 영향` — `"A13 개발 스택 익숙도 | TypeScript 가능 인력 있음 | 미확인 | Java/.NET 팀이면 §11 스택 옵션 B로 교체. API·ERD·규칙은 스택 무관"`
- 기술 선택에 트레이드오프: §11.1 A/B/C 6기준 비교 + `"선택: A. ... A13이 틀리면 B로 교체하되, §7 규칙·§9 ERD·§10 API는 그대로 쓴다"`, ADR-1~9(결정/대안/이유), §12.3 비-PostgreSQL 대안(`FOR UPDATE` 직렬화)
- 약점 ①: 출처 0건. §5.1 `"Google Calendar 리소스 예약, Microsoft Exchange 룸 메일박스, Robin, Joan, Envoy Rooms, Skedda 등에서 공통적으로 나타나는 구성 요소"`, §5.2 D3 노쇼, A5 `"상용 제품의 일반 기본값"` — 전부 무출처 단정
- 약점 ②: 자기 가정을 끝까지 따라가지 않음. A3에서 `"Google Workspace 또는 Microsoft 365 중 하나 사용"` 을 가정해 놓고, 그 플랫폼의 회의실 자원 예약으로 대체 가능한지는 문서 전체에서 한 번도 묻지 않는다

**doc2 근거**
- 증거 경계 4분류를 문장 단위로 적용 + URL·확인일: `learn.microsoft.com/exchange/recipients/room-mailboxes (확인 2026-09-03)`, `support.google.com/a/answer/9025584`, `postgresql.org/docs/current/rangetypes.html`, `rfc-editor.org/rfc/rfc9457`, `endoflife.date/nodejs`, `martinfowler.com/articles/practical-test-pyramid.html`, `sre.google/sre-book/monitoring-distributed-systems/`
- 출처 품질 자체를 고지: `"두 글 모두 15분을 OWASP 권고로 인용 — OWASP 원문은 미확인, 근거는 독립 블로그 2건 교차."`
- 기각 근거까지 기록: `"대안 Prisma는 EXCLUDE·range를 스키마로 표현 못 해 동일하게 raw SQL이 필요하고 타입 생성 단계가 하나 더 있어 기각"`, `"검토한 대안"` 8행, DL-001~009(결정/이유/버린 대안/영향)
- 프로젝트 자체를 의심: `"조직이 M365 또는 Google Workspace를 이미 쓰고 있다면 → Adopt(설정). 구축 자체가 불필요."` → 08 잔여 리스크 1순위 + `"IT에 「Outlook/Google 캘린더로 회의실 초대가 되나요?」 한 줄 질문"`

**판정: doc2** — 가정 라벨링은 대등하지만, 사실 주장에 검증 가능한 출처·확인일이 붙고 출처 품질까지 고지하며 "만들지 않는 선택지"를 근거와 함께 남긴 쪽은 doc2뿐이다. doc1은 A3에서 이미 Workspace/M365 보유를 가정하고도 그 함의를 검토하지 않은 논리적 공백이 있다.

## 6. 범위 절제

**doc1 근거**
- MoSCoW로 MVP를 12항목에 묶고 Won't 명시: `"좌석 예약, 방문자 관리, 다지점, 비용 청구, 네이티브 앱."`
- 규모 대비 기각을 반복: ADR-3 `"서버 1대 Docker Compose ↔ Kubernetes, 서버리스 | 사용자 ≤ 200, 운영자 1인. 복잡도 대비 이득 없음"`, ADR-8 `"30초 폴링 ↔ WebSocket/SSE | 100명 규모에서 실시간 푸시 불필요. 인프라 단순"`, ADR-2 반복 예약 제외, `"스케줄러: 앱 내 setInterval 워커 ... 단일 인스턴스이므로 외부 큐 불필요"`
- 인력 축소 시나리오까지: `"1인 개발이면 W4의 리포트·필터·주간 뷰를 Phase 1.5로 미룬다."`
- 과잉 후보: F12 사용률 리포트를 MVP에 포함, §12.3 비-PostgreSQL 대안(스택 확정 후엔 불용 분기)

**doc2 근거**
- 절제한 사례: `"CalendarAdapter 포트 선제 정의 | 구현 없는 인터페이스 = 투기적 설계 | P2 착수 시 도입해도 비용 동일"`, 페이지네이션을 `"EP-16(감사 로그)·EP-17(사용자 목록)에만 적용"`, 스코프는 `"문서 표기용이다 — 저장·검사는 app_user.role 2값으로만"`
- 그러나 자체 적대적 검토가 과설계를 지적하고 **부분 반영**에 그침: `"#15 MEDIUM | 05 — 규모 대비 과설계(Idempotency-Key·커서 페이지네이션·미디어타입 버저닝·스코프 체계) | **부분 반영** ... Idempotency-Key·버저닝 규약은 유지(템플릿 규약)"`
- 유지된 기제: 응답 본문을 저장하는 `IDEMPOTENCY_KEY` 테이블, `application/vnd.roombook.v2+json` 버저닝, 컨테이너 4개(caddy·app·worker·db), 전용 파기 롤 `roombook_retention` + `RETENTION_DATABASE_URL`, outbox `priority`·`claimed_at`·SKIP LOCKED·2분 회수, `alert-check.sh` 상태 파일 중복 억제
- 구현에 쓰이지 않는 공정 잔여물: `"## 단계별 스킬 사용 기록"` 20행, 무응답 질문 배치 Q1~Q5 전문, GATE 지적 처리 표 15행
