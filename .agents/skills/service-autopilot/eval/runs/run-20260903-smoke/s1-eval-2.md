# 심사 결과 — 사내 회의실 웹 예약 설계 문서 비교 (doc1 vs doc2)

- 심사일: 2026-09-03
- 대상: `s1-judge-2.md` 의 `<doc1>`(RoomBook 다단계 패키지) / `<doc2>`(s1-a 단일 설계 문서)
- 시드: "사내 회의실 예약을 웹에서 하고 싶다. 지금은 화이트보드에 수기로 적는다."
- 심사 원칙: 길이가 아니라 "구현 착수에 필요한 정보의 밀도". 두 문서는 분량이 거의 같으므로(각 ~1,300줄) 길이 자체는 변별력이 없다.

## [1. 완전성]

**doc1 근거**

- 위협모델이 자산 × 범주 전수다: "STRIDE 셀 | 36/36 검토, '해당없음'에 전부 이유 기재, ②→③ 미대응 위협 0". DFD에 신뢰경계 4개(TB1~TB4)를 그리고, 대응을 Mitigate/Transfer/Accept/Eliminate로 분류한 뒤 "④ 충분한가 — 상위 리스크 3 재검토"까지 닫는다.
- 운영/장애가 가장 두껍다: SLI/SLO 4개(가용성·예약 확정 지연·메일 도착·정확성), 4 골든 시그널 계측 표, "모든 알람은 조치 가능, 알람:런북 = 1:1, 증상 기반", 장애 시나리오 5건에 RTO/RPO 개별 부여(앱 크래시 30분/0, DB 다운 4h/24h), RB-02 런북 전문(진단 명령·해결·에스컬레이션·검증·롤백), 준비도 체크리스트.
- 규제·보존을 실제 설계로 반영한다: "**[사실] 개인정보보호법(국내)**: 직원 이름·이메일·예약 이력은 개인정보. 최소 수집, 목적 달성 시 지체 없는 파기" → FR-015 "90일 후 이름·이메일을 익명화" + 파기 전용 롤 `roombook_retention`.
- 요구사항 커버리지를 수치로 닫는다: "P0·P1 매핑 누락: **0건**", "누락 확인: SC 8/8 · P0/P1 FR 15/15 · EC 22/22 → **누락 0**".
- 빠진 영역(실재): 화면 설계가 없다. UI 절은 "dial = VISUAL_DENSITY **6** · MOTION_INTENSITY **3** · DESIGN_VARIANCE **3**"와 UX-01~05 지표뿐 — 와이어프레임·화면 목록·접근성 요구가 0건이다. 일정/로드맵 없음, 화이트보드 기존 예약 이관 절차 없음. FR-008이 Room에 "수용 인원·설비 태그"를 저장하지만 이를 소비하는 요구사항이 없어 사실상 미사용 필드다.

**doc2 근거**

- 사용자 정의가 더 두껍다: 페르소나 3인에 "대표 질문"과 "빈도"(주 1~5회 등)를 붙이고, US-1~US-13 각각에 인수 기준을 단다.
- doc1에 통째로 없는 영역을 채운다: §8 화면 설계(S1 데스크톱/모바일 타임라인, S2 모달, S4, 관리자 화면 목업), §8.7 접근성 체크리스트("그리드 셀은 `role=gridcell`, 화살표 키로 이동, Enter로 예약 시작"), §17 이관·출시 계획(초기 데이터 이관·주차별 단계·커뮤니케이션), §18 6주 로드맵, 부록 B 사용자 안내문 초안.
- 도메인 함정 D1~D9를 별도 절로 정리한다(경계 접촉 오판, 반복 예약 예외 복잡성, KST 날짜 경계 버그, 민감 제목 노출, 화이트보드 관성).
- 빠진 영역(실재): 개인정보보호법·보유기간·파기 언급이 문서 전체에 0건이다. 오히려 "퇴사자 계정 비활성화 시 예약 이력은 유지(익명화 안 함 — 감사 목적)"로 무기한 보관을 택하면서 법적 근거를 대지 않는다. 운영 쪽은 런북 5행·알림 규칙 5개 수준으로 얕고 SLO·RTO/RPO 정의가 없다.

**판정: doc1** — 차원이 열거한 6영역(사용자·엣지케이스·보안위협·API/데이터·테스트·운영/장애) 안에서는 doc1이 보안위협·운영/장애·규제에서 확연히 깊고 요구사항 커버리지를 수치로 닫은 반면 doc2의 우위(화면·접근성·이관·로드맵)는 대부분 열거 밖 영역이다 — 다만 UI 중심 제품에서 doc1의 화면 설계 0은 실재하는 결손이다.

## [2. 비모호성]

**doc1 근거**

- 미결정을 명시적으로 0으로 닫는다: "## 미결정 — **0건.** (Q1~Q5는 추천안을 Assumed(무응답)로 채택 — 잔여 리스크는 08에 기록)", 그리고 "측정 불가 표현(03 FR/SC) | 0건".
- 원래 모호했던 지점을 지목해 제거한 이력이 남아 있다: "HIGH | 03 '오늘' vs 04/05 '24h' — 대안 슬롯 탐색 창 불일치 | **반영** — '요청 start_at 이후 당일 운영시간 종료까지 전방 탐색'으로 통일"; "HIGH | 05 EP-09/10 vs 06 TS-053 — 에러 slug 드리프트 | **반영** — TS-053 두 단언 분리, EC-C6 slug 병기".
- 서로 모순되던 두 규칙을 실제로 화해시킨다: 감사 로그 append-only(INV-3)와 1년 파기가 동시에 참일 수 없다는 지적에 "앱 DB 계정에 booking_audit UPDATE/DELETE 권한 없음(INV-3)… 파기는 별도 롤 `roombook_retention`만 수행"으로 확정.
- 잔존 모호성(자기 신고): "패치는 1회 적용됐으나 **재검토를 돌리지 않았다**… 패치가 새 드리프트를 만들지 않았는지는 자체 확인뿐이다."

**doc2 근거**

- 규칙표 R1~R14가 값·기본값·에러 코드를 한 줄에 묶어 모호성이 거의 없다: "R2 | 길이: `min_minutes ≤ end − start ≤ max_minutes` | 15분 / 240분 | `DURATION_OUT_OF_RANGE`". 검사 순서까지 못박는다: "인증 → 권한 → 형식(R1) → 값 범위(R2~R5, R7) → 회의실 상태 → 겹침(R6, DB). 앞 단계에서 실패하면 뒤를 검사하지 않는다."
- 애매할 수 있는 케이스를 괄호로 즉시 확정한다: "T12 | 최소 길이 미만 | `14:00~14:10` | 422 `TIME_NOT_ALIGNED` 또는 `DURATION_OUT_OF_RANGE` (정렬 먼저 검사 → 전자)".
- 반면 미결정이 명시적으로 남는다: §19.2 "발주자 확인이 필요한 항목 (현재는 가정으로 진행)" Q1~Q9. 각각 현재 가정과 확인 시점이 달려 있어 착수는 가능하나, 열린 항목 수 자체는 doc1(0건)보다 많다.
- "선택"으로 남긴 결정들: 멱등성 "`Idempotency-Key` 헤더 선택", "`/metrics` | Prometheus 형식 (선택, 사내망 IP만 허용)", "Sentry 등은 선택", "Auth.js 같은 라이브러리는 선택 사항". 목표 하나는 목표치가 비어 있다: "G5 | 노쇼 회수 (Phase 1.5) | … | 측정 후 기준선 설정".

**판정: doc1** — 두 문서 모두 수치·에러코드 수준까지 구체적이지만 doc1은 미결정 0건에 더해 문서 간 드리프트를 지목해 제거한 이력이 있고, doc2는 발주자 확인 9건과 다수의 "선택" 항목을 남겼다(다만 doc2의 잔여 모호성은 전부 기본값이 붙어 있어 격차는 작다).

## [3. 검증가능성]

**doc1 근거**

- SC-001~008 전부 측정 방법과 목표가 붙은 pass/fail이다: "SC-001 | 겹치는 `confirmed` 예약 0건 | 같은 방·겹치는 구간 100 동시 요청 부하 테스트 후 DB 조회 | confirmed ≤ 1 (pass)". 예외 조건까지 넣어 반증 가능하게 만든다: "SC-007 | 근무시간(평일 07~22 KST) 월 가용성 ≥ 99.5% (≈ 월 허용 다운 100분; 계획 배포는 근무시간 외로 제외)".
- **추적 폐쇄**가 이 차원의 결정타다: SC/FR/EC가 전부 TS-ID로 매핑되고 그 개수를 센다 — "누락 확인: SC 8/8 · P0/P1 FR 15/15 · EC 22/22 → **누락 0**", "P0·P1 매핑 누락: **0건**".
- 게이트 정의도 검증 가능하다: "전체 라인 커버리지는 보고만 하고 게이트로 쓰지 않는다. 게이트 = 위 표의 시나리오 100% + RED→GREEN 이력." 자동화 불가 항목은 정직하게 배제한다: "TS-004 | SC-004·005 | (운영 지표 — 자동 테스트 대상 아님) 파일럿 4주 후 총무 점검표로 판정".
- 계약 테스트를 별도 표로 명세한다(멱등 키 재요청 시 최초 응답 재생, `X-Requested-With` 없는 POST → 403, 61번째 요청 → 429, 본문 `role:"admin"` 주입 무시).

**doc2 근거**

- T1~T48 매트릭스가 입력/기대를 구체 시각으로 못박아 그대로 실행 가능하다: "T7 | 경계 접촉 (뒤) | `11:00~12:00` | 201", "T24 | 상한 계산에 취소 제외 | 활성 9 + 취소 5, 10번째 | 201", "T43 | KST 날짜 경계 | `date=2026-09-07` 조회, UTC로는 09-06 23:00 시작 예약 | 09-07 목록에 포함".
- 출시 게이트를 단일 테스트로 명문화한다: "**T26** | **동시 경쟁** | 같은 슬롯 50개 병렬 POST | **정확히 1건 201, 49건 409, DB confirmed 1행**" + "이 테스트가 통과하지 않으면 출시하지 않는다."
- 주차별 완료 기준이 검증문이다: "W2 | … | **T26 동시성 테스트 통과**", "W4 | … | axe critical 0, k6 기준 통과", "W6 | … | 출시 후 3일 5xx 0건".
- 약점: Must 목록 대비 테스트가 비어 있다. F7(내 예약 목록)과 F12(사용률 리포트)에 대응하는 케이스가 T1~T48에도 E2E E1~E5에도 없다. doc1과 달리 "요구사항 → 테스트" 누락 카운트를 하지 않아 이 공백이 문서 안에서 드러나지 않는다.

**판정: doc1** — 케이스 개별 구체성은 doc2의 T-매트릭스가 대등하거나 더 낫지만, doc1만이 SC/FR/EC→테스트 매핑을 전수로 세어 "누락 0"을 증명했고 doc2는 자기 Must 중 F7·F12가 무테스트로 남는다.

## [4. 실행가능성]

**doc1 근거**

- 백엔드는 그대로 코딩 가능한 수준이다: 19개 엔드포인트 표(에러 slug·권한 포함), OpenAPI 스케치, ERD 9엔티티, DDL에 `EXCLUDE USING gist (room_id WITH =, period WITH &&) WHERE (status = 'confirmed')` + 권한 회수(`REVOKE UPDATE, DELETE, TRUNCATE ON booking_audit FROM roombook_app`) + 큐 클레임 SQL(`FOR UPDATE SKIP LOCKED`) + 매직링크 원자 소비 SQL을 실물 쿼리로 제시한다.
- 시퀀스 다이어그램 3종(매직링크 로그인·동시 충돌·조기 반납)과 컴포넌트 다이어그램으로 호출 경로가 확정된다.
- 핸드오프 블록이 다음 담당자의 첫 작업을 지정한다: "SPEC.md 작성 — … 착수 전 확인 2가지: (a) 회사가 M365/Google Workspace 캘린더를 쓰는가 → 쓰면 중단·설정 경로, (b) 03↔05↔06 교차 대조(FR-ID·에러 slug·정책 숫자·상태값)로 GATE 패치 후 드리프트 0 확인".
- 착수 마찰(실재): (a) 화면 설계가 없어 이 제품의 핵심 UX인 타임라인 그리드를 구현자가 처음부터 발명해야 한다. (b) 위 핸드오프가 선행 확인 2건과 문서 간 교차 대조를 착수 전 과제로 부과한다. (c) 최종 판정이 "## 판정: **CONCERNS**"이며 일정·이관 계획이 없다.

**doc2 근거**

- 화면을 그려 준다: S1 데스크톱 타임라인 목업(범례 "████ 예약됨 / ▒▒▒▒ 비공개 / ┃ 현재 시각(빨간 세로선) / 회색 = 운영시간 외"), 모바일 <768px 세로 타임라인, S2 예약 모달 목업. 동작 규칙까지 붙는다: "빈 칸 클릭 → 그 시각부터 기본 1시간으로 S2 열림", "409 응답은 모달을 닫지 않고 충돌 예약 정보를 보여준다", "30초마다 자동 새로고침(폴링). 실시간 푸시는 하지 않는다".
- 코드 배치를 지정한다: §11.3 `app/(pages)/…` · `api/v1/…/route.ts`(얇게) · `src/domain/reservation/rules.ts`(R1~R14 순수 함수)/`service.ts`(트랜잭션 경계)/`repo.ts` · `workers/` · `lib/time.ts` + 원칙 "**규칙은 순수 함수**, **트랜잭션은 서비스 한 곳**, **라우트는 얇게**".
- 환경을 즉시 세울 수 있다: `.env.example` 전문(`SESSION_SECRET= # 32바이트 랜덤, openssl rand -hex 32` 포함), Caddyfile 전문, compose(백업 컨테이너 포함), settings 초기값 INSERT 10행, 테스트 시드("회의실 5개(정원 4/6/8/12/20), 사용자 3명(employee 2, admin 1), 이번 주 예약 20건(비공개 3건 포함)").
- 일정이 있다: §18 W1~W6 주차별 산출물·검증 + "1인 개발이면 W4의 리포트·필터·주간 뷰를 Phase 1.5로 미룬다".
- 착수 마찰: 스택 세부에 신선도 오류가 있다 — "프레임워크 | Next.js 15 (App Router), Node 22 LTS". 2026-09 시점 기준 Node 22는 유지보수 단계이며, 이는 doc1이 출처(endoflife.date)와 함께 지적하고 Node 24로 정정한 항목이다.

**판정: doc2** — "이 문서만 들고 바로 착수"라는 기준에서 화면 목업·디렉터리 구조·`.env.example`·시드 데이터·주차별 계획은 doc1에 전혀 없는 착수 자산이고, doc1은 UI를 백지로 남긴 채 착수 전 선행 확인 2건을 부과한다.

## [5. 근거성]

**doc1 근거**

- 증거 경계를 라벨로 강제하고 URL·확인일을 붙인다: "**[사실]** 출처 있는 사실 · **[입력]** 사용자 제공 · **[추론]** 사실에서 도출 · **[추천]** 판단". 실제로 M365 room mailbox, Google Workspace 자원 캘린더, 고스트 미팅 30~45%(myseat.io·deskbird), 개인정보보호법(privacy.go.kr), RFC 9457, Stripe 멱등성, PostgreSQL rangetypes, martinfowler 테스트 피라미드, SRE book, outplane 백업 가이드가 전부 "(확인 2026-09-03)"과 함께 달려 있다.
- 자기 인용을 스스로 강등한다: "두 글 모두 15분을 OWASP 권고로 인용 — OWASP 원문은 미확인, 근거는 독립 블로그 2건 교차."
- 근거 없는 선택은 근거 없음을 표기한다: "커모디티 도구(대체 가능, 근거 생략을 명시): Caddy(TLS 종단), age(백업 암호화), gitleaks(비밀 스캔), Mailpit(개발용 SMTP), k6(부하 테스트)".
- 버전·라이브러리 선택에 출처가 붙는다: "런타임 **Node.js 24**(Active LTS, EOL 2028-04-30; Node 22는 2026-09 현재 Maintenance) — https://endoflife.date/nodejs", "EXCLUDE 제약은 Drizzle 스키마 DSL이 아직 미지원(기능 요청 …/issues/3388)이므로 `drizzle-kit generate --custom`으로 만든 SQL 마이그레이션에 기술한다".
- 대안 비교가 가격·라이선스까지 간다: MRBS(GPLv2, v1.12.2)·Cal.com(AGPLv3)·Skedda($99~199/월)·Robin($4~6/자원/월) 표 + "**[추천] search-first 판정 (Adopt / Extend / Build)** … 조직이 M365 또는 Google Workspace를 이미 쓰고 있다면 → Adopt(설정). 구축 자체가 불필요."
- 가정 관리: 31항목 레지스터(Clear/Partial/Missing + 근거·출처) + 잔여 리스크 표에 "틀리면"과 "확인 방법 (5분)" 열. 결정 기록 DL-001~009는 Nygard 형식(결정/이유/버린 대안/영향)이고, 독립 검토 8건·적대적 검토 15건의 채택/부분채택/보류 사유가 남는다.

**doc2 근거**

- 가정 표 A1~A14의 구조는 우수하다 — "가정값 / 근거 / 틀렸을 때 영향"을 열로 두고 파급까지 적는다: "A13이 틀리면 §11 스택 옵션 B로 교체. API·ERD·규칙은 스택 무관".
- ADR-1~9에 대안과 이유가 붙는다: "ADR-8 | 30초 폴링 | WebSocket/SSE | 100명 규모에서 실시간 푸시 불필요. 인프라 단순". 스택은 A/B/C 3안 비교표 후 선택하고 "A13이 틀리면 B로 교체하되 §7 규칙·§9 ERD·§10 API는 그대로 쓴다"로 교체 비용까지 밝힌다.
- 그러나 외부 근거가 사실상 없다: §5.1은 "Google Calendar 리소스 예약, Microsoft Exchange 룸 메일박스, Robin, Joan, Envoy Rooms, Skedda 등에서 공통적으로 나타나는 구성 요소"라고만 하고 URL·확인일·가격이 0건이다.
- 핵심 가정의 근거가 일반화에 그친다: "A3 | … Google Workspace 또는 Microsoft 365 중 하나 사용 | 근거: 대다수 국내 중소·중견 기업", "A5 | 15분 단위, 최소 15분, 최대 4시간, 최대 30일 전 예약 | 근거: 상용 제품의 일반 기본값". doc1은 같은 항목을 M365 `BookingWindowInDays`/`MaximumDurationInMinutes` 기본값 문서와 대조한 뒤 자기 값(60일·4시간)은 "사내 보수값으로 Assumed"라고 표기한다.
- 그리고 A3이 참일 때의 귀결을 다루지 않는다 — M365/Google을 이미 쓴다고 가정하면서 그 제품에 이미 있는 회의실 자원 예약을 왜 안 쓰는지는 검토하지 않는다. doc1은 같은 조건을 Go/No-go로 승격했다: "**Go — 단, 조직이 M365/Google Workspace 캘린더를 이미 쓴다면 No-go(설정으로 해결)**".

**판정: doc1** — 가정을 가정으로 표기하는 규율은 양쪽이 비슷하지만, doc1만이 사실 주장에 출처·확인일을 달고 과잉 인용을 스스로 강등하며 버전·ORM·상용 대안을 근거로 판정한 반면 doc2의 도메인 조사·정책 기본값·핵심 가정 A3은 무출처 일반화에 머문다.

## [6. 범위 절제]

**doc1 근거**

- 절제의 최상급 사례로, 만들지 않는 선택지를 1순위 잔여 리스크로 남긴다: "**조직이 M365/Google Workspace를 쓰면 이 패키지는 폐기** — room mailbox/자원 캘린더 설정으로 끝난다".
- 투기적 추상화를 명시적으로 철회한다: "CalendarAdapter는 FR-018 착수 시 도입한다 — 지금 포트를 미리 만들지 않는다(YAGNI, DL-008)". 유계 목록에 페이지네이션을 붙이지 않고("주간 그리드(창 ≤8일·회의실 ≤30)·내 예약은 유계라 페이지네이션 없음"), HA·Prometheus·라인 커버리지 게이트를 각각 이유와 함께 거절한다.
- 반대로 자기 문서가 과설계 지적을 미해소로 남긴다: "MEDIUM | 05 — 규모 대비 과설계(Idempotency-Key·커서 페이지네이션·미디어타입 버저닝·스코프 체계) | **부분 반영**". 그 결과 런타임 의미가 없는 표기 체계가 남았다: "**스코프는 문서 표기용이다** — 저장·검사는 `app_user.role` 2값(member/admin)으로만 하며 별도 스코프 저장소·토큰 클레임은 만들지 않는다."
- 분량의 상당 부분이 구현자가 소비하지 않는 프로세스 기록이다: "## 단계별 스킬 사용 기록 — [A0] 스킬 없음 … [A1] (참고자료) — 증거 경계 4분류를 …", GATE 지적 15행 표, 08 준비도 리포트. 설계 내용이 아니라 생성 과정의 기록이다.

**doc2 근거**

- MoSCoW로 단계를 자르고 Won't를 명시한다: "**Won't (이번 릴리스)** 좌석 예약, 방문객 관리, 다지점, 비용 청구, 네이티브 앱." Phase 1.5/2 분리도 일관된다: "ADR-3 | 서버 1대 Docker Compose | Kubernetes, 서버리스 | 사용자 ≤ 200, 운영자 1인. 복잡도 대비 이득 없음", "ADR-2 | 반복 예약 MVP 제외 | RRULE 저장 + 전개 | 예외 처리 복잡도가 MVP 6주에 맞지 않음".
- 규모에 맞춰 프로토콜을 가볍게 잡는다: 멱등성은 필수가 아닌 "선택", 폴링으로 WebSocket 회피, "메모리 기반 토큰 버킷(단일 인스턴스 가정 A7)".
- 인력에 따라 범위를 줄이는 다이얼이 있다: "1인 개발이면 W4의 리포트·필터·주간 뷰를 Phase 1.5로 미룬다."
- 반대로 MVP 기능면이 doc1보다 넓다: Must에 F8 비공개 예약, F12 사용률 리포트, F9의 관리자 설정 화면이 모두 들어가고 settings 키가 10개다(`slot_minutes`·`min/max_minutes`·`max_advance_days`·`business_days`·`business_open/close`·`user_active_quota`·`checkin_grace_minutes`·`checkin_enabled`). 화이트보드 대체라는 원 요구에 비해 리포트와 전 규칙 설정화는 초과이며 "요청하지 않은 설정화"에 해당한다.
- 이미 PostgreSQL을 확정하고도 §12.3 "대안 (PostgreSQL이 아닐 때)"로 MySQL/SQL Server 행 잠금 레시피를 싣는다(짧지만 채택되지 않은 경로의 내용).

**판정: tie** — doc1은 "안 만드는 선택"과 투기적 포트 제거라는 최상급 절제를 보이면서도 스스로 인정한 프로토콜 과설계와 프로세스 메타 기록을 남겼고, doc2는 페이지 밀도가 높고 단계 분할이 깔끔한 대신 MVP에 리포트·전면 설정화를 밀어 넣었다 — 초과의 종류가 다를 뿐 크기는 대등하다.

## 종합 판정: doc1

1. 두 문서는 분량이 거의 같아 승부가 밀도에서 갈렸는데, doc1은 사실 주장마다 출처와 확인일을 붙이고(그리고 과잉 인용을 스스로 강등하고) SC/FR/EC→테스트 매핑을 "누락 0"으로 닫았으며 미결정을 0건으로 확정한 반면, doc2의 도메인 조사·핵심 가정 A3·정책 기본값은 무출처 일반화에 머물고 자기 Must인 F7·F12는 대응 테스트 없이 남는다.
2. doc2는 화면 목업·접근성 체크리스트·디렉터리 구조·`.env.example`·주차별 로드맵이라는, doc1에 아예 없는 착수 자산으로 실행가능성 차원을 분명히 이겼고, 타임라인 그리드가 이 제품의 핵심 UX인 만큼 doc1의 화면 설계 부재는 실제로 치러야 할 비용이다.
3. 그럼에도 doc1이 이기는 결정적 지점은 "조직이 M365/Google을 쓰면 이 패키지는 폐기"라는 Go/No-go를 1순위로 세운 반면 doc2는 바로 그 플랫폼이 있다고 가정(A3)하면서도 이미 존재하는 회의실 자원 예약을 왜 안 쓰는지 끝내 묻지 않았다는 것이며, 여기에 개인정보보호법 기반 보존·파기 설계와 감사 로그 권한 분리까지 더하면 완전성·비모호성·검증가능성·근거성 네 차원의 우위가 실행가능성 한 차원의 열위를 넘어선다.
