# Seed — 요양시설 낙상 감지·알림 서비스 (가칭: FallGuard)

- 원문: 요양시설 어르신 낙상을 감지해 보호자와 직원에게 알리는 서비스를 만들고 싶다.
- 서비스 유형: 복합 — IoT·엣지(침실·복도 감지 장치, 온프레미스 추론) + 관제(직원 즉시 대응·대시보드) + 모바일(보호자·직원 앱 알림) + 웹 SaaS(다시설 관리·설정) + AI(센서/영상 기반 낙상 판정 모델 — LLM 아님)
- 주 도메인 / 인접 도메인: 노인 장기요양기관(요양원·노인요양시설) 안전 관제 / 헬스케어 IoT · 영상·민감정보 프라이버시 · 의료기기 규제 경계 · 대량 알림 메시징(푸시·SMS·알림톡)
- 감지된 제약:
  - 안전: 낙상 = 부상·사망 직결. 미감지(FN)가 오탐(FP)보다 비싸지만, 오탐 폭주는 직원의 알람 피로 → 진짜 알람 무시로 이어짐
  - 민감정보: 입소자 건강·영상 정보(개인정보보호법상 민감정보) + 요양시설 CCTV 관련 법정 의무(A1에서 확인)
  - 수신자 2군: 직원(내부·초 단위 대응) / 보호자(외부·사실 확인 후 통보) — 요구 지연·내용·채널이 다르다
  - 하드웨어/엣지: 감지 장치가 시설에 설치됨 (전원·네트워크·유지보수 부담)
- 로드할 블라인드스팟 프로파일: P1(IoT·엣지) + P2(웹 SaaS) + P3(관제·알람 폭주) + P4(모바일) + 임시 프로파일 PX(요양시설 낙상 감지 — 프로파일 없는 도메인 절차)
- 강도: full — 사유: 사용자 지정(`full`). 신호 표로도 full — 안전·민감정보·법(CCTV·개인정보) · 외부 연동 2개 이상(푸시·SMS/알림톡·장기요양 기록) · 하드웨어/엣지 · 다시설 확장 시 데이터 볼륨. 단, 감지 수단(플랫폼)이 미확정이라 spike 신호도 있다 → 사용자 지정을 우선하되 A2 질문 1칸(Q1)을 이 리스크에 예약한다.
- 해석한 것 (사용자가 말하지 않았는데 내가 정한 것 — 틀리면 비싼 순, 전부 Assumed):
  1. **감지 수단**: 비접촉 센서(밀리미터파 레이더 또는 카메라+온디바이스 비전) 우선, 웨어러블은 보조. 근거 — 인지저하 어르신은 웨어러블 착용 유지가 어렵다(A1에서 확인). 틀리면 하드웨어 재구매 → Q1
  2. **대상 시설**: 국내 장기요양기관(노인요양시설·요양원). 요양병원(의료법·의료기관)은 범위 밖 — 규제 체계가 다르다
  3. **사업 형태**: 우리가 서비스 공급자, 시설이 B2B 고객(구독), 보호자·입소자는 최종 사용자. 시설 1곳 파일럿(≤100침상) → 다시설 SaaS 확장 가능한 구조
  4. **알림 흐름**: 감지 → 직원 즉시 알림(앱 푸시+관제 화면) → 직원이 현장 확인·조치 → 보호자에게는 **확인된 낙상만** 통보(오탐이 보호자에게 직접 가지 않게). 직원 미응답 시 에스컬레이션
  5. **"감지"의 뜻**: 실시간 자동 감지(사후 영상 확인 아님). 감지→직원 알림 지연 상한을 성공 기준으로 둔다
  6. **보호자 채널**: 모바일 앱 푸시 + 앱 미설치·미수신 시 SMS/카카오 알림톡 폴백
  7. **규제 해석**: 낙상 감지·알림 SW는 진단·치료 목적이 아니므로 의료기기가 아니다 — A1에서 식약처 기준으로 확인, 미확인이면 register에 Assumed로 남기고 위험 표시
  8. **영상 취급**: 카메라를 쓰더라도 원본 영상은 장치 밖으로 상시 전송하지 않는다(온디바이스 추론, 이벤트 클립만 선택 저장). CCTV 법정 의무와의 관계는 A1에서 확인
- 기존 시스템: 없음 (신규)
