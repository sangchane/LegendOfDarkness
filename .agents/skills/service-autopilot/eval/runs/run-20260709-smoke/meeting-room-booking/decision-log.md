# Decision Log - 사내 회의실 웹 예약

## DL-001 - MVP 외부 캘린더 연동 제외

- 결정: Microsoft/Google Calendar 양방향 동기화는 P2로 둔다.
- 이유: 현재 문제는 화이트보드 수기 운영이며, 첫 가치는 중복 예약 차단과 전사 가시성이다. 외부 캘린더 연동은 조직이 Microsoft 365인지 Google Workspace인지에 따라 구현과 권한 모델이 달라진다.
- 버린 대안: MVP에서 M365/Google Calendar를 필수 연동.
- 영향: API와 아키텍처에 Calendar Adapter를 P2로만 남겼다.

## DL-002 - 예약 상세 기본 비공개

- 결정: 기본 목록은 free/busy를 제공하고, 제목/참석자는 예약자·참석자·관리자에게만 보인다.
- 이유: 회의 제목과 참석자는 업무상 민감한 정보일 수 있다. Google Calendar resource 권한도 free/busy와 상세 보기를 구분한다.
- 버린 대안: 모든 직원에게 모든 제목 공개.
- 영향: FR-009, API masked response, STRIDE 정보 노출 완화책에 반영했다.

## DL-003 - 승인 정책은 제한 회의실에만 적용

- 결정: 일반 회의실은 즉시 예약, 제한 회의실은 관리자 승인 가능 정책을 둔다.
- 이유: 화이트보드보다 느려지면 도입 실패 가능성이 크다. 다만 임원실/대형 회의실처럼 희소 자원은 승인 정책이 필요하다.
- 버린 대안: 모든 예약 관리자 승인.
- 영향: BookingPolicy.approval_required와 pending_approval 상태를 추가했다.

## DL-004 - 체크인과 자동 해제는 P1

- 결정: 체크인/미체크인 자동 해제를 MVP P1에 포함한다.
- 이유: Envoy 등 유사 제품이 체크인 알림과 공간 회수를 핵심 기능으로 제공하며, 수기 화이트보드에서 흔한 노쇼 문제를 줄인다.
- 버린 대안: 노쇼 관리를 운영자 수동 처리로 둔다.
- 영향: EP-009, CheckInReleaseJob, SC-005, 운영 알림에 반영했다.

## DL-005 - 반복 예약은 제한된 주간 반복만 P1

- 결정: 매주 같은 요일/시간 반복 예약은 P1로 두고, 복잡한 RRULE 전체 지원은 P2로 둔다.
- 이유: 팀 정기회의에는 반복 예약이 필요하지만, 예외일/복합 규칙까지 구현하면 초기 복잡도가 커진다.
- 버린 대안: 반복 예약 전면 제외 또는 RRULE 전체 지원.
- 영향: recurrence_rule은 단순 문자열/JSON 후보로 두고, 테스트는 주간 반복과 충돌 검증부터 시작한다.
