# Blindspot Register - 사내 회의실 웹 예약

스캔 범위: 공통 10축 + STRIDE 6범주 + P2 SaaS

## 공통 10축

| 축/항목 | 상태 | 처리 | 근거·출처 |
|---|---|---|---|
| 1. 기능 범위 | Assumed | MVP는 회의실 목록/가용 시간 조회/예약/변경/취소/관리자 회의실 관리/이력으로 제한 | Seed, Microsoft/Google 리소스 예약 모델 |
| 2. 도메인 데이터 모델 | Assumed | Room, Booking, BookingAttendee, BookingAudit, BookingPolicy를 핵심 엔티티로 채택 | M365 room mailbox, Google Calendar resource |
| 3. UX 흐름 | Assumed | 주간/일간 타임라인 + 조건 필터 + 빠른 예약 모달 | 화이트보드 대체에는 한눈에 보는 시간표가 필요 |
| 4. 비기능 목표 | Assumed | 월~금 업무시간 기준 p95 조회 800ms 이하, 예약 생성 p95 1.5s 이하, 월 가용성 99.5% | 내부 업무 시스템 초기 SLO-lite |
| 5. 통합/외부 의존성 | Assumed | MVP 외부 캘린더 연동 없음, CSV 내보내기만 제공 | 도입 속도 우선, 연동은 P2 |
| 6. 엣지케이스/실패 처리 | Assumed | 중복 예약은 DB 제약+트랜잭션으로 차단, 동시 요청은 409 반환 | 예약 시스템 핵심 무결성 |
| 7. 제약/트레이드오프 | Assumed | 사내망/온프레미스 배포 가능 구조, 단일 조직/다중 지점 확장 가능 | 사용자 입력과 일반 사내 도구 운영 제약 |
| 8. 용어/일관성 | Assumed | 회의실=Room, 예약=Booking, 예약자=Organizer, 참석자=Attendee | Microsoft/Google 리소스 모델과 일치 |
| 9. 완료 신호 | Assumed | 중복 예약 0건, 관리자 수기 조정 없이 직원이 직접 예약 완료 | 화이트보드 대체 성공조건 |
| 10. 비용/라이선스 | Assumed | 오픈소스/기존 사내 인프라 우선, 유료 SaaS 의존 없음 | 온프레미스 및 폐쇄망 가능성 |

## P2 SaaS 항목

| 항목 | 상태 | 처리 | 근거·출처 |
|---|---|---|---|
| 테넌시 | Clear | 단일 사내 조직 기본, tenant_id는 미래 확장을 위해 선택 컬럼으로만 검토 | 입력이 사내 단일 용도 |
| 인증 | Assumed | 사내 계정 로그인 필수, 관리자/일반 사용자 권한 분리 | 내부 일정 정보 보호 |
| 결제/구독 | Clear | 해당 없음 | 사내 내부 시스템 |
| 백업/DR | Assumed | 일 1회 DB 백업, 분기 1회 복구 리허설 | 업무 예약 데이터 보존 |
| 개인정보 | Assumed | 예약자/참석자/회의 제목 보관, 제목 공개 범위 설정 | Google resource 권한의 free/busy 구분 |
| 이메일 알림 | Assumed | MVP는 앱 내 알림/브라우저 알림 또는 이메일 선택, 실패 재시도 3회 | 예약 변경 인지 필요 |

## STRIDE 스캔

| 자산/경계 | S | T | R | I | D | E | 처리 |
|---|---|---|---|---|---|---|---|
| 로그인 사용자 -> 예약 API | 위조 세션 가능 | 요청 파라미터 변조 | 예약 부인 | 타인 예약 상세 노출 | 반복 요청 폭주 | role 변조 | JWT/세션 검증, 서버 권한 검사, 감사 로그, rate limit |
| 예약 API -> DB | 서비스 계정 오남용 | SQL/데이터 변조 | 변경자 추적 실패 | DB 덤프 노출 | 잠금 경합 | 관리자 권한 남용 | 파라미터 바인딩, 트랜잭션, 최소 권한, 백업 암호화 |
| 관리자 UI -> 정책 관리 | 관리자 사칭 | 운영시간/권한 정책 변조 | 정책 변경 부인 | 전체 예약 상세 노출 | 잘못된 정책으로 예약 불가 | 일반 사용자의 관리자 API 호출 | admin 권한, audit log, 변경 전후값 저장 |
| 알림 발송 | 발신자 위조 | 알림 내용 변조 | 발송 여부 분쟁 | 회의명 노출 | 대량 알림 | 알림 API 권한 상승 | 알림 최소 정보, 재시도 제한, 발송 로그 |

## 질문 배치(자동 채택)

사용자 요청에 따라 질문하지 않고 추천안을 자동 채택했다.

| 질문 후보 | 추천 채택 | 이유 | decision-log |
|---|---|---|---|
| 외부 캘린더 연동을 MVP에 넣을까? | 아니오, P2로 둔다 | 화이트보드 대체의 첫 가치는 중복 예약 차단과 가시성이다. M365/Google 연동은 조직 환경 의존성이 크다. | DL-001 |
| 회의 제목을 전 직원에게 공개할까? | 기본은 free/busy, 상세는 예약자/참석자/관리자만 | 회의명은 업무상 민감할 수 있다. | DL-002 |
| 예약 승인 워크플로가 필요한가? | 일반 회의실은 즉시 예약, 제한 회의실만 관리자 승인 | 수기 화이트보드보다 빨라야 하며 고가/임원 회의실은 통제가 필요하다. | DL-003 |
| 노쇼 처리는 MVP인가? | 체크인+자동 해제는 P1에 포함 | Envoy 등 유사 제품이 체크인/공간 낭비 감소를 핵심으로 제공한다. | DL-004 |
| 반복 예약을 MVP에 넣을까? | 주간 반복만 P1, 복잡한 RRULE은 P2 | 실사용 빈도는 높지만 복잡도를 제한해야 한다. | DL-005 |

## 반영 기록

- DL-001은 PRD 범위 밖, API 계약의 externalCalendarSync를 P2로 반영.
- DL-002는 PRD 개인정보 요구사항, API 응답 필드 마스킹, STRIDE 완화책에 반영.
- DL-003은 BookingPolicy와 approvalStatus 모델에 반영.
- DL-004는 check-in 엔드포인트, 자동 해제 배치, 테스트 설계에 반영.
- DL-005는 recurrenceRule 단순 모델과 P2 non-goal에 반영.
