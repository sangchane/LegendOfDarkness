# 심사 결과 — s8 (요양시설 낙상 감지·알림 서비스) · doc1 vs doc2

심사일: 2026-09-07 · 심사관: 설계 문서 심사관 · 기준: 구현 착수에 필요한 정보의 밀도(길이 아님)

---

## [1. 완전성]

**doc1 근거 인용**
- API·데이터: HTTP `E-01`~`E-32`, MQTT `M-01 fallguard/{device_id}/fall (QoS 1)`~`M-03`, 내부 잡 `J-01 escalate(event_id, level)`~`J-09 ops-alarm`, 그리고 실제 DDL — `CREATE UNIQUE INDEX fall_events_one_active_per_device ON fall_events (device_id) WHERE status IN ('detected','notified','acked');`
- 추적성: "매핑 0건 P0/P1 요구사항: 없음" (FR-001~029 → 담당 엔드포인트/잡 전건 매핑표)
- 보안: "STRIDE 전수 (경계 6 × 범주 6)" — TM-01~TM-28 각각에 Eliminate/Mitigate/Accept 대응
- 운영: `AL-01`~`AL-09` + "전부 조치 가능, 알람:런북 = 1:1", 장애 시나리오 7종 + RTO/RPO 표, 백업·복원 리허설, `.env.example` 21키, "첫 작업 3개 — 워킹 스켈레톤"
- 테스트: `TS-001`~`TS-065` + "누락 검사: SC-001~SC-012 전부 ≥1 시나리오"

**doc2 근거 인용**
- "§9.3 감지 품질 검증 프로토콜" — 실험실 시나리오별 반복 횟수(전방/후방/측방 각 20, 느린 낙상 20, ADL 침대 눕기 30 …)와 "채택 기준: 민감도 ≥ 95%, 느린 낙상 ≥ 85%, ADL 오탐 ≤ 3%"
- "F-06 시설 내 로컬 알림 (스테이션 패널·사이렌), 클라우드 불통 시 동작 | P0 | 안전 요구", "F-13 섀도 모드 | P0", "F-09 동의 관리 … 미동의 침상 센서 비활성 | P0 | 법적 요건"
- §8.6 인가 매트릭스(역할 5 × 리소스 6), §9.5 보안 테스트 + "파일럿 전 외부 침투 테스트 1회", §9.6 사용성 테스트(SUS ≥ 70), §10.5 런북 10종 목록
- 다만 DDL·OpenAPI·컨테이너 정의는 없고, F-01~F-19에는 개별 수용 기준이 붙지 않는다.

**판정: doc1** — 여섯 영역을 둘 다 건드리지만, API·데이터·테스트·운영에서 doc1은 실행 가능한 산출물(DDL·엔드포인트 표·65개 시나리오·9개 알람+런북 골격)까지 내려가는 반면 doc2는 목록·원칙 수준에서 멈춘다.

## [2. 비모호성]

**doc1 근거 인용**
- 상수 단일 출처: "04~07은 이 이름으로만 참조하고 값을 다시 쓰지 않는다" + 47개 상수 각각에 근거 열 — `ACK_TIMEOUT | 3 | 분 | 야간 1~2인이 생활실까지 이동·확인하는 시간 가정(A-6)`
- 요구사항은 EARS 문장 고정: "EARS 패턴('~할 때, 시스템은 ~해야 한다'). 상한·기간·임계는 상수 표의 이름으로만 쓴다."
- "## 미결정 — 0건", 자기 점검 "03~07에 `미정·TBD·추후·(선택)` 0건", 용어집 15항목에 코드명 병기
- 흠결: 엣지케이스 ID가 "EC-단계"로 5건 중복돼 `TS-025 · EC-단계`, `TS-029 · EC-단계`가 어느 케이스를 가리키는지 문서만으로 특정되지 않고, 핸드오프 절에 "`/(문서) 로 다음을 실행`" 같은 해소 불가 참조가 남아 있다.

**doc2 근거 인용**
- 타이머·임계가 구체 수치: "S2 | T0+45s 미응답 | 같은 층 전 직원", "동일 센서·60초 내 재감지는 같은 이벤트로 병합(중복 알림 금지)", "종결 후 15분 내 … 유예 창"
- 라벨 체계: "모든 주장은 [확정] / [가정] / [미확정] 으로 구분한다."
- 흠결: "11.3 오픈 이슈 [미확정]" 7건(채택 센서 모델, 가격, 식약처 판정, 레이더의 영상정보처리기기 해당 여부, 단말 OS, 게이트웨이 이중화 시점, 화장실 설치 기준)이 열린 채 남고, 스택 표에 "필요 시 Wi-Fi/PoE", "Wi-Fi/이더넷 계열 1종", 오프라인 요구에 "시설 내 Wi-Fi 푸시(가능 시)" 같은 조건부 표현이 있다. 또 "## 7. 위협 모델·개인정보 설계"와 "## 7. 데이터 모델 (ERD)"이 같은 절 번호를 쓴다.

**판정: doc1** — 값 재기입 금지 + 상수 단일 출처 + 미결정 0으로 해석 여지를 구조적으로 제거한 쪽이며, doc1의 중복 EC-ID 결함을 감안해도 doc2의 미확정 7건·조건부 표현보다 덜 모호하다.

## [3. 검증가능성]

**doc1 근거 인용**
- SC-001~SC-012 전부에 '측정 방법' 열: "SC-003 | 푸시 실패를 주입했을 때 `CHANNEL_FALLBACK_DELAY` 안에 SMS 폴백 발송 100% | 통합 테스트(FCM 어댑터 실패 목킹)", "SC-011 | 감사 로그 행의 UPDATE/DELETE 시도가 DB 제약으로 100% 거부 | DB 통합 테스트"
- 실데이터로만 판정되는 기준을 "운영 검증" 레이어로 분리: "파일럿 실데이터로만 판정 가능한 SC(001·004·005·009·012)는 '운영 검증' 레이어로 분리하고 07 대시보드 쿼리·리허설에 연결 / 대안: 자동 테스트로 위장"
- 0·100% 목표 거부: `DETECTION_RECALL_MIN | 90 | % | 파일럿 대사 기준. 미탐 0은 SLO로 부적절(SRE)`, `API_AVAILABILITY | 99.9 … 100% 금지(SRE)`

**doc2 근거 인용**
- §1 성공 지표가 pass/fail: "낙상 발생 → 직원 단말 알림 도착 P95 ≤ 30초", "오탐 ≤ 1건 / 침상 / 주", "직원이 '알림을 끄고 싶다'고 답한 비율 < 20%"
- §9.4 장애 주입 표에 '합격' 열: "인터넷 단절 … 10초 내 패널·사이렌 … 복구 후 5분 내 이벤트 동기화, 유실 0", "푸시 실패 … 30초 내 SMS 폴백, Notification에 fallback_of 기록"
- 흠결: "파일럿 기간 미감지 낙상 0건", "섀도 기간 시설 보고 낙상 중 미감지 0" 같은 0 목표가 SLO로 들어가 있고, F-01~F-19 어디에도 수용 기준이 붙지 않으며 요구사항↔테스트 추적표가 없다(§9.2는 8개 남짓의 단위 시나리오 나열).

**판정: doc1** — doc2의 §9.3 감지 품질 프로토콜은 단일 항목으로는 더 날카롭지만, 요구사항 전건에 수용 기준·시나리오 ID를 붙이고 누락 검사까지 수행해 pass/fail 판정을 문서 전체에 강제한 쪽은 doc1이다.

## [4. 실행가능성]

**doc1 근거 인용**
- 실제 SQL: RLS 정책(`ALTER TABLE fall_events FORCE ROW LEVEL SECURITY; CREATE POLICY tenant_isolation …`), 부트스트랩 `SECURITY DEFINER` 함수 4개, audit_log 불변 트리거(`RAISE EXCEPTION 'audit_log is append-only'`)
- 배포 자산: `infra/compose/docker-compose.yml` 스케치(edge/api/worker/mosquitto/postgres, `read_only`, `no-new-privileges`), 멀티스테이지 Dockerfile, 디렉터리 트리 2단계, `.env.example` 21키
- 착수: "첫 작업 3개 — 워킹 스켈레톤 (Impact × Uncertainty 순)" — 각 작업에 RED 테스트 ID 지정("RED 먼저: TS-023·025·026·052·053·058·062·063"), "벤더 실제 샘플 페이로드 1건을 얻어 어댑터를 맞추는 것이 이 작업의 완료 조건"

**doc2 근거 인용**
- 인프라는 모듈 '이름' 수준: "`network`(VPC, 프라이빗 서브넷), `iot-core`(thing type, 정책 …), `services`(ECS Fargate: api, event-engine, notifier, ws-gateway) …" — HCL 코드는 없음
- 데이터는 엔티티·컬럼 목록만(§7.1)이고 DDL·제약·인덱스 정의는 "인덱스 핵심: `fall_event(facility_id, status, detected_at_sensor desc)` …" 한 줄
- 런북은 "§10.5 런북(요약 목록)" 10줄, API는 표 + JSON 예시(OpenAPI 없음)
- 착수 전제: "M0 검증(4주) → M1 MVP 구축(10주)" — 센서 채택·법무 검토·가격 검증이 끝나야 구현이 시작된다.

**판정: doc1** — 문서를 그대로 열고 마이그레이션·컨테이너·첫 실패 테스트부터 칠 수 있는 쪽은 doc1이고, doc2는 착수 전 4주짜리 검증 단계를 명시적으로 전제한다.

- 못 찾은 것을 별도 절로 고정: "## 미확인 항목 (조사로 못 찾은 것)" 13건 — 식약처 판정 사례, 인지저하 성인 대리 동의 지침, 급여수가 포함 여부 등
- 대안에 트레이드오프와 기각 사유: "D3 EMQX 브로커 | 대시보드·규칙 엔진 내장 | v5.9+ BSL 1.1 라이선스 — SaaS 재판매 검토 비용", D1~D10 전건

- 상수 47개 전부 근거 열, 가정 A-1~A-9 별도 목록

**doc2 근거 인용**
- 라벨 체계와 가정 목록: "부록 A. 가정 전체 목록" 15건에 '확인 시점'(M0/법무/파일럿) 부여, 스택 표에 '대안' 열, "ADR-001 … 채택 [가정]"처럼 결정 상태를 표기
- 흠결 1(사실 오류를 [확정]으로): "장기요양기관 CCTV 의무화 | **노인복지법·시행규칙 개정**으로 2023-06-22부터 … | [확정]" — doc1이 정정한 대로 실제 근거법은 노인장기요양보험법 제33조의2다
- 흠결 2(무출처 단정): "장기요양보험 수가 | 낙상 감지 서비스에 대한 별도 수가 없음. 시설 자부담 모델 | [확정]" — 부록 C 어디에도 대응 출처가 없다
- 흠결 3(자기모순): 핵심 결정 "D3 … 감지 알고리즘은 상용 센서가 이미 90%+ 수준"의 근거를 §2.4에서 스스로 "높음(90~99% 주장, 실환경 검증 필요)"으로 격하한다

**판정: doc1** — 주장 단위 출처·확인일·미확인 목록·자기 정정까지 갖춘 쪽은 doc1이고, doc2는 라벨 체계는 훌륭하나 [확정] 라벨 안에 사실 오류와 무출처 단정이 섞여 라벨의 신뢰도 자체가 깎인다.

## [6. 범위 절제]

**doc1 근거 인용**
- 기술 선택의 절제는 뚜렷: "D2 Redis + BullMQ … 이벤트 볼륨이 작아 pg-boss로 충분", "D5 마이크로서비스 … 파일럿 규모에서 배포 대상만 늘림", "D6 TimescaleDB … heartbeat를 행으로 저장하지 않으므로 시계열 볼륨 자체가 없음", 관측성 축소 "Prometheus·Grafana·Loki는 다시설 단계 — 파일럿 VM에 동거시켜 R4 SPOF를 키우지 않는다"
- 흠결: 시설 1곳·침상 ≤100·`PILOT_DURATION` 30일 파일럿을 위해 FR 29 · 상수 47 · 엔드포인트 32 · 잡 9 · 테스트 시나리오 65를 두고, 그 위에 구현자에게 쓸모가 없는 메타 층이 얹혀 있다 — 블라인드스팟 레지스터 49행, decision log 53행, "절차 이탈 (평가 런 예산 — 명시)" 표, "## 비용 기록 — 검색: 서브에이전트 26회 … 합계 약 765,000 tok", "참고자료 호출 13회 … 단계당 ≤2 준수"

**doc2 근거 인용**
- MVP 경계를 명시적으로 잘라냄: "4.7 범위 밖 — 낙상 예방(위험도 예측, 보행 분석), 생체신호(호흡·심박) 표시 … 카메라·영상 저장, 얼굴 인식 … 보호자 네이티브 앱 … 직원 성과 평가 지표(응답 시간의 개인별 랭킹)"; F-14~F-19를 P1/P2로 밀어냄; "MVP: mmWave 레이더 단독"
- 흠결: MVP 인프라 폭이 넓다 — AWS IoT Core+SQS+Cognito+ElastiCache+ECS Fargate+Terraform 11모듈+ChirpStack/LoRaWAN+Mender. 파일럿이 "시설 1~2곳, 20~40침상"인데 비기능 요구는 "확장성 | 시설 300곳 × 100센서 = 30,000 센서 heartbeat/분 처리", 부하 테스트는 "300시설 × 100센서 heartbeat 60s, 초당 이벤트 50"으로 잡혀 있다.

**판정: doc2** — 양쪽 다 과잉이 있으나 doc1의 초과분은 구현자에게 전달되지 않는 프로세스 기록(장식)인 반면 doc2의 초과분은 대부분 요구에 연결된 설계이고, 문서 자체가 훨씬 짧으면서도 결정이 완결돼 있다.

## 종합 판정: doc1

여섯 차원 중 다섯(완전성·비모호성·검증가능성·실행가능성·근거성)에서 doc1이 앞서고, 범위 절제 한 차원만 doc2가 가져간다. doc1은 상수 단일 출처, FR↔엔드포인트↔테스트 전건 매핑, 실제 DDL·컴포즈·RED 시나리오가 붙은 첫 작업 3개까지 내려가 "이 문서만 들고 착수한다"는 기준을 실제로 충족하며, 스스로 판정을 CONCERNS로 내리고 미검증 지점을 착수 조건으로 남긴 점도 신뢰를 높인다. doc2는 오탐 피로·다인실 낙상자 식별 불가·감지 품질 실험 프로토콜·클라우드 불통 시 로컬 알림 같은 도메인 통찰에서 더 날카롭지만, 요구사항별 수용 기준과 착수 자산이 없어 구현까지 한 단계(M0 4주)가 더 남아 있다.
