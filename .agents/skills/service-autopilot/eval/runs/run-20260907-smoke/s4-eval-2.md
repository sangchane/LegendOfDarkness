# 심사 결과 — s4 (seed: 라즈베리파이 IP 카메라 제어·실시간 모니터링)

## [1. 완전성]

**doc1 근거 인용**
- 누락을 "증명"하는 장치가 있다: "## 커버리지 매핑 (P0·P1 매핑 0건 = 결함)" 표가 FR-001~026을 전부 E-/J- 항목에 대응시키고, 테스트 절 말미에 "누락 검사: SC-001~010 전부 T-045~052·T-062·T-024·027·030·033·038·042·056에 매핑, FR-001~020 전부 ≥1행(FR-020은 T-019), INV-1~6 각각 T-008·038·011·015·056·040".
- 엣지케이스가 전용 표로 존재: "Given 카메라 A(MAC X) 등록됨, When 같은 MAC를 다른 IP로 다시 등록, Then 409 + '이미 등록된 카메라예요 — 기존 항목의 IP를 바꿀까요?' CTA" 외 등록·라이브·PTZ·헬스/알림 4묶음.
- 운영/장애: "SD 카드 손상·부팅 불능 | 데드맨(RB-05) + 현장 확인 | 전부 중단 | 새 SD에 OS 플래시 → `install.sh --restore /data/backup/latest` ... | RTO_H / RPO_H" 표 + RB-01 런북 전문(메타·트리거·진단·해결·에스컬레이션·검증·롤백) + "복원 리허설: RESTORE_DRILL_INTERVAL".
- 조사 공백 자체를 목록화: "집계: 33항목 전부 마킹 — Clear 1 · Assumed 27 · Asked 5".

**doc2 근거 인용**
- 사용자 축은 더 두껍다: 페르소나 3종("P1 소상공인 사장(카페/매장) / P2 홈랩·스마트홈 / P3 소규모 사무실 관리자"), US-1~11, FR-01~20, NFR-01~12, 역할 3종("owner|operator|viewer")과 RBAC.
- 제품 표면도 넓다: 연속 녹화·타임라인 재생·구간 내보내기, "부록 B 카메라 호환성 매트릭스(초안)"의 브랜드별 ONVIF/PTZ/이벤트 토픽/RTSP 템플릿.
- 위협모델에 doc1에 없는 항목: "EoP | SSRF: 사용자가 입력한 RTSP/XAddr URL로 내부 서비스 접근 ... 목적지 사설대역만 허용·Pi 자신(127.0.0.1, 링크로컬) 차단", "Info disclosure | 카메라 phone-home으로 영상 유출 | nftables로 카메라 VLAN→WAN 차단 룰 제공".
- 반면 엣지케이스 전용 절이 없고, FR별 수용기준이 없으며, 장애 대응은 "10.7 운영 런북(요약)" 6행에 그치고 RTO/RPO가 없다.

**판정: doc1** — 제품 표면(사용자·녹화·호환성)은 doc2가 넓지만, 지정된 6영역 중 엣지케이스·테스트·운영/장애에서 doc1만 커버리지 매핑·누락 검사·RTO/RPO·런북 전문이라는 "빠진 곳 없음"의 증거를 갖췄다.

## [4. 실행가능성]

**doc1 근거 인용**
- 다음 담당자용 핸드오프가 문서 안에 있다: "<preconditions> 1. 08 '잔여 리스크' 1을 SPEC 작성 중 대조 (FR-009 4상태 ↔ 04 상태 기계 ↔ 06 T-024/060/061) ...", "<first_task>SPEC.md 작성 — 위 문서를 진실원으로 ... 상수는 `picam/constants.py`에 03과 같은 이름으로".
- 첫 작업이 통과 시험ID와 묶여 있다: "1. **등록→스트림→그리드 관통** — compose(hub-api+go2rtc host 네트워크) 기동 ... (T-007·T-015·T-016·T-018·T-042 GREEN). 여기서 **검증 대기 가정(03) 4개를 함께 해소**".
- 오류 응답까지 표준화: "camera-duplicate | 409 | 같은 MAC (INV-1) | '이미 등록된 카메라예요 — 기존 항목의 IP를 바꿀까요?'", "storage-exhausted | 507 | 디스크 잔여 < DISK_STOP_PCT".
- 착수 자산이 실물 수준: 디렉터리 구조 트리, `.env.example`(키 이름과 설명만), compose.yaml·Dockerfile 스케치, `install.sh` 4단계.
- 약점: 핵심인 E-18(go2rtc WS 프록시가 offer SDP의 `m=audio` 제거·MSE fMP4 릴레이)의 실제 메시지 포맷은 명시되지 않아 구현자가 go2rtc 소스를 읽어야 한다.

**doc2 근거 인용**
- 외부 시스템 계약이 더 복붙 가능하다: "Control API(127.0.0.1:9997): `POST /v3/config/paths/add/{name}` ... `GET /v3/recordings/list`", "`authJWTJWKS: http://127.0.0.1:8000/api/v1/internal/jwks`, 클레임 `mediamtx_permissions: [{\"action\":\"read\",\"path\":\"cam_front\"}]`", 플레이백 "`GET /get?path=&start=&duration=&format=mp4`".
- 요청/응답 JSON 실례와 브랜드 지식: "온보딩은 설정 파일 0개 ... 브랜드별 RTSP URL 템플릿(Hikvision `/Streaming/Channels/101`, Dahua `/cam/realmonitor?channel=1&subtype=0`, Reolink `/h264Preview_01_main`, Tapo `/stream1`)".
- 착수 순서가 검증과 함께 제시된다: "3. hub-api: /auth/setup,/auth/login, /cameras/discover,/probe,/cameras POST → MediaMTX path 생성 → 검증: 통합 테스트", "4. 스트림 JWT + JWKS + MediaMTX jwt 인증 → 검증: aiortc WHEP 클라이언트 프레임 수신".
- 약점: 상수 단일 표가 없어 임계치를 본문에서 찾아야 하고, MVP 범위 안의 삭제 경로가 "[미확정: M2]"라 M2 착수 시 설계를 다시 해야 한다.

**판정: doc1** — doc2의 서드파티 계약 기술이 더 구체적인 건 사실이나, 미해결 결정 0건 상태에서 첫 작업·선행조건·통과 시험까지 지정한 doc1이 "이 문서만 들고 착수"라는 조건에 더 가깝다.

- 반대로 문서 자체는 과정 산출물이 크다: 33항목 블라인드스팟 레지스터, 미제시 질문 배치 5문항 + 옵션 표, "## 준비도 리포트" 15건 지적 표, "## 비용 기록 ... 서브에이전트 3명 ... 소요 시간 10:20 → 13:50 KST" 등은 구현에 직접 쓰이지 않는다. 다만 읽기 경로를 지정해 완화한다: "<references>... 필요할 때만 읽는다".

**doc2 근거 인용**
- 문서는 압축적이고 무거운 것을 옵션화한다: "관측 스택(옵션 프로파일) | node_exporter, Prometheus, Grafana ... 기본 설치 시 node_exporter만", "**MVP 제외 (Later)** — 클라우드 릴레이/계정, 네이티브 앱, 푸시 알림 인프라, AI 객체 검출 ... CSI 카메라 모듈".
- 그러나 MVP 자체가 시드보다 넓다: "**MVP (M1~M2) 포함** — ... 연속 녹화(fMP4 세그먼트), 타임라인 재생, 클립 내보내기(MP4) / 보존 정책 / 계정·역할(owner, operator, viewer), 감사 로그 / 카메라 이벤트 수신 ... / 원클릭 설치 스크립트"에 React PWA·Caddy·Ansible이 더해지고, 전제는 "팀 2~3명, **MVP 8~10주**"다.
- 부가 산출물도 붙는다: "부록 C. (Later) 라즈베리파이 CSI 카메라 모듈 지원 방안 ... PTZ는 서보 HAT(PCA9685) 드라이버를 PTZ 어댑터 인터페이스로 추상화".

**판정: tie** — doc1은 제품 범위를 시드에 맞춰 절제하는 대신 과정 문서를 부풀렸고, doc2는 문서를 절제하는 대신 MVP 제품 범위를 시드의 두 배 가까이 키워, 과잉이 놓인 자리만 다르고 총량은 우열을 가리기 어렵다.

## 종합 판정: doc1

doc1은 상수 단일 출처·FR↔SC↔테스트ID 커버리지 매핑·엣지케이스 Given/When/Then·RTO/RPO와 런북까지 갖춰 "미결정 0건" 상태로 넘어가며, 근거마다 URL·확인일과 미확인 목록을 달아 되짚어 검증할 수 있다. doc2는 페르소나·RBAC·녹화/재생·브랜드 호환성 매트릭스·MediaMTX 계약 등 제품 표면과 서드파티 계약 기술이 더 넓고 구체적이지만, 삭제 경로·버전 핀·사용자군 같은 MVP 핵심 결정을 [미확정]으로 남기고 FR별 수용기준과 상수 단일 표가 없어 착수 시점의 결정 밀도가 낮다. 범위 절제만 무승부이고 나머지 다섯 차원에서 doc1이 앞서므로, "구현 착수에 필요한 정보의 밀도" 기준에서 doc1을 택한다.
