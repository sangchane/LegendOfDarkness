# 심사 결과 — 사내 회의실 예약 설계 문서 doc1 vs doc2

seed: "사내 회의실 예약을 웹에서 하고 싶다. 지금은 화이트보드에 수기로 적는다."

---

## [1. 완전성]

**doc1 근거 인용**

- 운영/장애 대응은 촘촘하다: "RB-3 DB 볼륨 손상·VM 유실 | 5xx 지속, 백업 데드맨 | ... 새 VM에 compose 배포 → 최신 `pg_dump`를 `psql`로 복원 ... | `RTO_HOURS` / `RPO_HOURS`" — 장애 4종에 감지·영향·절차·RTO/RPO가 모두 붙어 있다.
- 추적성도 있다: "커버리지 매핑 (P0·P1 매핑 0건 = 결함) ... P0·P1 8건 모두 매핑됨. 역방향: 매핑되지 않은 엔드포인트 없음".
- 그러나 보안은 스스로 축약을 선언한다: "lite 판정: ... 신호 표 항목(돈·안전·법·민감정보·외부 노출) 없음 → **STRIDE 전수 표 생략**, 한 단락으로 기록".
- 화면은 하나뿐이다: "## 화면 스케치 (핵심 화면 1: 일 그리드)" — 내 예약·관리자 화면은 문장으로만 존재하고, 모바일·접근성 규격은 "반응형 웹으로 대체"라는 non-goal 한 줄이 전부다.
- 도입/이관 계획이 없다. SC-004는 "화이트보드 철거 상태로 4주 운영"을 요구하는데, 어떻게 철거까지 가는지(병행 기간·초기 데이터 이관·공지)는 어느 문서에도 없다.
- 데이터 모델에 회의 제목·용도 필드가 없다: `bookings { id, room_id, owner_id, period, status, cancelled_by, cancelled_at, idempotency_key, created_at }`. 화이트보드에 적던 "용도"가 대체되지 않는다.

**doc2 근거 인용**

- 위협: "## 14. 위협 모델 (STRIDE)" 표에 S/T/R/I/D/E + 공급망 + 설정까지 18행, 각 행에 "잔여 위험" 열까지 있다 — "I | DB 백업 파일 유출 | 전체 유출 | 백업 암호화(age/gpg), 접근 권한 최소화 | 운영 규율".
- 접근성: "그리드 셀은 `role=\"gridcell\"`, 화살표 키로 이동, Enter로 예약 시작 ... 모달 열릴 때 포커스 이동, Esc로 닫기, 포커스 트랩".
- 이관·출시: "§17.1 초기 데이터 ... 기존 화이트보드 예약: 출시 시점의 이번 주·다음 주 분량을 관리자가 S1에서 대신 입력", "W6+2주 | 병행 운영 종료. 화이트보드 철거 | WAU ≥ 50%, 더블부킹 신고 0".
- 테스트: T1~T48 매트릭스 + "E1~E5" + k6 부하 + "접근성 | Playwright + axe-core | S1, S2, S4 | 심각(critical) 0".
- 화면: S1~S8 목록 + 데스크톱/모바일 ASCII 목업 + S2 모달 + S4 내 예약.
- 사용자: 페르소나 3종("P2 참석자 | 방만 확인 | '오늘 3시 기획 회의 어느 방?'")과 US-1~US-13.

**판정: doc2** — 차원이 열거한 6개 영역(사용자·엣지케이스·보안위협·API/데이터·테스트·운영) 중 doc1이 앞서는 것은 운영/장애 뿐이고, doc1은 STRIDE 전수·접근성·이관 계획·예약 제목을 스스로 비워 둔 반면 doc2는 전부 채웠다.

## [2. 비모호성]

**doc1 근거 인용**

- 수치의 단일 출처를 강제한다: "## 상수 표 (단일 출처 — 04~07은 이름으로만 참조)"에 `SLOT_MINUTES 30` … `RPO_HOURS/RTO_HOURS 24/4`까지 18행, 하류 문서는 `GRID_P95_MS` 같은 이름으로만 부른다.
- 정성 표현을 스스로 금지했다: "03의 질적 표현은 전부 상수·UX-NN으로 변환됨(G2 '1초' → `GRID_P95_MS`, '3클릭' → SC-002)".
- 미결정 0을 명시하고 검증한다: "## 미결정 — 0건 ... 착수 조건 2개는 08로 이관", 그리고 자기 점검에서 "'Drizzle 또는 Kysely 중 하나 — 구현 시 채택'은 **위장된 미결정** ... 반영: Drizzle로 확정".
- 다만 결정 로그·핸드오프에 자리표시자가 남아 주어가 사라진 문장이 여럿이다: "- [단계] (참고자료) — 증거 경계 표기 ... 강제", "/(문서) 로 다음을 실행".

**doc2 근거 인용**

- 규칙은 명확하다: "R6 | 같은 `room_id`에서 `status = 'confirmed'`인 예약과 `[start, end)` 교집합 금지. 경계 접촉(11:00 종료 / 11:00 시작) 허용 | `OVERLAP` (HTTP 409)".
- 그러나 미확정이 9건 남아 있다: "§19.2 발주자 확인이 필요한 항목 — Q1 사내 계정 체계는? ... Q9 예약 시 참석자 초대(캘린더)가 꼭 필요한가".
- 교차 참조가 세 군데 어긋난다: "§12.5 통합 테스트 **T16**(§15): 같은 슬롯에 대해 50개 병렬 POST"라고 하지만 매트릭스의 T16은 "자정 넘김", 동시성은 T26이다. §14도 IDOR에 "테스트 T17"(실제 T17=주말), 권한 상승에 "테스트 T22"(실제 T22=비활성 방)를 건다.
- 계약 강도가 흔들린다: "§10.1 멱등성 | `POST /reservations`에 `Idempotency-Key` 헤더 **선택**"인데 §12.4는 그 헤더를 중복 방지 수단으로 전제한다.
- 측정 불가 목표가 하나 있다: "G5 노쇼 회수 ... 목표치 = 측정 후 기준선 설정".

**판정: doc1** — 상수 단일 출처와 "미결정 0건" 자기 검증이 doc2의 미확정 9건·깨진 테스트 참조 3건·선택/필수가 엇갈리는 멱등성보다 앞서지만, doc1도 결정 로그의 자리표시자 때문에 격차는 좁다.

## [3. 검증가능성]

**doc1 근거 인용**

- 성공 기준 5개가 전부 pass/fail이고 판정 방법이 붙어 있다: "SC-001 | 같은 Room·겹치는 구간의 활성 Booking이 DB에 2건 이상 존재하는 경우 0건 | 동시 100 요청 부하 테스트 후 `SELECT`로 겹침 검사 = 0행", "SC-005 | ... ≤ `RTO_HOURS`, 유실 ≤ `RPO_HOURS` | 분기 복원 리허설 기록".
- 수용 기준 → 시나리오 변환표가 레이어와 데이터까지 지정한다: "Given 활성 예약 `[10:00,11:00)` When `[11:00,11:30)` POST Then 201 (경계 맞닿음 허용) | integration | 실 PG".
- 착수 전 RED를 게이트로 건다: "각 시나리오는 처음엔 반드시 실패해야 한다 (RED 확인 후 구현)".

**doc2 근거 인용**

- 48행 매트릭스가 입력과 기대값을 그대로 준다: "T26 | 동시 경쟁 | 같은 슬롯 50개 병렬 POST | **정확히 1건 201, 49건 409, DB confirmed 1행**", "T24 | 상한 계산에 취소 제외 | 활성 9 + 취소 5, 10번째 | 201".
- 출시 게이트를 명시한다: "이 테스트가 통과하지 않으면 출시하지 않는다."
- 부하·접근성도 임계값이 있다: "통과 기준: 조회 p95 < 300ms, 생성 p95 < 500ms, 5xx 0건, 409는 허용", "심각(critical) 0".
- 다만 목표 표의 G5는 목표치가 비어 있다(위 참조).

**판정: tie** — doc1은 성공 기준 5개 전부에 판정 방법을 붙였고 doc2는 48개 케이스에 기대 상태코드를 붙였으며, 양쪽 모두 "무엇이 통과인가"를 기계적으로 판정할 수 있어 우열을 가릴 근거가 없다.

## [4. 실행가능성]

**doc1 근거 인용**

- 착수 순서가 리스크 순으로 정렬돼 있다: "첫 작업 3개 (워킹 스켈레톤 — Impact×Uncertainty 큰 것부터) 1. **DB 스키마 + EXCLUDE 경합 테스트 RED→GREEN** ... 이 하나로 G1이 증명된다."
- 계약은 표로 완결돼 있다: "EP-05 | `POST /api/bookings` (+`Idempotency-Key`) | `{room_id, start, end}` — owner는 세션(INV-3) | 201 ... 409 `booking-conflict` + `next_free`".
- 그러나 산출물은 스케치 수준에서 멈춘다: "핵심 DDL 스케치 (INV-1·INV-4, **전문은 마이그레이션에서**)", compose는 파일이 아니라 문장이다("`web`(Next.js standalone 이미지, non-root, `read_only` + `/tmp` tmpfs ...)").
- 핸드오프 절이 자리표시자로 끊긴다: "/(문서) 로 다음을 실행: <inputs>eval/runs/.../(문서) (요구사항·불변식·상수 표), (문서) (엔드포인트·ERD·DDL 스케치)".

**doc2 근거 인용**

- DDL이 그대로 실행 가능하다: `CREATE TABLE reservations (... CONSTRAINT no_overlap EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status = 'confirmed'))` + 인덱스 3개 + `INSERT INTO settings ...` 시드 10행.
- 인프라 파일이 실물이다: "§16.2"의 `docker-compose.yml`(caddy/app/db/backup, healthcheck·logging 포함), `Caddyfile`, `.env.example` 16키.
- API가 요청/응답 JSON 실물로 제시된다: "POST /api/v1/reservations ... 201 Created { \"id\": …, \"can_edit\": true, \"warnings\": [] }", 충돌 응답의 `conflict` 객체까지.
- 예외 처리 코드까지 있다: "if (isPgError(e, '23P01') && e.constraint === 'no_overlap') { const conflict = await findConflict(tx, row); throw new Overlap(conflict); }".
- 주차별 산출물·검증이 붙는다: "W2 | 규칙 함수(R1~R7, R12) + 단위 테스트, 예약 생성 API, T1~T26 통합 테스트, 타임라인 화면 | **T26 동시성 테스트 통과**".

**판정: doc2** — doc1의 "첫 작업 3개"는 순서 감각이 뛰어나지만, 다음 담당자가 곧바로 실행할 수 있는 DDL 전문·compose·Caddyfile·요청/응답 실물은 doc2에만 있고 doc1의 핸드오프 절은 참조가 비어 있다.

## [5. 근거성]

**doc1 근거 인용**

- 증거 경계를 표기 규약으로 강제한다: "**[출처]** = 웹에서 확인한 사실 · **[사용자]** = 입력에서 읽은 것 · **[추론]** = 그로부터 도출 · **[추천]** = 선택 제안".
- 도메인 수치에 출처와 확인일이 붙는다: "[출처] ... '유령 회의(ghost meeting)': 예약됐지만 아무도 안 오는 방이 주당 30~40% ... https://www.deskbird.com/blog/ghost-meetings ... (확인 2026-09-07)".
- 규제 근거를 인용한다: "[출처] 개인정보보호법: 목적에 필요한 **최소한의 개인정보만** 수집하고, 최소 수집의 입증책임은 처리자에게 있다 ... https://www.privacy.go.kr/...".
- 기술 선택에 트레이드오프와 폐기 사유가 붙는다: "검토한 대안 | 앱 층 SELECT-then-INSERT ... | READ COMMITTED에서 경합 시 둘 다 통과 가능 ... | INV-1을 코드 리뷰에 의존하게 됨", 그리고 "#2 ... (b) MRBS Adopt/Extend: 기능 충족하나 GPLv2·PHP·모바일/알림 부재로 운영 스택을 물려받음".
- 가정을 가정이라 표시하고 값이 틀렸을 때의 경로까지 적는다: "7. 제약·트레이드오프 | Assumed | ... 팀 역량 미기재 → TypeScript 가정(S1) | ... 틀리면 S2(FastAPI)로 교체 — 계약·ERD는 그대로".

**doc2 근거 인용**

- 가정 표의 형식이 훌륭하다: "| ID | 항목 | 가정값 | **근거** | **틀렸을 때 영향** |" — "A13 | 개발 스택 익숙도 | TypeScript 가능 인력 있음 | 미확인 | Java/.NET 팀이면 §11 스택 옵션 B로 교체. API·ERD·규칙은 스택 무관".
- 스택 선택에 비교축이 있다: "§11.1 | 1~2인 개발 속도 | 상 | 중 | 상 ... **선택: A.** 이유: 한 언어로 프론트·백엔드·검증 스키마(Zod)를 공유하고 ...".
- ADR로 대안과 이유를 남긴다: "ADR-2 | 반복 예약 MVP 제외 | RRULE 저장 + 전개 | 예외 처리 복잡도가 MVP 6주에 맞지 않음".
- 그러나 외부 근거가 한 건도 없다: "Google Calendar 리소스 예약, Microsoft Exchange 룸 메일박스, Robin, Joan, Envoy Rooms, Skedda 등에서 **공통적으로 나타나는** 구성 요소" — 출처·확인일 없음. 개인정보 관련 결정("퇴사자 계정 비활성화 시 예약 이력은 유지(익명화 안 함 — 감사 목적)")도 법적 근거 없이 단정한다.

**판정: doc1** — doc2의 가정 표·ADR도 내부 논증으로는 훌륭하지만, doc1만이 사실/추론/추천을 구분 표기하고 도메인 수치·법령·DB 기능에 확인일이 붙은 출처를 달았다.

## [6. 범위 절제]

**doc1 근거 인용**

- 만들지 않을 조건을 먼저 건다: "**그룹웨어 자원 캘린더 부재 확인** — 회사가 M365 또는 Google Workspace를 쓰고 회의실을 자원으로 등록할 수 있으면 **이 패키지를 폐기하고** room mailbox/Calendar 자원을 설정한다."
- MVP를 3개 유스케이스로 묶는다: "5. MVP — 방×시간 그리드 조회 + 중복 없는 예약 + 내 예약 취소. 6. 안티골 — 개인 일정·외부인 예약·결제·다지점·모바일 앱."
- YAGNI를 결정으로 남긴다: "#14 ... 로그 스택 없음(docker json-file + 주간 집계 스크립트) — Loki/Grafana는 대시보드 필요가 생기면 추가", "실시간 푸시 ... SC-003은 조회 시점 정확성만 요구".
- 반대 증거: 절제가 지나쳐 화이트보드의 "용도" 칸을 대체할 필드가 없다(bookings 스키마에 title 없음).

**doc2 근거 인용**

- Must가 12개다: "F1 SSO(OIDC) ... F8 비공개 예약 ... F9 관리자: 회의실 CRUD·비활성화, **설정 변경** ... F11 감사 로그: 전/후 값 ... F12 사용률 리포트" — 여기에 §10.3 속도 제한, §16.4 지표 6종, 접근성 axe, 아웃박스 워커까지 MVP에 들어간다.
- 그 부담을 스스로 인정한다: "1인 개발이면 W4의 리포트·필터·주간 뷰를 Phase 1.5로 미룬다" — 즉 A8(1~2명, 6주) 가정에서 이미 넘친다.
- 설정화도 선제적이다: "US-11 관리자로서 운영 규칙(시간 단위·운영시간·최대 길이·선예약 일수·1인 상한)을 바꾼다 ... 변경 즉시 반영" — 요청되지 않은 유연성이 MVP에 들어와 `settings` 테이블·화면·검증(T42)을 유발한다.
- 결정적으로, 기존 그룹웨어 자원 예약을 **채택할지**는 검토되지 않는다. §5.1은 Google Calendar 리소스 예약을 "상용 제품의 패턴"으로만 인용하고 대안으로 저울질하지 않는다.

**판정: doc1** — doc1은 "이미 M365가 있으면 만들지 마라"까지 범위 판단에 넣고 MVP를 3개로 잘랐지만, doc2는 Must 12개에 설정 화면·리포트·속도 제한을 넣고도 6주/1~2인 가정을 유지한다.

## 종합 판정: doc1

doc2는 실행 가능한 DDL·compose·48개 테스트 케이스로 "지금 당장 코딩을 시작할 수 있는" 패키지를 더 두껍게 갖췄고, 완전성과 실행가능성에서 분명히 앞선다. 그러나 doc1은 사실/추론을 구분한 출처 있는 근거, 이름으로만 참조되는 상수 단일 출처, "미결정 0건"의 자기 검증, 그리고 "그룹웨어가 있으면 이 패키지를 폐기하라"는 범위 판단으로 6개 차원 중 3개를 가져갔다(2무 아닌 1무 2패). 두 문서의 격차는 좁고 doc2의 우위는 상당 부분 분량에서 나오므로, 결정의 완결성과 근거를 기준으로 doc1을 택한다.
