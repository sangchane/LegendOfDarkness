# 심사 결과 — s1 (doc1 vs doc2)

seed: "사내 회의실 예약을 웹에서 하고 싶다. 지금은 화이트보드에 수기로 적는다."

---

## 1. 완전성

**doc1 근거**
- 위협모델이 전수 표다. §14 STRIDE 18행에 잔여 위험 열까지 있다: "| **I**nfo Disclosure | 민감 회의 제목 노출 | 인사 정보 유출 | 비공개 옵션(R11), 목록·상세·리포트·알림 모두 마스킹 | 예약자가 비공개를 안 켜는 경우 — UI에서 제목 입력 시 힌트 |"
- 테스트가 6계층 + 48케이스: "| 단위 | Vitest | `rules.ts`(R1~R14) ... | 규칙 함수 100% 분기 커버 |", T1~T48, E2E 5개, k6 부하, "접근성 | Playwright + axe-core | S1, S2, S4 | 심각(critical) 0"
- 운영·이관까지: §16.5 런북 5항목, §17.1 "기존 화이트보드 예약: 출시 시점의 이번 주·다음 주 분량을 관리자가 S1에서 대신 입력", §17.4 "30분 이상 서비스 불능이면 관리자가 전사 메시지: '임시로 화이트보드/구두 조율'"
- §8.7 접근성 체크리스트("그리드 셀은 `role=\"gridcell\"`, 화살표 키로 이동, Enter로 예약 시작")

**doc2 근거**
- doc1에 없는 층위를 덮는다. 01 유사 솔루션 표: "**회사가 이미 M365/Workspace를 쓰면 이게 정답** — 이 패키지 전체가 불필요"
- 개인정보 파기까지: "FR-008 | `BOOKING_RETENTION_DAYS`가 지난 Booking과 `INACTIVE_USER_PURGE_DAYS` 지난 비활성 사용자를 일 1회 배치로 파기한다", JOB-01
- 그러나 위협모델을 스스로 축약: "lite 판정: SKILL.md 신호 표 항목(돈·안전·법·민감정보·외부 노출) 없음 → STRIDE 전수 표 생략, 한 단락으로 기록"
- 커버리지 역추적: "P0·P1 8건 모두 매핑됨. 역방향: 매핑되지 않은 엔드포인트 없음"

**판정: doc1** — 차원이 열거한 여섯 영역(사용자·엣지케이스·보안위협·API/데이터·테스트·운영) 전부에서 doc1의 공백이 더 적고, doc2는 위협모델 전수 표·접근성·이관/공지·통지 설계를 스스로 생략했다(반대로 buy-vs-build와 보존·파기 배치는 doc1의 실제 공백이다).

## 2. 비모호성

**doc1 근거**
- 규칙이 기본값·에러코드·평가 순서까지 확정돼 있다: "| R2 | 길이: `min_minutes ≤ end − start ≤ max_minutes` | 15분 / 240분 | `DURATION_OUT_OF_RANGE` |", "규칙 우선순위: 인증 → 권한 → 형식(R1) → 값 범위(R2~R5, R7) → 회의실 상태 → 겹침(R6, DB). 앞 단계에서 실패하면 뒤를 검사하지 않는다."
- 반면 참조가 여러 곳에서 깨져 있다. §12.5 "통합 테스트 T16 (§15): 같은 슬롯에 대해 50개 병렬 `POST`"인데 §15.2의 T16은 "자정 넘김"이고 동시성은 T26이다. §14도 IDOR 대응을 "테스트 T17"(실제 T31), 권한상승을 "테스트 T22"(실제 T38)로 가리킨다.
- 가정 표의 ID 열이 전부 "단계"로 뭉개져 K1 "IdP가 Google/MS가 아님 (단계)", Q3 "단계, 단계" 같은 역참조가 해석되지 않는다. §11.1은 "세션 | 서버 세션 (DB `sessions` 테이블)"이라 하지만 §9.2 DDL에 `sessions` 테이블이 없다.

**doc2 근거**
- 수치를 단일 출처로 묶는다: "## 상수 표 (단일 출처 — 04~07은 이름으로만 참조)" — SLOT_MINUTES·MAX_BOOKING_MINUTES·GRID_P95_MS·RPO_HOURS 등 전부 이름으로만 하류 참조.
- "## 미결정 / 0건 — register 전 항목 Assumed 처리 완료, 착수 조건 2개는 08로 이관."
- 숨은 모호성을 스스로 적발: "| 1 | HIGH | 04:구현 접근 | \"Drizzle 또는 Kysely 중 하나 — 구현 시 채택\"은 위장된 미결정 ... | 반영: Drizzle로 확정 |"
- 다만 결정 로그·핸드오프에 "(문서)", "(참고자료)", "[단계]" 같은 해석 불가 토큰이 다수 남아 그 부분은 읽히지 않는다.

**판정: doc2** — 양쪽 다 표기 훼손이 있으나, 값의 단일 출처화·미결정 0건 선언·위장된 미결정의 자체 적발까지 갖춘 doc2가 내부 참조 정합성에서 앞선다.

## 3. 검증가능성

**doc1 근거**
- 핵심 리스크가 하나의 pass/fail 게이트로 못 박혀 있다: "| **T26** | **동시 경쟁** | 같은 슬롯 50개 병렬 POST | **정확히 1건 201, 49건 409, DB confirmed 1행** |", §12.5 "이 테스트가 통과하지 않으면 출시하지 않는다."
- 지표마다 측정 방법 열: "| G2 | 더블부킹 0 | 동일 회의실·시간 겹침 건수 | 0건 (DB 제약으로 보장) | DB 제약 위반 시 409 카운트 + 월간 감사 쿼리 |"
- 부하 통과 기준: "조회 p95 < 300ms, 생성 p95 < 500ms, 5xx 0건, 409는 허용."
- 케이스마다 입력과 기대가 확정: "| T19 | 30일 후 정확히 | now + 30d (같은 시각) | 201 |", "| T43 | KST 날짜 경계 | ... | 09-07 목록에 포함 |"

**doc2 근거**
- SC 5개가 전부 판정 방법을 달고 있다: "| SC-001 | 같은 Room·겹치는 구간의 활성 Booking이 DB에 2건 이상 존재하는 경우 0건 | 동시 100 요청 부하 테스트 후 `SELECT`로 겹침 검사 = 0행 |"
- 실패 선행 게이트: "AC는 개발 시작 전에 존재한다. 각 시나리오는 처음엔 반드시 실패해야 한다 (RED 확인 후 구현)."
- 운영 기준도 pass/fail: "SC-005 ... 복원해 그리드 조회가 성공하기까지 ≤ `RTO_HOURS`, 유실 ≤ `RPO_HOURS` | 분기 복원 리허설 기록"

**판정: doc1** — 양쪽 다 pass/fail이지만, doc1의 T1~T48은 입력·기대 상태코드·DB 상태까지 적혀 그대로 수용 스위트가 되고 경계 접촉·시간대 경계·마스킹·멱등 재요청처럼 doc2가 다루지 않는 지점까지 판정 가능하다.

## 4. 실행가능성

**doc1 근거**
- 스키마가 스케치가 아니라 실행문이다: "CREATE EXTENSION IF NOT EXISTS btree_gist;" 이하 users/rooms/reservations/reservation_events/notifications/settings 6개 테이블 전문 + "INSERT INTO settings (key, value) VALUES ('slot_minutes','15'), ..." 시드까지.
- 인프라도 전문: §16.2 `docker-compose.yml`(caddy/app/db/backup 4서비스, healthcheck·로그 로테이션 포함), Caddyfile, `.env.example`.
- 착수 순서: "| W2 | 규칙 함수(R1~R7, R12) + 단위 테스트, 예약 생성 API, T1~T26 통합 테스트, 타임라인 화면 | **T26 동시성 테스트 통과** |"

**doc2 근거**
- 스키마는 부분만: "핵심 DDL 스케치 (INV-1·INV-4, 전문은 마이그레이션에서)" — EXCLUDE·CHECK·인덱스 4개뿐, 테이블 정의는 ERD 컬럼 목록으로 대체.
- 대신 첫 손이 매우 구체적: "1. **DB 스키마 + EXCLUDE 경합 테스트 RED→GREEN** ... 이 하나로 G1이 증명된다.", 디렉터리 구조와 `.env.example` 키 목록, CI 단계 순서.
- 다만 착수 전 정지 조건이 있다: "**그룹웨어 자원 캘린더 부재 확인** — ... 자원으로 등록할 수 있으면 **이 패키지를 폐기하고** room mailbox/Calendar 자원을 설정한다."

**판정: doc1** — doc2의 "첫 작업 3개"는 진입점으로 훌륭하지만, 복붙 가능한 DDL·컴포즈·프록시 설정·에러 본문·요청/응답 예시를 다 갖춘 doc1이 "이 문서만 들고 바로 착수"에 더 가깝다.

## 5. 근거성

**doc1 근거**
- 가정을 표로 분리하고 실패 영향까지 적었다: "| 항목 | 가정값 | 근거 | 틀렸을 때 영향 |" — 예: "개발 스택 익숙도 | TypeScript 가능 인력 있음 | 미확인 | Java/.NET 팀이면 §11 스택 옵션 B로 교체. API·ERD·규칙은 스택 무관"
- 결정마다 대안과 이유: "| ADR-1 | 겹침 방지를 DB `EXCLUDE` 제약으로 | 앱 레벨 `SELECT` 후 `INSERT`, 회의실 행 잠금 | 레이스 컨디션을 DB가 원자적으로 차단 |", §12.1의 실패 시퀀스 도해.
- 그러나 도메인 주장에 출처가 없다: "Google Calendar 리소스 예약, Microsoft Exchange 룸 메일박스, Robin, Joan, Envoy Rooms, Skedda 등에서 공통적으로 나타나는 구성 요소", "예약 규칙 | 15분 단위 ... | 상용 제품의 일반 기본값" — 검증 경로가 없다.

**doc2 근거**
- 사실과 추론을 표기로 분리: "증거 경계 표기: **[출처]** = 웹에서 확인한 사실 · **[사용자]** = 입력에서 읽은 것 · **[추론]** = 그로부터 도출 · **[추천]** = 선택 제안"
- 수치에 출처와 확인일: "예약됐지만 아무도 안 오는 방이 주당 30~40%라는 업계 수치가 있고, 표준 대책은 **시작 후 10~15분 체크인 없으면 자동 해제** ... (확인 2026-09-07)", 개인정보보호법·PostgreSQL rangetypes 문서 링크.
- 결정 로그가 버린 대안을 남긴다: "#4 ... 대안 (a) 로그인 없음(이름만 입력): 남의 예약 취소·부인 방지 불가 → 화이트보드 문제 재현. (b) 비밀번호: 리셋 흐름·해시 관리 부담이 1인 운영에 과잉."
- 상충도 기록: "#12 ... tdd-workflow의 80% 일률은 채택 안 함", "#10 ... 템플릿 우선".

**판정: doc2** — 확인일자 있는 출처로 사실을 고정하고 추론과 구분했으며, 기술 선택마다 버린 대안과 이유가 남아 있다.

## 6. 범위 절제

**doc1 근거**
- 배제 결정은 분명하다: "**Won't (이번 릴리스)** 좌석 예약, 방문객 관리, 다지점, 비용 청구, 네이티브 앱.", "| ADR-3 | 서버 1대 Docker Compose | Kubernetes, 서버리스 | 사용자 ≤ 200, 운영자 1인 |", "| ADR-8 | 30초 폴링 | WebSocket/SSE | 100명 규모에서 실시간 푸시 불필요 |"
- 그런데 MVP가 크다: Must가 F1~F12로 감사 로그·비공개 예약·사용률 리포트·아웃박스 이메일 워커·관리자 설정 화면까지 포함하고, 거기에 §10.3 속도 제한과 `Idempotency-Key`까지 6주 안에 넣는다. 화면도 S1~S8 8개.

**doc2 근거**
- MVP를 세 줄로 자른다: "5. MVP — 방×시간 그리드 조회 + 중복 없는 예약 + 내 예약 취소.", P0는 FR-001~004 4건, 화면 2개.
- 배제에 이유가 붙는다: "| 실시간 푸시(WebSocket/SSE) | ... | SC-003은 조회 시점 정확성만 요구. 사내 소규모에서 재조회로 충분 (YAGNI) |", 레이트리밋도 "그 외는 사내망이라 미적용", "#14 로그 스택 없음 ... Loki/Grafana는 대시보드 필요가 생기면 추가(YAGNI)".
- 다만 register 22축·준비도 리포트·model_hints·"DENSITY 6 / MOTION 2 / VARIANCE 3" 같은 절차 메타가 그 자체로 부피를 만든다.

**판정: doc2** — 화이트보드 대체라는 요구 크기에 doc2의 MVP가 더 비례하고, 뺀 것마다 왜 뺐는지가 남아 있다(대신 doc2는 절차 메타라는 다른 종류의 군더더기를 진다).

## 종합 판정: doc1

차원은 3 대 3(완전성·검증가능성·실행가능성 = doc1 / 비모호성·근거성·범위 절제 = doc2)으로 갈렸지만, 질문이 "구현 착수에 더 적합한 문서"인 이상 실행 가능한 스키마·컴포즈·규칙·수용 스위트를 통째로 넘겨주는 doc1이 앞선다 — doc2가 DDL을 스케치로 남기고 위협모델·접근성·이관 절차를 축약한 자리에서 doc1은 바로 코드가 된다. 대신 doc2가 이긴 세 차원은 장식이 아니라 doc1의 실제 약점을 정확히 찌른다: 도메인 주장에 출처가 없고, "이미 M365/Workspace가 있으면 만들 필요가 없다"는 가장 비싼 질문을 doc1은 아예 던지지 않으며, MVP가 화이트보드 대체치고 과하다. doc1을 구현 입력으로 쓰되 doc2의 착수 조건 #1(그룹웨어 확인)과 보존·파기 배치를 얹는 것이 실무적으로는 최선이다.
