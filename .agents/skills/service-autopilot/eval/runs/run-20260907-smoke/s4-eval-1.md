# 심사 판정 — s4 (doc1 vs doc2)

시드: "라즈베리파이로 IP 카메라를 제어하고 실시간 모니터링하는 서비스를 만들고 싶다."
심사 기준: 구현 착수에 필요한 정보의 밀도(길이 아님). 차원별로 근거 인용 → 판정.

---

## [1. 완전성]

**doc1 근거**
- 사용자 축이 두껍다: "P1 소상공인 사장(카페/매장) / P2 홈랩·스마트홈 사용자 / P3 소규모 사무실 관리자" 3 페르소나 + US-1~US-11이 각각 수용 기준을 달고 있다 — 예) "US-1 … 검색 버튼 후 10초 내 ONVIF 장치 목록(IP, 모델, 제조사) 표시. 미검색 시 수동 등록 경로 안내".
- 6개 영역을 모두 건드리기는 한다: STRIDE 20행(§5.3), 엔드포인트 표(§6.2, 약 30개), ERD(§7), 레벨별 테스트 표(§9.3), "10.7 운영 런북(요약)" 6증상.
- 다만 **엣지케이스 전용 절이 없다.** 예외 처리는 "§4.5 스트리밍 결정 트리", "US-8 … 사용률 85% 도달 시 가장 오래된 세그먼트부터 삭제" 처럼 본문 곳곳에 흩어져 있고, FR↔엔드포인트↔테스트 추적표가 없다. 그 결과 FR-15(설정 백업/복원)·FR-17(외부 알림)·FR-18(HA API 토큰)에 대응하는 테스트 케이스가 §9.3에서 확인되지 않는다.

**doc2 근거**
- 엣지케이스가 전용 절로 존재한다: "## 엣지케이스 (Given/When/Then)" 아래 등록·라이브·PTZ·헬스/알림 4묶음 — "Given 카메라 A(MAC X) 등록됨, When 같은 MAC를 다른 IP로 다시 등록, Then 409 + '이미 등록된 카메라예요 — 기존 항목의 IP를 바꿀까요?' CTA", "Given PTZ 패드 누름 중, When 브라우저 탭이 닫히거나 네트워크 끊김, Then 허브가 서버측 타임아웃(PTZ_HOLD_TIMEOUT_MS)으로 Stop을 보낸다; 허브 자체가 죽어도 카메라가 멈추도록 ContinuousMove의 Timeout을 … 함께 보낸다".
- 추적이 표로 닫혀 있다: "## 커버리지 매핑 (P0·P1 매핑 0건 = 결함)"(FR-001~026 → E-xx·J-xx), 그리고 "누락 검사: SC-001~010 전부 T-045~052·T-062·T-024·027·030·033·038·042·056에 매핑, FR-001~020 전부 ≥1행(FR-020은 T-019), INV-1~6 각각 T-008·038·011·015·056·040".
- 운영/장애가 알람:런북 1:1까지 내려간다: 알림 표의 RB-01~RB-06, "### 런북 골격 (예: RB-01 카메라 offline)"(진단 3단계가 복붙 가능한 명령), 장애 시나리오 표에 RTO/RPO 열, "복원 리허설: RESTORE_DRILL_INTERVAL … 리허설 결과는 감사 로그에 restore.drill로 기록", 비밀 회전 절차(install.sh --rotate-secrets).
- 반대로 사용자 축은 얇다: 권한 1종(관리자), 유저 스토리 US-1~US-5뿐.

**판정: doc2** — 사용자·페르소나는 doc1이 두껍지만, 엣지케이스·API/데이터 추적·테스트 매핑·운영/장애 대응 네 영역에서 doc2가 비어 있는 곳이 뚜렷이 적다.

## [2. 비모호성]

**doc1 근거**
- 표기 규칙 자체는 좋다: "**[확정]** 근거 있는 사실/결정 · **[가정]** 이 문서가 스스로 정한 전제 · **[미확정]** 검증·의사결정이 남은 항목".
- 그러나 뿌리 결정이 열린 채로 끝난다: "12.2 오픈 이슈 [미확정] 1. 사용자군이 B2C 셀프호스팅인지 B2B 관제인지 … 답에 따라 멀티사이트·RBAC 깊이 변경", "(MediaMTX 버전별 키 이름 변경 가능 → 설치 시 버전 핀 고정 [미확정: 핀 버전은 M0에서 결정])", "삭제는 MediaMTX recordDeleteAfter + hub-api가 … 사이드카로 수행 [미확정: 삭제 경로 최종 결정은 M2]".
- 수치가 단일 출처 없이 본문에 흩어져 있다(워터마크 85→80%, PTZ 워치독 2초, 스트림 JWT 5분, 제어권 락 30초, 온도 80°C). 같은 값이 §2·§4·§5·§10에 재기술돼 문서 내 상충을 막는 장치가 없다.

**doc2 근거**
- 단일 출처를 명시적으로 세운다: "## 상수 표 (단일 출처 — 04~07은 이름으로만 참조)" 38개 + "### 운영 기본값 (근거 약함 — 운영 관행, 착수 후 조정 가능. 05·07은 이 이름으로만 참조)" 14개. 이후 요구사항·API·테스트·compose가 전부 이름으로만 참조한다: "compose의 숫자(interval·retries·memory)는 03 상수 표 값을 deploy/render.sh가 템플릿에서 치환해 생성한다 — 손으로 두 곳을 고치지 않는다".
- 모호해지기 쉬운 상태값을 정의로 못박는다: FR-009 "**unknown**=등록 후 첫 프로브 전 · **online**=두 프로브 성공 · **degraded**=RTSP 성공이나 ONVIF가 OFFLINE_AFTER_FAILURES회 연속 실패(라이브 가능, PTZ·스냅샷 불가) · **offline**=RTSP가 OFFLINE_AFTER_FAILURES회 연속 실패(라이브 불가)".
- 미결을 0으로 몰고, 남은 것을 성격이 다른 항목으로 분리한다: "## 미결정 — 0건 … 값이 정해졌으나 실측·확인이 남은 것은 위 '검증 대기 가정' 4건으로 관리 — 결정은 끝났고 검증만 남았다".
- FR이 EARS 문형이라 주어가 항상 있다: "FR-010 카메라 상태가 바뀌면 시스템은 이벤트를 기록하고 알림 채널로 보내야 하며, 같은 카메라·같은 유형은 ALERT_DEDUP_WINDOW_S 안에 1건만 …".

**판정: doc2** — doc1은 대상 사용자군·버전 핀·삭제 경로가 미결인 채 남았고, doc2는 미결 0건 + 상수 단일 출처로 재기술 상충의 여지까지 제거했다.

## [3. 검증가능성]

**doc1 근거**
- KPI가 목표치와 측정 방법을 함께 가진다: "라이브 지연(LAN, WebRTC) | ≤ 1.0 s (glass-to-glass) | 타임스탬프 화면 촬영 비교", "녹화 누락률 | ≤ 0.1 % (분 단위 갭 기준) | 세그먼트 인덱스 갭 분석".
- 릴리스 게이트가 체크박스로 있다: "9.4 수용 테스트 — [ ] 신규 Pi에서 설치 스크립트 → 첫 라이브까지 5분 이내(스톱워치) … [ ] 보안 자동화 스캔 High 0건".
- 그러나 KPI↔테스트 케이스의 번호 매핑이 없고, 성능 근거는 "4.6 성능 예산 [가정 — HIL 테스트로 검증 필요]"로 남는다. §9.3의 테스트에는 식별자가 없어 개별 수용 기준과 1:1로 걸리지 않는다.

**doc2 근거**
- 성공 기준이 전부 pass/fail + 측정 방법 + 반복 횟수다: "SC-003 … 타일 offline 표시 ≤ OFFLINE_DETECT_MAX_S; 이벤트 기록 시각(event.ts) 기산 푸시 수신 ≤ ALERT_DELIVERY_MAX_S | 스톱워치 10회 전부 통과 (lab T-062) + 시뮬레이터 T-024·T-027", "SC-008 무설명 신규 사용자 5인이 … 결정 지점 ≤ UX_MAX_DECISIONS, ≤ 3분에 완료 | 사용성 테스트 5인 4/5 이상".
- 시나리오가 T-001~T-062로 번호가 붙고 각각 Given/When/Then·레이어·픽스처를 가진다: "T-020 … Given 패드 press, When 150ms 동안 move 3회(50ms 간격), Then sim-camera 수신 ContinuousMove ≤ 2회(PTZ_THROTTLE_MS 병합), 마지막 벡터 값 | integration | sim-camera 로그".
- 게이트를 명시한다: "AC는 개발 시작 전에 존재한다. 각 시나리오는 처음엔 반드시 실패해야 한다(RED 게이트) … RED 확인 후에만 구현", 커버리지는 "리스크 기반 … P0 경로·INV 불변식·위협모델 상위 3 관련 코드 ≥ 90% 분기, 그 외 ≥ 60% 라인".

**판정: doc2** — doc1의 KPI도 측정 가능하지만, doc2는 SC 10개 전부를 번호 붙은 62개 시나리오와 양방향으로 매핑하고 누락 검사까지 돌려 "무엇이 통과하면 끝인가"가 코드 수준에서 닫힌다.

## [4. 실행가능성]

**doc1 근거**
- 착수 순서를 검증 기준과 함께 준다: "부록 E … 1. 리포 골격(monorepo: apps/hub-api, apps/hub-web, deploy/ansible, deploy/compose, tools/sim) → 검증: CI lint/test 통과 … 4. 스트림 JWT + JWKS + MediaMTX jwt 인증 → 검증: aiortc WHEP 클라이언트 프레임 수신".
- 구체 자산도 있다: "10.3 docker-compose 스케치"(이미지 핀·user·read_only·healthcheck), "10.4 Ansible 롤 구조"(common/storage/docker/picamhub/firewall/monitoring/update), 요청·응답 JSON 실물 예시(§6.3), ERD 컬럼 타입(§7).
- 다만 착수 즉시 막히는 지점이 남는다: MediaMTX 버전 핀 미확정, 보존 삭제 경로 미확정, "사용자군 B2C/B2B" 미확정(→ RBAC 깊이가 흔들림), 성능 예산 미검증.

**doc2 근거**
- 코드 배치까지 지정한다: "### 디렉터리 구조 … src/picam/ — main.py(라우터 조립) · auth/ · cameras/ · ptz/ · streams/(go2rtc 클라·프록시·reconcile) · health/ · alerts/ … tests/ — unit/ · integration/ · contract/ · e2e/ · lab/", ".env.example (키 이름과 설명만 — 값 없음)", "상수(03 상수 표)는 환경변수가 아니라 코드 상수 모듈 picam/constants.py에 03과 같은 이름으로 둔다 — 운영자가 바꾸는 값이 아니다".
- 첫 작업이 통과해야 할 테스트 ID로 정의된다: "1. **등록→스트림→그리드 관통** — compose 기동, E-20 health(8443), E-01/E-02 setup·login, E-05/E-06 등록(sim-camera), J-04 go2rtc 스트림 등록, E-18 WS 프록시 + 오디오 필터, 그리드 1타일 WebRTC 재생(T-007·T-015·T-016·T-018·T-042 GREEN). 여기서 **검증 대기 가정(03) 4개를 함께 해소**".
- 인계 조건을 명문화한다: "<preconditions> 1. 08 '잔여 리스크' 1을 SPEC 작성 중 대조 … 2. 첫 작업 1에서 03 '검증 대기 가정' 4건 해소 — 실패 시 03 개정 후 05·06·07 갱신", "<first_task>SPEC.md 작성 — 위 문서를 진실원으로, 낯선 구현자 실행 가능 수준".
- 배포 자산도 구체적이다: compose.yaml(host 네트워크·cap_drop·read_only·메모리 상한), Dockerfile 전문, install.sh 4단계, CI/CD 8단계 표 — "deploy | **Pi가 pull 한다**(인바운드 없음): 운영자가 picam update 실행 → compose pull → up -d → 헬스체크 3회 통과 대기 → 실패 시 이전 태그로 자동 복귀".

**판정: doc2** — 양쪽 다 착수 스크립트를 주지만, doc2는 디렉터리·상수 모듈·첫 작업의 GREEN 조건까지 지정하고 남은 불확실성을 "첫 작업에서 해소할 4건"으로 좁혀 두어 담당자가 멈출 지점이 더 적다.

## [5. 근거성]

**doc1 근거**
- 가정을 표로 세우고 "틀렸을 때 무엇이 바뀌는지"까지 적는다: "| 가정 | 근거/이유 | 가정이 틀리면 영향 | … 카메라와 Pi는 같은 LAN(권장: 카메라 전용 VLAN) … | 포트포워딩·공인 IP 노출 회피 | 클라우드 릴레이 필요 시 §4.8 'Later' 토폴로지 승격 |".
- 기술 선택에 기각 사유가 붙는다: "미디어 코어 | **MediaMTX** | … | go2rtc(녹화·플레이백 없음, 별도 ffmpeg 세그먼터 필요) / ffmpeg 직접(시그널링·재생 서버를 직접 작성해야 함)", ADR-001~007에 "이유 / 결과·트레이드오프" 열.
- 그러나 **출처가 URL·확인일 없이 이름만** 남는다: "부록 D 참고 — Raspberry Pi 포럼 'RPi5 Codec confusion' 및 'Lack of Hardware H.264 Decoding' 스레드, Jeff Geerling …, Frigate Discussion #18431". 성능 근거도 "MediaMTX CPU (패스스루, 채널당) | Pi 5 ≈ 2~4 % | Go 패스스루 벤치 경험치"처럼 경험치로 제시된다.

**doc2 근거**
- 주장마다 라벨·URL·확인일이 붙는다: "**사실**: BCM2712는 HEVC(H.265) 4K60 하드웨어 디코더는 유지하지만 **Pi 4에 있던 H.264 하드웨어 디코더/인코더는 Pi 5에서 빠졌다** … 출처: https://forums.raspberrypi.com/viewtopic.php?t=387547 … (확인일 2026-09-07, 공식 사이트 아닌 라즈베리파이 공식 포럼 — 반공식으로 취급)".
- 못 찾은 것을 목록으로 남긴다: "## 미확인 항목 (못 찾은 것 목록) — go2rtc의 ONVIF 지원 범위(공식 문서 직접 확인 못함) … SD카드 등급의 정확 IOPS 수치 … ntfy, Telegram Bot API의 공식 가격·약관 페이지 직접 확인".
- 자기 숫자의 근거 약함을 스스로 표시한다: "MVP_TARGET_WEEKS | 4~6 | 주 | 계획 가정(**근거 없음**, 02 축 7)", "PTZ_THROTTLE_MS | 100 | ms | 초당 10명령 — ONVIF ContinuousMove 갱신에 충분(**추론**)", "### 운영 기본값 (근거 약함 — 운영 관행, 착수 후 조정 가능)".
- 수용한 리스크에 사유와 재검토 조건을 단다: "단계-I **RTSP·ONVIF 평문** | **Accept(사유)** | 카메라 대부분 RTSPS/HTTPS 미지원(01) … 잔여: LAN 도청자", "기기 물리 탈취 | Accept(사유) … **Pi를 통째로 가져가면 키(SD)와 데이터(SSD)가 함께 넘어가 … 완화가 아니라 수용이다.**", "재검토 조건: RTSPS 지원 카메라가 대상 목록에 들어오면 우선 사용".

**판정: doc2** — doc1의 가정-영향 표도 훌륭하지만, doc2는 출처·확인일·미확인 목록에 더해 "이 숫자는 근거가 없다"까지 자기 고발해 사실과 추측의 경계가 훨씬 선명하다.

## [6. 범위 절제]

**doc1 근거**
- 제외 목록은 명시한다: "MVP 제외 (Later) — 클라우드 릴레이/계정, 네이티브 앱, 푸시 알림 인프라 / AI 객체 검출 … / 다중 사이트 통합 관제, 멀티테넌트".

## 종합 판정: doc2

doc2는 상수 단일 출처·미결정 0건·FR↔엔드포인트↔테스트 양방향 매핑·출처와 확인일이 붙은 조사로 "무엇이 정해졌고, 무엇이 남았으며, 무엇을 통과하면 끝인가"를 문서 안에서 닫아 놓았다. doc1은 페르소나·로드맵·카메라 호환성 매트릭스에서 더 두껍고 단일 문서로 읽기 좋지만, 엣지케이스 전용 절과 추적표가 없고 대상 사용자군·버전 핀·보존 삭제 경로를 미확정으로 남겨 착수 담당자가 그 결정을 대신 내려야 한다. 범위 절제만 무승부(doc1은 제품 과잉, doc2는 프로세스 과잉)이고 나머지 다섯 차원은 doc2가 앞선다.
