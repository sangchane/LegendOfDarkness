# 블라인드스팟 체크리스트 — A2 INTERROGATE 심문 엔진

> 목적: "도메인을 모르는 사용자가 못 떠올리는 질문"을 시스템이 대신 떠올린다.
> 모든 축·항목은 검증된 출처에서 이식했다 (spec-kit /clarify 택소노미, OWASP STRIDE,
> AWS Well-Architected Lens, Google SRE, Mender/커뮤니티 검증 엣지 함정).

## 사용법 (3패스)

1. **기본 스캔**: 아래 공통 10축을 전부 스캔해 축별 `Clear / Partial / Missing` 마킹.
2. **도메인 프로파일 로드**: SEED에서 감지한 서비스 유형의 프로파일을 적용(복합 서비스는 합집합).
   프로파일의 각 항목을 같은 방식으로 마킹.
3. **분류**: Partial/Missing 항목을 둘 중 하나로 처리해 `02-blindspot-register.md`에 전수 기록:
   - `Assumed` — 근거 있는 현업 기본값 채택 (기본값 + 출처 명시)
   - `Asked` — 질문 승격 (아래 기준 충족 시만, **전체 최대 5문항**)
   - 해당 없는 축도 `Clear(해당없음 — 근거)`로 기록한다. **마킹 안 된 축이 남으면 게이트 통과 불가.**

## 질문 승격 기준 (Impact × Uncertainty — 둘 다 충족해야 승격)

- **Impact**: 틀리면 비싸다 — 아키텍처 재작업 / 데이터 손실 / 법적 문제 / 하드웨어 재구매 / 확정 후 변경 불가.
- **Uncertainty**: 조사로 못 정한다 — 답이 사용자의 실제 환경·예산·운영 인력·사업 방향에 달려 있다.
- 승격 후보가 5개를 넘으면 (Impact × Uncertainty) 상위 5개만. *(spec-kit /clarify 이식)*
- 질문 형식: 객관식 2~4옵션, 첫 옵션 = `(추천)` + 이유, 각 옵션에 근거·트레이드오프 한 줄.

## 위협 스캔 (4축 보안의 세부 — STRIDE 6범주, OWASP 정의)

각 컴포넌트·데이터 흐름·trust boundary(덜 신뢰→더 신뢰 구역 진입점)마다 6범주를 돌며
"이 위협이 여기서 유효한가? 유효하면 무엇을 하나?"를 묻는다. 대응은 4택:
**Mitigate(완화) / Eliminate(기능 제거) / Transfer(전가) / Accept(수용 — 사유 명시)**.

| 범주 | 침해 속성 | 대표 질문 |
|---|---|---|
| **S**poofing | 인증 | 훔친 자격증명·위조 디바이스로 위장 가능한가? |
| **T**ampering | 무결성 | 저장·전송 데이터를 무단 변조할 수 있나? |
| **R**epudiation | 책임추적성 | 행위자가 "내가 안 했다"고 부인하면 반박할 로그가 있나? |
| **I**nformation Disclosure | 기밀성 | 인증 없이/권한 밖 데이터가 노출되는 경로가 있나? |
| **D**enial of Service | 가용성 | 자원 고갈·잠금 유도로 서비스를 멈출 수 있나? |
| **E**levation of Privilege | 인가 | 토큰·파라미터 변조로 권한을 올릴 수 있나? |

### P1. IoT·엣지 디바이스 (라즈베리파이급)

| 항목 | 심문 질문 | 현업 기본값 | 틀리면 비용 |
|---|---|---|---|
| SD카드 마모 | 로그·DB를 SD카드에 계속 쓰면 카드가 먼저 죽는다. 로그를 RAM(log2ram/tmpfs)에 쌓다 주기 동기화할까, 외부 서버로 즉시 쏠까? | log2ram + noatime + swap 비활성 + 고내구 카드. 원격 수집 가능하면 즉시 전송 병행 | 현장 카드 교체 출동(truck roll) |
| 전원 차단 | 전원이 갑자기 나가면 파일시스템이 깨질 수 있다. read-only rootfs로 갈까, 저널링+fsck로 버틸까, UPS를 달까? | read-only rootfs + 쓰기 구역만 tmpfs (움직이는 부품 최소화) | 부팅 불능·데이터 소실 |
| 자가 복구 | 프로세스가 멈추면 누가 살리나? 하드웨어 watchdog을 켤 건가? | HW watchdog 활성 + systemd 재시작 정책. **주의: Pi watchdog 타임아웃 최대 15초 — 초과 설정 시 무한 재부팅 루프** | 무인 현장 먹통 방치 |
| OTA 업데이트 | 배포 후 기기 소프트웨어를 어떻게 갱신하나? 실패하면 현장 출동 없이 롤백되나? | A/B 파티션 원자적 업데이트 + 자동 롤백 + 서명 검증 + 단계적 배포 (AWS IoT Lens 표준) | 업데이트 실패 = 전 기기 벽돌 |
| 시계 드리프트 | Pi에는 RTC(배터리 시계)가 없다 — 오프라인이면 시간이 틀어져 TLS 인증서 검증이 실패한다. NTP 가능 환경인가, RTC 모듈을 달아야 하나? | 인터넷 가능=NTP, 폐쇄망=RTC 모듈 필수, fake-hwclock은 보조일 뿐 | 통신 두절·타임스탬프 오염 |
| 디바이스 신원 | 기기마다 고유 인증서(X.509)인가, 공유 패스워드인가? (IoT Lens IOTSEC 1·2) | 기기별 고유 X.509 + 최소 권한(자기 토픽만) | 기기 1대 탈취 = 전체 위장 |
| 연결 끊김 | 네트워크가 끊긴 동안 데이터를 버릴까, 로컬 버퍼 후 재전송할까? 버퍼 상한은? | 로컬 링버퍼 + 재접속 시 순서 보장 전송, 메모리·저장 상한 명시 | 데이터 유실 또는 메모리 고갈 |
| 영상 스트림 (카메라류) | 실시간 뷰는 RTSP 중계인가 WebRTC인가? 동시 시청자 수와 대역폭 상한은? | 저지연 필요=WebRTC, 녹화/단순 뷰=RTSP+HLS. 기기 업링크 대역 먼저 실측 | 스트림 끊김·기기 과부하 |
| 원격 접근 | 기기가 NAT/방화벽 뒤에 있으면 어떻게 접근하나? (포트포워딩 금지 전제) | 기기→서버 아웃바운드 터널(MQTT/WebSocket 상시 연결) | 원격 관리 불능 |
| 프로비저닝 | 신규 기기 초기 설정을 현장에서 손으로 하나, 구우면 끝인가? (IOTOPS 3) | 이미지에 클레임 자격증명 → 첫 접속 시 고유 인증서 발급(fleet provisioning) | 설치 인건비 폭증 |

| 프롬프트 인젝션 | 사용자 입력·문서 내용이 시스템 지시를 덮어쓸 수 있다. 도구 호출 권한 분리했나? | 지시/데이터 구분 구조화 + 도구 권한 최소화 + 출력 검증 | 데이터 유출·오동작 |
| 평가셋 | "좋아졌다"를 무엇으로 재나? 골든 질문셋과 회귀 평가가 있나? | 대표 질문 20~50개 동결 + 변경 시 회귀 채점 (Anthropic evals 관행) | 개선인지 악화인지 모름 |
| 모델 교체 | 모델 단종·가격 변동에 대비해 프롬프트가 모델 종속적이지 않나? | 모델 추상화 계층 + 교체 시 평가셋 재실행 | 벤더 락인 |
| PII | 프롬프트·로그에 개인정보가 흘러가나? 외부 API 전송이 허용되는 데이터인가? | PII 마스킹 후 전송 + 로그 보존기간 제한 | 법 위반 |

## 프로파일에 없는 도메인을 만나면

1. RECON 결과에서 그 도메인의 "반복 검증된 함정" 소스를 찾는다 (Well-Architected에 해당 Lens가
   있는지 먼저 확인 — ML·Analytics·Serverless·HPC·SAP·스트리밍·게임·금융 Lens 실존).
2. 공통 10축 + STRIDE는 그대로 적용하고, 도메인 고유 항목을 임시 프로파일로 작성해 register에 남긴다.
3. 같은 도메인을 2회 이상 만나면 임시 프로파일을 이 파일에 승격(append)한다.
