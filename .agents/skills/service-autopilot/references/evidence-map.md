# Evidence Map — 조사 항목별 근거 소스 매핑

조사 항목의 성격에 따라 어떤 근거를 어디서 찾을지 결정하는 테이블.
원칙: **검증 가능하고, 최신이고, 1차 소스에 가까운 것**을 우선한다.

## 매핑 테이블

| 조사 항목 | 1순위 근거 | 2순위 근거 | 확인 지표 |
|---|---|---|---|
| 라이브러리/프레임워크 | GitHub 저장소 (스타, 최근 커밋, 이슈 응답 속도, 라이선스) | npm/PyPI 다운로드 추이, 공식 로드맵 | 최근 6개월 커밋 활동, 메이저 버전 안정성, 라이선스 변경 이력 |
| 도메인 표준·규제 | 공식 표준 기구 (ISO, IEEE, ASHRAE, W3C, 국가 법령정보센터 등) | 업계 협회 가이드 | 최신 개정 연도, 법적 강제 여부 |
| 아키텍처 패턴 | 유사 오픈소스 프로젝트의 실제 코드 구조 | 클라우드 벤더 레퍼런스 아키텍처, 엔지니어링 블로그 | 실제 운영 사례 여부 |
| 시장·경쟁 제품 | 경쟁사 공식 문서, 가격 페이지, 릴리스 노트 | G2/Capterra 리뷰, 애널리스트 리포트 | 실제 기능 목록 (마케팅 문구 아님) |
| 사용자군·업무 흐름 | 해당 직군의 공식 직무 기술, 업계 표준 프로세스 문서 | 실무자 커뮤니티 (Reddit, 직군 포럼) | 복수 소스 교차 확인 |
| DB/인프라 선택 | 공식 벤치마크, 공식 문서의 제약사항 명세 | DB-Engines 랭킹, 실사용 후기 | 요구 규모 대비 검증된 사례 존재 여부 |
| SaaS/외부 API | 공식 API 문서, 요금 페이지, SLA | 상태 페이지 이력 | 요금 모델, 레이트 리밋, 데이터 소유권 |

## 조사 방법

1. **웹 검색으로 현재 데이터 확인.** 스타 수, 버전, 라이선스, 요금은 변하므로 학습 지식으로 단정하지 않는다. 조사 시점을 산출물에 기록한다.
2. **GitHub 저장소 확인 시** 스타 수만 보지 말고 최근 커밋 날짜, 열린 이슈 대비 닫힌 이슈, 라이선스를 함께 본다. 스타 많고 커밋 멈춘 프로젝트는 감점.
3. **교차 확인.** 단일 블로그 글은 근거가 아니다. 공식 소스 1개 + 독립 소스 1개 이상이 기준.
4. **출처 표기.** 모든 근거에 URL과 확인 날짜를 붙인다. "일반적으로 알려져 있다"는 표현 금지.

## fit_score 산정 기준

fit_score(높음/중간/낮음)는 다음 가중 요소로 매긴다. 인기 지표는 이 중 하나일 뿐이다.

1. 요구사항 충족 — Discover에서 파악한 기능·비기능 요구를 실제로 커버하는가
2. 팀 적합성 — 사용자(또는 가정된 팀)의 기존 역량과 학습 곡선
3. 운영 환경 적합성 — 클라우드/온프레미스/폐쇄망, 규제 준수 가능 여부
4. 생태계 건강 — 유지보수 활성도, 커뮤니티 규모, 라이선스 리스크
5. 총 비용 — 라이선스, 인프라, 운영 인력

카드에는 점수만 쓰지 말고 "어떤 요소 때문에 이 점수인지" 한 줄로 밝힌다.
